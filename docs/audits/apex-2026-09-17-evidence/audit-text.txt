R  is written at the last _updateReserve . deployed  is recomputed every call from the current pool
tick. Differencing a live quantity against a stale one is not a conservative floor — the error is
unbounded in whichever direction the pool has moved.

U = B0 - 0 = the entire free balance
…credited to the caller with no transfer.

call.

3. APEX-2026-003 — High, live
Custody vault 0x2E9C1F705aB967c5Af59249203d7495bDabb223b ,
RebasingAwareERC4626Common.takeShares :
uint256 prepaid = ERC20Repo._balanceOf(address(this));
ERC20Repo._burn(address(this), amount);
uint256 refund = prepaid - amount;
ERC20Repo._transfer(address(this), msg.sender, refund);   // msg.sender, not the depositor
The refund goes to whoever calls, not to whoever pretransferred. The two-step pretransfer flow
( transfer  then exchange ) is therefore front-runnable: a victim moves shares onto the vault, an
attacker calls first with a minimal burn and takes the remainder.
Fork PoC confirms. Note a 1-wei burn trips ZeroOperationOutput  at the ~1e10:1 share ratio — the
attacker needs the smallest burn yielding non-zero output (~1e11); everything above it still comes
back as "refund".
This vault correctly reverts assetIn && pretransferred , so it does not carry 001-M. Different
primitive, same root cause.

5. APEX-2026-005 — the root cause, and the one change that fixes it
All of the above are one defect: unbooked balance treated as claimable. There is no canonical
helper, so it is implemented 10 times, 4 different ways, 2 of them unsafe.
You already wrote the correct version three times. In the same file as the broken one:
// UniswapV4StandardExchangeCommon.sol:1270   BROKEN — mixes stored R with live deployed
uint256 faceBooked = R > deployed ? R - deployed : 0;
uint256 U          = B0 > faceBooked ? B0 - faceBooked : 0;
// UniswapV4StandardExchangeCommon.sol:1313   CORRECT — ~30 lines below
uint256 R = MultiAssetBasicVaultRepo._reserveOfToken(address(this));
uint256 U = b0 > R ? b0 - R : 0;
_secureShareDelivery  subtracts booked reserve and stops — and is right not to subtract deployed .
The same correct/broken pair exists in the V3 file ( :907  vs :855 ).
Best of the three is ERC4626StandardExchangeCommon._prepaidCredit:123 , which also clamps to the
caller's own declared maximum:
uint256 available = token.balanceOf(address(this)) - MultiAssetBasicVaultRepo._reserveOfToken
(address(token));
return available < maximum ? available : maximum;
The entire bug is the extra deployed  term. Delete it. Promoting _prepaidCredit  to a shared library
and routing all ten sites through it closes 001, 003, 004, 008 and 009 together.

6. Retractions — two things I flagged that are NOT defects
I required an executed PoC for every finding before sending this. Two did not survive, and I am
retracting them rather than leaving them on your plate.
beforeSwap  missing _onlyPoolManager()  — WITHDRAWN, false positive
I claimed UniswapV4StandardExchangeBalancerQuadStableBufferHookHooksTarget.beforeSwap  lacked
the guard its siblings have. It does not. Its first line is:
BeforeInitializeLib.beforeInitialize(key);
which itself begins if (msg.sender != Repo._layout().poolManager) revert NotPoolManager();  plus
validates currency ordering, token binding, the dynamic-fee flag, tick spacing and poolKey.hooks == 
address(this) . Strictly stronger than the guard I said was missing.
Confirmed empirically: a direct EOA call reverts 0xae18210a  ( NotPoolManager() ), and it is also
rejected when called from inside an attacker-opened PoolManager.unlock()  — the only context
where _take / _settle  would not trip the manager lock.
My error: I grepped for the guard's name, not its behaviour.
Weighted-hook dust refund — downgraded High → informational
I claimed any resting face balance on the weighted hook was claimable. Measured, it is not. The
buffer-first branch converts the balance into SE shares held by the hook before anything is paid out,
then re-reads:
donation placed on hook   : 500 token0
hook face balance (after) : 10            (== MAX_DUST_WEI)
attacker face balance     : 0.000999      (its own unused join input)
attacker contributed      : 1 token0
=> donation buffered into SE shares held by the hook; accrues to LPs, NOT to the caller
No net profit. Same result for curve quad-stable, balancer quad-stable, single-CP and dual-CP. Two
further attempts to reach the unsafe preview == 0  branch naturally also failed.
Still worth a cleanup on principle: to = msg.sender  is the wrong destination, and its safety depends
entirely on a downstream call in a different contract fully consuming the balance. A future SE that
under-consumes turns this into a real leak with no change to the hook files.
