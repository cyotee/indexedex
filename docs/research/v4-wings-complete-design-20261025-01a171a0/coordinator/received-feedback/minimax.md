I accept the §12 characterization of my original as "sometimes mint before placement"; my original's §7.4.3 did mint at `V_before` and rely on a value-neutrality argument that the draft's ordering does not need.

The coordinator is right that a price-distance bound does not bound attacker-created ticks inside that distance, and that skipping ticks breaks exact parity of the simulated path and of fee accounting. 4. **A separate `depositWithEntrySwap` route with the spread charged to the entrant (my original §7.4.5/§7.4.6).** Withdrawn in favour of one credit rule for all entry. The draft's structure — one mint equation, one deposit machine — is simpler than my two-route proposal, and I support it subject to C-MIN-01.

## 3. Concerns

### C-MIN-01 — The credit unit and the cost-allocation sentence are mutually exclusive under the draft's own marking
**Location:** §3 ("Use an old-equity upper valuation `A_hi` and contribution lower valuation `C_lo`…"; "Credit cannot be fixed from post-swap wallet tokens and then assumed unchanged by a lossy reference-valued LP placement. Either credit final retained liquidity/idle as above, or retain the assets idle. **The entrant bears its allocation cost.**"), §3 illustration, §4 steps 7 and 9, §12 row "Fees and placement cut".
**Evidence:** Under the draft's marking the mark increments by `V_ref(ΔL_j)` — the reference-composition value of the added liquidity — because reference range value is linear in L at fixed bounds/P. The tokens the entrant actually pays are the *live-price* principal `Δprincipal`, whose reference value is `V_ref(Δprincipal) ≠ V_ref(ΔL)`. For a full-range core with `P = token1/token0` and target = token0, using the draft's own `x0_ref = L(1/z − 1/b)`, `x1_ref = L(z − a)`, `z = clamp(√P,a,b)`, the difference of the two reference values is `Δ = 2·ΔL·(1/√P − 1/√q)` in target units — proportional to `(P − q)` and to the increment's size, **not** to rounding. Consequently:
- If `C := V_ref(ΔL)` (the mark increment), the conservation identity `N_after = A + C` is exact, but "the entrant bears its allocation cost" is **false**: the difference `Δ` is absorbed by the existing holders as a book-level revaluation at P.
- If `C := refvalue(entrant's net token outlay)` (so the entrant does bear it), then `N_after − A ≠ C` and §3's identity breaks.
The draft currently asserts both, and §4 step 9's "compute final C and m" does not resolve which is computed.
**Requested correction:** choose one and state it.
- (a) `C` = mark increment ⇒ delete "The entrant bears its allocation cost" and replace it with: "the placement difference `Δ` is a book-level revaluation at P, disclosed in the preview (add a field `expectedCredit` alongside `refValueOfOutlay`), bounded by the deviation band times the touched position's size, and borne by existing holders"; add a validation test that the **actual** reference value of the book after entry equals `A + refvalue(outlay)` within `Δ_max`.
- (b) `C` = reference value of the outlay ⇒ this only works if the placement is restricted to cases where `Δ = 0`, i.e. the overage is retained as idle (the escape the draft already offers in §4 step 7) and the increment is placed at bounds whose reference composition equals the live composition. State that restriction explicitly, or re-base `A` and `C` on actual holdings at P — which reopens the denominator question the coordinator correctly closed.

### C-MIN-02 — Fee/principal separation must come from fee growth, not from `feesAccrued`
**Location:** §3 ("Additions whose principal delta is netted against collected old fees require explicit principal/fee separation"), §4 steps 2, 6, 8 ("Record principal and fees separately… The current callback's aggregate local delta alone is insufficient attribution").
**Evidence:** `lib/crane/contracts/protocols/dexes/uniswap/v4/interfaces/IPoolManager.sol:129-136` — `modifyLiquidity` returns `(BalanceDelta callerDelta, BalanceDelta feesAccrued)`; `callerDelta` is documented as "the total of both principal, fee deltas, and hook deltas", while `feesAccrued` is "Returned for informational purposes" and carries the warning that it "can be artificially inflated by a malicious actor" (donation to self-inflated `feeGrowthGlobal`). The current `UniswapV4UpperLowerWingsStandardExchangeVaultExecutionDelegate.sol:_modify` discards `feesAccrued` and settles only `callerDelta`. If the new separation is implemented by adopting the `feesAccrued` return, the draft would import a donation-inflatable, informational number into the denominator `A` — the APEX-2026-040 donation vector in a new location. The safe attribution already exists: `UniswapV4UpperLowerWingsStandardExchangeVaultInventory.sol:39-49` `earnedFee(L, growthInside − last)`, which `Harvest.snapshot` uses.
**Requested correction:** specify that fee attribution derives from **fee growth** (`getFeeGrowthInside` minus the position's last checkpoint), state that `feesAccrued` is untrusted and must not enter `A`, `C`, or the rounding bound, and state the rounding direction of the principal delta (the pool rounds in its favour on a decrease).

### C-MIN-03 — The mark-to-assets gap is a closed-form, unstated and currently unbounded quantity
**Location:** §3 (the `x0_ref/x1_ref` formula; "The reference composition is a valuation basis, not a claim that those token quantities are presently in custody"), §9 ("Bound before/after spot deviation and cumulative new credit per reference interval/round"), §13.
**Evidence:** A concentrated position's composition is a pure function of `(L, price, range)` — `UniswapV4UpperLowerWingsStandardExchangeVaultInventory.sol:18-42` — so there is no path dependence: the actual holdings are `f(q)` and the reference holdings are `f(P)`. The gap in reference value is therefore a closed form in `(P − q)` per range, not a drift. For the full-range core it is `2L(1/√P − 1/√q)`; for a wing, when the reference and the live price fall on opposite sides of the wing boundary, the wing is marked as if it held a *different token or a mix* than the one it actually holds — a gap of the order of that wing's whole reference value, for a deviation as small as one boundary crossing. §9's band bounds `(P − q)` at the instant of an operation; it does not state the resulting mark-to-assets gap, and it does not bound the gap **across** a session (the band is per-operation). The user's "full economic credit for retained overage" is denominated in the mark, while §6 pays **actual tokens** on exit — the two are different objects and the draft never reconciles them.
**Requested correction:** add a subsection giving (i) the per-range gap formula, (ii) the band-implied maximum gap as a fraction of `N(book;P)`, (iii) an explicit statement that the exit pays actual tokens so the mark-to-exit gap is borne by the holder unless bounded, and (iv) a validation test that the post-entry actual reference value equals `A + refvalue(outlay)` within the declared `Δ_max` (paired with C-MIN-12(i)).

### C-MIN-05 — The consumer-side consequence of an exact, revertible `getRate` must be stated as eligibility
**Location:** §1 item 4, §7 ("If `S<U`, the whole-share slice does not exist: getRate is unavailable/reverts, including at zero supply"), §11.
**Evidence:** the current implementation publishes a synthetic `1e18` at zero supply (`UniswapV4UpperLowerWingsStandardExchangeVaultEconomicTarget.sol:27-30`), so the draft changes the empty-vault convention. The buffer hooks fail closed on a failed or zero rate read — `contracts/hooks/uniswap/v4/libs/UniswapV4SeBufferHookLegLib.sol:133-152` (`RateProviderFailed`) and `contracts/hooks/uniswap/v4/libs/UniswapV4SeBufferHookContextQuoteLib.sol:24-30` — so a reverting `getRate` **freezes the consumer**. `S < U` is not an exotic state: it is reachable at launch for any pair whose seed does not reach one whole share, and in normal operation after any redemption that takes supply below one whole share.
**Requested correction:** add to §11 an explicit eligibility statement — "the vault must not be registered as an `IRateProvider` subject for the buffer-hook families while its canonical rate can revert" — and record the `1e18` empty-convention replacement and the below-one-whole-share state as named changes in §14, not only as internal states.

### C-MIN-06 — The rate's unit convention is unstated and differs from the existing adapter's convention
**Location:** §7 rate formula; §2 ("18-decimal shares"); §11.3.
**Evidence:** the draft's `rate(q) = floor(T(q)·10^dS·10^18/(q·10^dT))`, evaluated at `q = U = 10^dS`, gives `T(U)·10^18/10^dT` — i.e. **1e18 × (whole target units per whole share)**. The existing Balancer adapter publishes a different convention: `contracts/protocols/dexes/balancer/v3/rateProviders/standardExchange/StandardExchangeRateProviderFacet.sol:86-96` computes with `numeratorDecimals = 18 + subjectDecimals` and returns `mulDiv(out, 10^(18+subjectDecimals−targetDecimals), shares)`, i.e. **raw rate-target units per 1e18 raw subject (share) units**. With the draft's `dS = 18` and a 6-decimal target the two differ by `10^dS/10^dT = 1e12`. §11.3's "Reject/rewrite the chosen wiring explicitly and test it" is aimed at the adapter's *full-supply* derivation, not at a silent unit mismatch between the vault's canonical rate and the adapter that is supposed to forward it. The vault's own second rate — `UniswapV4UpperLowerWingsStandardExchangeVaultSYTarget.sol:30-33` `exchangeRate()` — publishes the whole-book-liquidation average per raw share and has no stated convention either.
**Requested correction:** state the canonical unit convention once ("target-whole-units per whole share × 1e18"), state that it is **not** the adapter's convention when `dT ≠ 18`, add a §14 row for the rate-unit change, and require `SYTarget.exchangeRate()` and `StandardExchangeRateProviderFacet._normalise` to be re-derived against it.

### C-MIN-07 — The SY internal redemption must be reconciled with the removal of public pretransfer credit
**Location:** §4 step 3 ("No arbitrary public pretransfer surplus claim…"), §7 (SY paragraph), §8, §7 ("First release supports exact-input plus minima").
**Evidence:** the SY route redeems **vault-held** shares through the push path: `UniswapV4UpperLowerWingsStandardExchangeVaultSYTarget.sol:11-17` calls `Money.redeem(shares_, minimum_, receiver_, /*pushed_*/ true)`, and `Money.redeem` with `pushed_ = true` calls `LocalCreditLib.requirePretransferCaller(msg.sender)` (`contracts/utils/LocalCreditLib.sol:24`) and takes the holder balance as `address(this)`. The draft's §4 step 3 language is compatible with keeping a **self-caller** path, but never says so, and §7 discusses SY only in terms of the exchange rate. Separately, withdrawing exact-output (§7) removes the push-refund path in `UniswapV4UpperLowerWingsStandardExchangeVaultOutTarget.sol` (`Money.pretransferBudget` / `Money.refund`), which the draft does not state.
**Requested correction:** state that SY's internal held-share redemption remains authenticated by the vault's own caller identity and never by a public pretransfer flag; state that the exact-output push-refund path is withdrawn together with exact-output, and that `Money.pretransferBudget`/`Money.refund` leave the first-release surface.

### C-MIN-08 — Terminal/zero-supply accounting: a new senior claim, three silent ruling overrides, and a unit-ambiguous rounding bound
**Location:** §2 (zero-supply surplus → "an immutable designated recovery recipient"; "genuine non-shareholder liabilities"), §3 ("reference value of owned idle + accrued fees − real liabilities"), §5 (bootstrap, "allowed issuance reference-rounding loss no greater than `ceil(C/10^12)`"), §6, §14.
**Evidence and gaps.**
- (a) §2 creates a **non-shareholder claim** that §3 then subtracts from `N`. The draft never states its priority, its discharge trigger, its beneficiary's enforcement path, or whether it survives the terminal redemption that §6 says must "settle every real asset or defined surplus liability". If it is senior, then at `S = 0` the book value is zero and the first depositor's `A` is reduced by it — a senior claim ahead of shareholders. A designated recipient able to pull vault tokens is also an administrative-withdrawal surface that PRD §3 forbids, and it is not reconciled with §8's "no first-release portfolio-funded swap" or §1's "no administrative asset withdrawal" posture.
- (b) The draft **silently drops three owner-rulings** and must name each override with its cost: **O5** (the `IVaultFeeOracleQuery.liquidReservePercentageOfVault` sleeve) — the draft has no sleeve anywhere, and idle becomes ordinary pro-rata inventory; **O7** (at least one native target unit retained locally while shares remain outstanding); **O1/O3** (residual inventory unowned at zero supply; pre-existing donations benefit the first depositor) — the draft reverses both by excluding pre-existing surplus from the first minter and assigning it to a recipient. The brief requires that changed expectations be "explicitly named", and the PRDs record these as owner rulings.
- (c) The rounding bound `ceil(C/10^12)` is **unit-ambiguous**: read in raw target units it is one whole token for a 6-decimal target — the exact failure Grok names ("A 1 wad tolerance on a 6-decimal token would be an entire token. Do not do that."). Only a relative form is scale-free.
**Requested correction:** specify the surplus payable's priority, discharge trigger and terminal treatment (or drop it and restore O3's first-depositor rule); add explicit §14 rows for O1/O3, O5 and O7 with their costs; and restate the rounding bound as relative (`≤ ε·C`, ε ≤ 1e-12, plus a quantum expressed in the `1e36`-per-whole-target accounting unit), never as `ceil(C/10^12)` in raw units.

### C-MIN-09 — The machine never says how a wing is first created, and the epoch budget has no unit
**Location:** §4 step 7 ("Add token0 overage to an eligible **existing** upper wing and token1 overage to an eligible existing lower wing"), §8 ("no-swap wing replacement… Charge permitted loss to an immutable cumulative epoch budget"), §14.
**Evidence:** `UniswapV4UpperLowerWingsStandardExchangeVaultGeometry.sol:16-38` derives wing bounds from the **live** price, so wing creation is a live-price-dependent act. In the draft, deposits only add to *existing* wings and §8 describes only *replacement* — so in the steady state a target-only deposit's overage has no destination: §4 step 7 leaves it "credited idle" (earning nothing) or refunded. That is materially idle-heavy and undercuts the product's purpose ("a reserve exposed to trading fees"). If the epoch budget is a fraction of `N(book;P)`, it is denominated in a mark that itself moves (C-MIN-03); if it is an absolute target amount, the draft must say so and say at which reference it is evaluated.
**Requested correction:** add the wing-creation lifecycle to §8 (who creates it, from what inventory, at what bounds, how its credit and reference cost are handled), or state explicitly that the first release has **no wings** and that the family's scope and name change accordingly; and specify the epoch budget's unit and its reference value.

### C-MIN-10 — Correct the liveness sentence; add the deploy-time work-feasibility check
**Location:** §10 ("Deposits without a swap and in-kind exits do not depend on that sale walker. Target-only deposit execution, target redemption and getRate may still fail for work/gas/depth."), §13, §14.
**Evidence:** three distinct failure classes are merged. (i) The **quote** work limit is `stepLimit = 512`, hard-coded at `UniswapV4UpperLowerWingsStandardExchangeVaultCommon.sol:31`, and is reached by the preview walker (`UniswapV4UpperLowerWingsStandardExchangeVaultLiquidationQuote.sol:298-336`); because §4 step 5 derives the deposit swap's price limit from the **reference** rather than from a quote, the deposit's **execution** does not consume the walker — only its preview does. (ii) Execution gas is a different limit. (iii) Market depth is different again. Separately, APEX-2026-026's own fix proposes a **deploy-time** check that a full empty-word walk fits the budget for the configured spacing, and Kimi recommends a minimum tick spacing; the draft's §14 owner-decision list includes neither.
**Requested correction:** split §10's sentence into the three failure classes and say which surface each applies to (preview / execution / market), stating explicitly that the default swap's *execution* does not need the walker while its *preview* does; add tick spacing and the deploy-time work-feasibility check to §14 and to the §13 gates.

### C-MIN-11 — Foreign-unlock restrictions: view behaviour, and the atomicity of §11.2
**Location:** §4 step 10 ("foreign unlock contexts do not get a skip-harvest/cash-payment branch"), §6 step 3 ("Public economic views cannot observe a lower supply backed by the old book"), §11.2, §11.4.
**Evidence:** the draft constrains the **money paths** ("manager locked-at-entry") but never states the behaviour of the **views** (`getRate`, previews, `quoteRate`, `liquidationValue`) while the manager is unlocked. APEX-2026-012's fix asks for exactly that ("guard `getRate()`, `liquidationValue()` and `preview`/`requiredInput` the same way"), and the current code is exposed: `UniswapV4UpperLowerWingsStandardExchangeVaultMoney.sol:41-48` (`begin`) has no unlocked check, and `:94-104` (`_harvest`/`_place`) silently no-op while unlocked. Separately, §11.2's "execution-backed route redeems the relevant actual-size shares before paying target proceeds" reads as an atomic in-unlock redemption, which §11.4 and the manager lock forbid — `UniswapV4UpperLowerWingsStandardExchangeVaultCommon.sol:43` reverts `ManagerAlreadyUnlocked`, so the vault cannot open its own unlock inside a foreign one. The redemption must therefore be prepared **outside** the outer unlock, which makes the flow two-transaction and non-atomic; that is a material property for a consumer designing against it.
**Requested correction:** state the view behaviour under a foreign unlock (revert, or quote a projected state) in §4/§6/§11; amend §11.2 to say that the redemption occurs outside the outer unlock (two transactions) unless a separately designed authenticated shared-unlock path is built; and state the business-scope consequence plainly in §1 or §14 — in this first release the user's second need ("shares to be used in liquidity") is served only by the §11 "distinct asset" listing, not by the parity/buffer integrations.
