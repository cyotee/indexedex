## Concerns

- **K1 (medium) — Zero-supply / sub-one-share `getRate` reversion breaks the recorded first-buffer rate expectation.** Draft §7: `getRate` reverts when `S < U`, including at zero supply, with "an initial issuance-price query is separate." But `StandardExchangeRateProviderFacet._getRate` explicitly relies on a well-defined zero-supply rate: at `totalShares == 0` it calls `_initialRate`, which inverts a unit-target deposit preview, and its own comment records D60 (2026-09-22): "Hooks bind fresh SEs and read the rate on the first buffer" (source: `StandardExchangeRateProviderFacet.sol:71-96`, read this pass and on the initial pass). A reverting zero-supply canonical rate therefore breaks the first-buffer binding flow unless the replacement wiring's zero-supply behavior is specified. **Requested correction:** the final report must either (a) specify that the "separate initial issuance-price query" is what the rate provider consumes at zero supply, with the exact interface, or (b) state plainly that hook/buffer integrations are ineligible until supply exceeds one whole share, as a named change to the D60 expectation.
- **K2 (medium) — No consolidated requirement-change list; the exit-liveness amendment is made in substance but never named.** The draft changes the meaning of PRD exit-preservation requirements (SO from my initial read: `UNISWAP_V4_UPPER_LOWER_WINGS_STANDARD_EXCHANGE_VAULT_PRD.md` §11 SEC-10 "Disabled inbound preserves supported holder exits" and the APEX-026 design note citing PRD :189 freezing all ordinary routes as a release blocker and :308 SEC-10) by accepting that the strict target route and `getRate` can be dust-frozen, leaving in-kind as the only guaranteed exit. §12 is a disagreement table and §14 is owner decisions; neither enumerates prior-expectation amendments the way all four originals did. **Requested correction:** the final report should carry one explicit requirement-change table, including at minimum: the SEC-10/PRD:189 exit-preservation amendment (in-kind becomes the guaranteed exit), the D60 zero-supply rate expectation (K1), the share-decimals change and its consumer incompatibility, the removal of advertised exact-output routes (PRD §10 "Exact-output target/share routes" row), and the removal of foreign-unlock/blocked-route operation (current `Money.sol:167-170` sleeve-limited blocked redeem semantics).
- **K3 (low-medium) — APEX-026 disposition needs an explicit owner sign-off framing.** Given K2, the final should state the 026 outcome as a decision to be accepted ("only in-kind exit is guaranteed under dust-tick attack; strict target exit and the rate may revert truthfully"), not merely as a table row, because the 026 design note records the owner requiring exhaustion-revert *and* exit preservation simultaneously — the draft resolves that tension by narrowing "exit" to the in-kind route, which the owner should see stated plainly.
- **K4 (low) — Converted-wing lifecycle during a reference outage is consistent but unwritten.** Entry checkpoints *without* converted-wing closure (§4.2), a live wing slot cannot be overwritten (§4.8), and wing replacement is reference- and epoch-gated maintenance (§8). Therefore, during an extended reference outage, a fully converted wing's inventory is parked (neither closed nor replaceable), and overage credit into that wing degrades to idle retention or refund (§4.7). The machine remains safe — in-kind exit still works — but the final should state this degrade path explicitly so integrators are not surprised that a two-sided book can sit unrotated for the length of an outage.
- **K5 (low) — Per-reference-interval entry caps are griefable.** §9's cumulative-credit cap per reference round, with no replenishment on withdrawal, bounds stale-reference exposure but gives an attacker a cheap issuance-DoS: burn the interval cap with own deposits to block entries until the next round. The draft's "caps reduce exposure, not oracle truthfulness" sentence does not name this tradeoff. **Requested correction:** one sentence in the final naming the griefing surface and assigning the cap size to the owner as a liveness-vs-exposure parameter.
- **K6 (verification request, not an error) — Boundary-straddling reference/live price cases.** Because §3 values ranges at the reference composition while custody/removal follows the live composition, the final's validation plan should explicitly include cases where the reference price and live price straddle a wing boundary in both directions (reference inside wing / live outside, and vice versa), asserting that issuance fairness holds at the deviation-bound edge. This is where the valuation-convention error is largest per unit of price gap.
