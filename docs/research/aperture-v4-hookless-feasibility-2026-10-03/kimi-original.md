## 1. How OptimalSwap actually works (traced, not README)

`OptimalSwap.getOptimalSwap(pool, tickLower, tickUpper, amount0Desired, amount1Desired)` returns `(amountIn, amountOut, zeroForOne, sqrtPriceX96)`. It is a **view returning numbers**; a separate layer executes. Inputs read on-chain: `sqrtPriceX96AndTick`, `liquidity`, `fee`, `tickSpacing`, tick bitmap words, `liquidityNet`. Inputs supplied by caller: target range and desired amounts. Steps:

1. **Direction selection** — `isZeroForOne(...)`: closed-form comparison of the wallet ratio against the position's required ratio at current price (out-of-range cases return the forced direction).
2. **`crossTicks` — monotone final-segment discovery.** A `do…while(true)` loop walks initialized ticks in the swap direction (`TickBitmap.nextInitializedTick` with word caching). Each iteration runs `SwapMath.computeSwapStepExactIn` on the *remaining input budget* and asks two questions: (a) did the budget run out inside this segment (`sqrtPriceX96 != sqrtPriceNextX96` → break); (b) did the optimal direction flip at the next tick (`isZeroForOne(post-step amounts) != zeroForOne` → break). Otherwise it applies `liquidityNet` and continues. **This is not binary search over candidate sizes, and it is not execution traversal of an already-sized swap**: it is read-only simulation of successively larger swap prefixes to locate the segment containing the optimum. Termination is guaranteed by budget depletion or sign flip; there is no explicit step cap (work is naturally bounded by remaining budget and initialized-tick density — an uncapped loop whose iterations are economically bounded, which our work-bounded law would still need to cap explicitly).
3. **Edge handling** — if the final price would leave the target range: either consume all input (fully out-of-range deposit) or swap exactly to the range boundary and update amounts.
4. **Terminal quadratic** — `solveOptimalZeroForOne` / `solveOptimalOneForZero`: one `FullMath.sqrt(b² + a·c)` (with a, c pre-doubled so the formula is `(√(b²+4ac)+b)/2a`), giving the optimal final sqrt price in the last segment; `amountIn`/`amountOut` are then computed with `SqrtPriceMath` deltas and the fee gross-up `×1e6/(1e6−f)`. Clamps: final price is clamped toward the current price when the wallet ratio is already at/past optimal ("calculated price may increase if the ratio is close to optimal") — i.e., a **no-swap optimum is handled**, and the root is an analytic candidate with integer clamps, not a proven-exact integer optimum.

**Coefficients (zeroForOne, from source):** with active liquidity `L`, fee `f`, current/lower/upper sqrt `s, w, u`:
```
a0 = x + L/((1−f)·s) ; a = a0 − L/u
b  = a0·w + f·L/(1−f) − (y + L·s)·Q96/u
c  = y + L·s − L·w/(1−f)
t  = (√(b² + 4ac) + b) / 2a        ; amountIn via getAmount0Delta(t,s)·1e6/(1e6−f)
```
The equation being solved: choose final price `t` so post-swap wallet amounts exactly match the ratio the target position requires at `t`, where the swap's price impact is `L`'s. It knows **only** wallet amounts, pool `L`, `f`, and `[w,u]`. `L` in the coefficients is the **pool's active liquidity** (impact), not the position's own liquidity — the position's own liquidity cancels out of the ratio condition. This is why it cannot, as written, see an incumbent vault position.

## 2. Execution layer (Automan.sol)

`mintOptimal(params, swapData, token0FeeAmount, token1FeeAmount)`: pull both desired amounts (either may be 0 → **single-token entry is the native case**); deduct explicit caller-supplied fee amounts bounded by `checkFeeSanity` (≤ `feeConfig.feeLimitPips`); `_optimalSwap(..., swapData)` — **`swapData.length == 0` ⇒ `_optimalSwapWithPool`: fully on-chain sizing + direct `pool.swap`; nonzero ⇒ allowlisted router with caller calldata (the class-B path)**; then `_mint` via the NFT position manager and **refund surplus** (`amount0Desired − amount0`) to the recipient — actual-fill accounting with refunds, not retain-and-credit. `increaseLiquidityOptimal` mirrors this for existing NFTs. Zap-out (`decreaseLiquidity` → `_collectDeductFees` → `_swapRefund`) swaps the **entire** other-token balance to `tokenOut` (sized conversion, no sizing loop) and enforces `tokenOutMin` on the post-swap balance. Automation entry points (`rebalance`, `reinvest`) are `isController`-gated; position ops check NFT ownership. Notably there is **no impact bound on the optimal swap itself** — the computed final sqrt price is implicitly the swap's limit; slippage lives in the mint's caller-supplied `amount0Min/amount1Min` and the fee cap.

Deployed production evidence: Aperture's transparency page (`docs.aperture.finance/docs/transparency/deployed-contracts`) lists Automan and "Optimal Swap Router" across 8 chains — deployment popularity, not a safety proof.

**V4 port search:** found `Aperture-Finance/uniswap-v4-hooks` (a hook-based LP-automation design — *hooks*, incompatible with our `poolKey.hooks == address(0)` admission), `Aperture-Finance/v4-core` (plain fork), a hackathon backtester, and v4-sdk *dependencies* in their TS SDK. **No official hookless V4 OptimalSwap port located** — evidence of absence in searched official sources, not a nonexistence proof.

## 3. Verdict (1): one V4 hookless position — YES, with a port

The math is V3/V4-identical in the relevant respects. Port map:
- `V3PoolCallee` reads (`slot0`, `liquidity`, `fee`, `tickSpacing`, bitmap, `liquidityNet`) → V4 `StateLibrary`/`extsload` on the singleton; `PoolKey.fee`/`tickSpacing` are static for hookless pools (dynamic fee impossible without hooks — this *simplifies* the port).
- `SwapMath.computeSwapStepExactIn` (Aperture's uni-v3-lib) → V4 `SwapMath.computeSwapStep`; our impl plan already reproduces `ProtocolFeeLibrary.calculateSwapFee` (`docs/plans/UNISWAP_V4_FULLSPREAD_IMPLEMENTATION_AND_TEST_PLAN.md:107`). The quadratic's `f` is the *total* swap fee pips; the protocol/LP split affects fee **ownership** (next section), not the gross-in equation.
- Direct `pool.swap` → `manager.swap` inside an `unlock` with delta settlement; native-currency handling added.
The discovery loop ports unchanged (bitmap via `extsload`). So: an idle, single-pool, exact-input, single-token zap into **one** position is achievable with a direct port plus the settlement wrapper. Not free: work-cap the discovery loop, add our impact/shortfall checks, and choose reject-vs-discover policy (§5).

## 4. Verdict (2): whole-book fungible vault — CONDITIONALLY YES; the algebra extends, and here is why

Our requirement (PRD D5): for credit `c`, choose `x` so `C = (c−x, out(x))` aligns with the **post-swap incumbent book** `B_i(x) = D_i(x) + F_i + E_i(x)` (credit excluded, fees once), then `m = min(floor(S·C_i/B_i))`. Prior rounds established Aperture lacks these fields; the question is whether adding them breaks the closed form **within a fixed segment**. Derivation (zeroForOne; Q96-normalized real algebra; `l` = incumbent position liquidity, full-range core so `l` never crosses its own bounds; `w,u` = core bounds; `F'₀ = F₀+E₀ⁱⁿⁱᵗ`, `F'₁ = F₁+E₁ⁿⁱᵗ` frozen before the swap):

```
net in:   n(t) = L·(1/t − 1/s)          gross x = n/(1−f)
caller:   C0 = c − n/(1−f)              C1 = L·(s − t)
incumbent:B1(t) = l·(t − w) + F'₁                       (D1 in-range; E1 unchanged — fees accrue in input token0)
          B0(t) = l·(1/t − 1/u) + F'₀ + f·l·(1/t − 1/s) (D0 + own-LP fee share f·n·(l/L) of the pool's fee growth)
align:    C0·B1(t) = C1·B0(t)
```
Substituting and clearing `1/t` (multiply through by `t`): both sides become products of two affine functions of `t` ⇒ **`A·t² + B·t + C = 0`, degree unchanged**. The basis functions are exactly Aperture's `{t, 1/t, const}`: `F'` terms are pure constants; the own-LP fee term `f·l·(1/t − 1/s)` has the same `1/t` structure as the swap input; incumbent `l` plays the same algebraic role as the wallet-side constants. Coefficients are polynomial in `(c, s, L, l, f, F'₀, F'₁, w, u)` — same Yul-solver pattern, more terms. **This refines my own round-1 statement ("no general arithmetic inverse"):** the correct statement is *no degree increase inside a fixed segment with frozen F/E and no boundary crossing* — the blockers are integer rounding, segmentation, and placement, not algebra.

What breaks or bounds it, honestly:
- **Integer reality:** net-input floors, sqrt-price rounding, amount-delta rounding, and `feeGrowth` flooring (`floor(lpFee·2¹²⁸/L)·l/2¹²⁸`) mean the continuous root is a **candidate**, not the integer predicate. But our acceptance is an *inequality* — `10000·m·B_i ≥ 9999·S·C_i` (1 bp, `ProtectionMath.sol:105–110`) — not equality. One candidate (root, or root±1 wei variants as a fixed stencil) plus exact integer verification is a **reject policy, not a probe sequence**: pass ⇒ search-free acceptance; fail ⇒ atomic revert. Liveness (how often a passing integer exists when the candidate fails) is an empirical gate, unquantified here. Grok's round-1 objection (a failing check doesn't prove no nearby integer passes) limits *completeness claims*, not the legality of the policy.
- **Segmentation:** if the optimal price crosses an initialized tick, `L` changes and the fee-accrual slope changes — coefficients must be recomputed per segment. Options: (a) Aperture's monotone discovery (bounded; the round's prompt explicitly contrasts this with trial sizing and does not ban it); (b) single-segment **certificate**: solve in current segment, verify root ∈ segment and no sign flip, revert otherwise. Our 50 bp composition-impact bound keeps the typical price move within ~0–2 initialized ticks in liquid pools, making (b) viable for common traffic; (a) with an explicit step cap is the fallback for thin liquidity. Out-of-range wings add **position** boundaries to the segmentation set, but an out-of-range wing's amounts are `t`-independent while uncrossed — wings *simplify* coefficients (constant terms) until a boundary crossing, which then defines a new segment.
- **Placement rounding:** post-mint placement loss is another integer delta deducted from `C` or `B` (current planner does this, `TransitionPlanner.sol:135–143`); it must sit inside the same verification, or placement must be deferred to maintenance so admission math stays clean (the precedent-round lesson: admission independent of placement).
- **Frozen conventions:** collection timing (`E→F` before credit/quote), one consistent fee-ownership rule (protocol fee never in `E`; own LP share once), and residual law. Aperture *refunds* rounding surplus; our law (D8/D16) **retains and books** it — under a near-exact root the residual is dust either way, but the semantic choice is an owner decision, not a detail.

**Answer for (2):** Aperture *as-is* does not zap a fungible whole-book vault; the fixed-segment whole-book equation **is derivable and remains quadratic** (coefficients above — new this round), so a Hookless zap could replace the 32-refinement `_composition` loop (`TransitionPlanner.sol:73–108`) with: bounded segment discovery or certificate → one quadratic solve → exact integer verification (1 bp inequality, 50 bp impact, 10 bp shortfall vs the fee-inclusive forward quote) → execute the single computed swap → place/mint → book residuals. That is engineering port + verification work, **not** established safety: no integer proof, no liveness measurement, no multi-position case yet.

## 5. Verdict (3): autonomous Orbital/SY nesting — NO from Aperture alone

- **Already-unlocked manager:** a V4 port must `unlock` to swap; nested unlock is forbidden (`PoolManager.unlock` reverts `AlreadyUnlocked`; current law PRD §4). Inside Orbital's hook callback on the same manager, the zap path is unreachable; blocked-state stays sleeve-only F1/F2 (`StandardExchangeConstantProduct.sol:78–110`) regardless of any sizing advance. Aperture contributes nothing there.
- **Fungibility/shares:** Aperture mints NFTs; there is no `S`, no min-ratio mint, no share inverse. Orbital needs fungible SE shares synchronously.
- **Outer searches:** the quadratic sizes **exact input** only. `_faceForClaim` (`OrbitalBufferHookExitQuoteLib.sol:347–373`) and `_invertBufferForEffective` (`OrbitalBufferHookClaimLib.sol:250–273`) need an exact-*share* (exact-output) inverse — unchanged, still eliminable only by the CP `_amountInForShares`-style closed form, not by Aperture. `zapSplitWad` (`OrbitalBufferHookMath.sol:270,317,336`) is Orbital's sphere-residual split — untouched. Exact-output scalar redemption stays `InvalidRoute` beyond linear domains, as today.
- **SY:** `NativeStandardYieldTarget.sol:20–77` aliases the SE routes; it inherits whatever the SE does, nothing more.

## 6. Protections, residuals, and the concrete autonomous call sequence

Idle exact-input scalar deposit under the derived design: (1) freeze credit, `F'`, policy; read slot0/L/fee/bitmap; (2) direction + segment (certificate or capped discovery ≤ explicit constant); (3) solve quadratic with whole-book coefficients; (4) verify candidate: root-in-segment, `max(P'/P, P/P')−1 ≤ 50 bp`, funding, and `10000·m·B_i ≥ 9999·S·C_i` on exact integers after placement-loss attribution — any failure ⇒ revert `AlignmentNotAchievable()` (no retry, no smaller-size probing); (5) execute the single computed exact-in swap inside the vault's own unlock; measure actual in/out (10 bp shortfall vs quote); (6) place per sleeve policy, mint `m = min(floor(S·C_i/B_i))`, book residuals (retain-and-sweep) or refund-dust per owner decision; (7) full booking sync. Preview uses the identical pure computation for same-state parity. Exact-output remains separate and unsupported beyond current domains.

## 8. Plain-English conclusion and ranking

Aperture locates, on-chain and without trial-and-error, the tick segment where the optimal swap ends, then solves one quadratic for the exact swap size that leaves zero leftover for a target range; a wrapper executes that exact-input swap directly against the pool and mints, refunding dust. **(1) Single V4 hookless position:** yes — direct port plus settlement wrapper. **(2) Whole-book vault:** conditionally yes — the alignment equation stays quadratic with the coefficients derived here, but needs the integer-verification layer, segment policy, and owner sign-off on discovery-vs-reject and residual semantics; feasibility is **accounting research completed to derivation stage + port work**, not a ready mechanism. **(3) Orbital nesting:** no — idle-state, exact-input, single-pool only; blocked/sleeve law and the outer Orbital loops are unaffected by it. Ranked readiness: (a) reusable now: monotone-discovery + quadratic *pattern* and the whole-book coefficient derivation; (b) port work: V4 state reads, settlement, verification layer; (c) research/liveness proof: reject-policy completeness, multi-segment/multi-position cases; (d) human decisions: discovery policy, residual semantics, license posture (GPL-clean reimplementation only).
