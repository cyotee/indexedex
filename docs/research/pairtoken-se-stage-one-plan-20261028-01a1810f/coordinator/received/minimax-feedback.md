## Concerns

**C-1 (High — mechanism gap). The fee-checkpoint-before-removal mechanism is stated as a requirement but not as a mechanism.** Draft §5.3 says "A partial remover cannot receive whole-position fees already assigned at the snapshot"; §5.2 says "finish with one poke of a nonempty position"; §6.1 says "Whole-position fees use old owned liquidity". None of these states *why* the whole-position fee cannot reach the partial remover. The load-bearing fact (verified in the sources I read in the initial pass) is: Crane's `Pool.modifyLiquidity` invokes `Position.update` **unconditionally**, i.e. outside the `liquidityDelta != 0` tick block; `Position.update` computes `feesOwed = mulDiv(feeGrowthInside − feeGrowthInsideLast, liquidity, 2^128)` on the **pre-update** liquidity and then advances `feeGrowthInsideXLast`. A zero-delta poke therefore realizes the whole position's accrued fees **and advances the checkpoint**, so a subsequent removal returns `feesAccrued == 0` and its `callerDelta` is pure principal. (The same routine reverts `CannotUpdateEmptyPosition` for an empty position — which is why "do not poke an empty position" is a hard rule, not a style preference.) *Correction:* add one sentence to §5.2 and one to §5.3 stating that every removal is preceded by a checkpoint poke on a non-empty position, and that the checkpoint's advancement of the inside-fee checkpoint is what makes the removal's `feesAccrued` zero. Without this, an implementer can satisfy §5.3's wording while still paying the whole-position fee into the remover's principal.

**C-2 (High — ordering slip). §5.3's paired-entry list reads as a temporal order that contradicts the PRD's.** The sentence lists "candidate qQuote/accepted inputs" *before* "maintenance/final fees". PRD S1-OP-01 orders it: validate → lock → isolate pending credit → preflight plan → **compound incumbent book and checkpoint fees → compute candidate/accepted input** → pull accepted ERC-20 amounts → add → compute S1-ACC-07 credit → mint. The accepted-input selection depends on **post-maintenance** reserves; the baseline gets this right (`_compound()` precedes `_quote(...)`). Read literally, the draft's order computes `qQuote` against pre-maintenance reserves. The draft's own planner architecture (§5.4, §6) makes the correct order natural, so this reads as a summarization slip rather than a design error — but it is the one sentence an implementer would code from. *Correction:* reorder to "maintenance/final fees → candidate qQuote/accepted inputs → …", or state explicitly that the candidate is computed from the post-maintenance state produced by the plan. Note the zap sentence in the same paragraph is correctly sequential and matches S1-OP-02 — only the paired sentence needs the fix.

**C-3 (Medium). Exit validation ordering.** §5.3's exit list runs "selected maintenance/final fees, snapshot S/L/B, authority check, burn, …". S1-OP-03 requires rejection of invalid recipients, missing shares, expired deadlines, and unmet minima "atomically"; S1-SEC-01's money sequence puts validation first. Checking `s`, authority, recipient and deadline *after* a fee-realizing manager mutation is safe (the transaction reverts) but wasteful and contrary to the stated order. *Correction:* move recipient/share/deadline validation ahead of the maintenance phase.

**C-4 (Medium — addition, from my original §2.4). The clamped-principal table and the baseline-vs-canonical identity are absent.** The draft requires "clamped principal/cost math" (§2.1 `FMath`) and A45 requires "canonical below/equal/interior/equal/above principal/costs", but never states the three-branch rule that is the single source of truth for `N_i`, `G_i`, removal principal and cost:

```
P ≤ sqrtLower → N0 = getAmount0Delta(sqrtLower, sqrtUpper, L, down), N1 = 0
P ≥ sqrtUpper → N0 = 0, N1 = getAmount1Delta(sqrtLower, sqrtUpper, L, down)
otherwise      → N0 = getAmount0Delta(P, sqrtUpper, L, down), N1 = getAmount1Delta(sqrtLower, P, L, down)
```

This is exactly S1-X13: the baseline substitutes the live price for the range boundary, so its `basket()` is wrong below the lower and above the upper bound and correct in the interior. Relatedly, the draft's comparison ledger (§7.5) would benefit from the verified identity that the baseline's `A0down`/`A0up`/`A1down`/`A1up`/`L0`/`L1`/`Fit` are **bit-identical** to Crane's `SqrtPriceMath.getAmount0Delta/getAmount1Delta` and `LiquidityAmounts.getLiquidityForAmount0/1/getLiquidityForAmounts` (both are `floor(floor(L·2^96·(b−a)/b)/a)` and `floor(L·|b−a|/2^96)`; `A0up` and the canonical round-up both equal `ceil` of the exact value). That converts several comparison-ledger rows from "re-derive" to "preserved, bit-identical", leaving only the boundary substitution, the attribution rules, the fee/dead-share removals and the new ledger as deviations.
