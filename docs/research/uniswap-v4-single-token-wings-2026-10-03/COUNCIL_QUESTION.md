# Follow-up question: mandatory scalar SE routes and one-sided wings

Date: 2026-10-03. Research only, not an adopted PRD or implementation permission.

## Latest human requirement (controls this design investigation)

“We can not drop the ability to accept one token for deposit or producing a single token for withdrawal. These are essential functionlaity we can not drop. The whole point of using a Standard Exchange vault is the ability to be used in a buffered pool where one token will be processed in an operation. Please reconsider our design options with this design requirement. I would like a solution that allowx for this without the binary search. If that is possible, I am willing to consider design that don't make a full-spread deposit, and instead make single sided deposits outside the tick range. Then has a management process that would consolidate out-of-range wings that move to be in-range into a single double-sided position.”

The previous basket-only recommendation is therefore not an acceptable final product. Full-range-only placement is relaxed for investigation; concentrated one-sided wings and consolidation are permitted proposals, not already approved implementation. Single-token entry and exit must remain meaningful autonomous SE/SY/buffered-pool capabilities. Do not substitute async-only receipt tokens, user-supplied opposite assets, or a router/off-chain sizing search and claim the requirement is satisfied. Explicitly distinguish exact-input scalar routes from exact-output inverses and preserve existing supported domains unless changes are named. The earlier no-nested-unlock and actual-local-cover limits remain; do not invent unlimited blocked withdrawals.
