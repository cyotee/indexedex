# Concerns

**C1 — §2.1 "Implement `sweepDust()` with one outer `nonReentrant` guard" / Task 2 — the release's arithmetic precondition and its failure mode are unstated.**
*Defect:* step 3 adds the booked donation to `residualInventory` before `_sweepDustBody()` runs, and the migration's `_beginBudget()` then computes `operationFloor[token] = IERC20(token).balanceOf(address(this)) - residualInventory[token]` in checked arithmetic (`M/UniswapV4DetfMigrationPolicy.sol:35`), with `_endBudget()` re-deriving `residualInventory[token] = balanceOf - operationFloor` (`:45`). The release therefore succeeds only while `donationInventory[token] + residualInventory[token] <= balanceOf(this)` for every released token; any overlap between the two books, or an over-booked donation, makes the whole explicit sweep revert with an arithmetic panic, so F1's "positive LP progress" proof cannot be produced. The handoff block states `next_operation_floor = held - residual_after_release` but never states the invariant, and Task 2's case list contains no case for the violated condition.
*Correction:* state the invariant in §2.1 step 3 and require the implementation to compare `donationInventory[token] + residualInventory[token]` against `balanceOf` before releasing, failing closed with the donation book untouched; and either add a Task 2 case that reaches that guard through a real path or record explicitly in §2.1 why no reachable state can violate it, so the underflow revert is a known outcome rather than an unexplained one.

**C2 — §2.3 "In `S/MigrationCoreLocalQA.s.sol`, add: …" / Stage A step 4 / Task 5 — the inherited pranked owner-first purchase is never retired, so "add" is ambiguous between adding and replacing.**
*Defect:* `MigrationCoreLocalQA is TestBase_UniswapV4DetfMigration` (`S/MigrationCoreLocalQA.s.sol:85`), and the base's `_buyOwnerFirstBond()` buys with `vm.startPrank(buyer_)` (`M/TestBase_UniswapV4DetfMigration.sol:376-387`) — a simulated call that is never part of a `--broadcast` transaction set, which is F2's premise. The script calls that inherited method at `:171` (`runMixedRecordRehearsal`) and `:199` (`_purchaseForActivation`). §2.3 only says to add `buyOwnerFirstBond(...)` and to execute "the helper's separate 1-ether paid ordinary purchase"; it never says the inherited pranked call sites go away. If the pranked call stays, it sets `ownerFirstBondTokenId` in simulation and the new real purchase then reverts with `Accounting.MigrationRewardsClosed`; if the pranked call is dropped but nothing real is mined, activation can still succeed in simulation with no owner-first bond on chain, and C7's mined-evidence requirement would be the only thing that catches it.
*Correction:* state in §2.3 that the script must retire the inherited `_buyOwnerFirstBond()` call sites (or override them to delegate to the helper's real purchase), that exactly one owner-first purchase exists in the broadcast path, and that Task 5 and C7 assert the mined owner-first bond id and owner from receipts and readbacks (`migrationOwnerFirstBondTokenId()`, `ownerOf`) rather than a console value or a simulation snapshot.

**C3 — §2.4 "R2: those input providers plus a real provider for `detf` quoted into `pairA` on the output leg" / Task 4 — the R2 output-leg provider is named in terms of an artifact that the plan's own fixture library cannot produce.**
*Defect:* the only provider factory in reach, `RateProviderFixtureLib.providerFor(create3Factory, diamondPackageFactory, se, rateTarget)` (`contracts/test/libs/RateProviderFixtureLib.sol:23-38`), always deploys the production `StandardExchangeRateProvider` for **one whole SE share quoted into `rateTarget`**; it cannot produce a provider that values the DETF. The hook does permit a provider on a raw leg ("a raw leg may carry one", `contracts/hooks/uniswap/v4/standardExchange/weighted/UniswapV4StandardExchangeWeightedBufferHookDFPkg.sol:404`) and reads it only through `IRateProvider.getRate()` (`.../UniswapV4StandardExchangeWeightedBufferHookTarget.sol:150-151`), so an SE-share-derived provider can be installed on the DETF output leg — but the output leg's rated inflow is then priced by an SE-share rate, not by any DETF value. §2.4's wording admits both readings, and the second (a DETF-quoting provider) has no source in the plan, while §2.4 also forbids inventing modes.
*Correction:* name the exact artifact and the exact expected value for R2 — e.g. install `RateProviderFixtureLib.providerFor(create3Factory, diamondPackageFactory, se0, pairA)` on the output leg and require the captured output-leg rate to equal that provider's live `getRate()` — and require `pricing-parity.md` to label the RawRate output case as an arithmetic fixture with no DETF-denominated meaning, consistent with §2.4's own "deliberate arithmetic fixtures, not approved live economics". If a DETF-quoting provider is intended, add its source to the plan or drop the R2 output case rather than leaving the implementer to choose.

**C4 — Task 2 hostile case, "separately have the token attempt reentry to `sweepDust` and verify the actual lock error" — the witness can be made vacuous by the fixture swallowing the inner revert.**
*Defect:* the reentry is attempted from the hostile token's `transferFrom` during the sweep's pull. If the token performs the reentrant call in a low-level form and ignores the returned failure, the lock error never surfaces, the outer pull succeeds, and the case passes without exercising the lock at all; only if the token bubbles the inner revert does the outer transaction fail with the lock error the draft intends to verify. The draft does not say which of the two behaviours the fixture must have, and a passing case in the swallowing shape would prove nothing about the new outer guard.
*Correction:* require the hostile fixture to bubble the inner revert so the outer call fails with the actual lock error, and require the case to assert both halves explicitly: the exact outer revert bytes for the armed-transfer path, and a separate successful-sweep outcome with the reentry attempt recorded, so the guard is observed rather than incidentally satisfied.
