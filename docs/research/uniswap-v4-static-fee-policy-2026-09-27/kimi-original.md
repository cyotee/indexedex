# Kimi K3 — Original: Static-fee readability, dynamic-fee deployment rejection, and limits of the static-fee assumption

**Date/access date:** 2026-09-27 · **Researcher:** Kimi K3 (independent first pass this round; no peer artifacts read)
**Question:** Can the new FullSpread V4 vault (V4FS, `contracts/vaults/standard/exchange/protocols/uniswap/v4/`) (a) read the configured pool fee, (b) reject dynamic-fee pools at deployment as incompatible, and (c) use the static fee in calculations under deployer hook-compatibility responsibility?
**Short answer:** Yes to all three, with one precise scope limit: the **static** guarantee covers only the *LP fee* component (`PoolKey.fee`). The **protocol fee is directional and controller-mutable** (must be read live, never frozen), and **hook callbacks can still alter swap amounts on static-fee pools** (must stay gated under the existing modeled-hook/deployer-responsibility rule). No code currently performs the dynamic-fee rejection — it is a real, small, deploy-time gap.

---

## 1. Facts (verified against local code and upstream)

### 1.1 Reading the configured fee — YES
- The PoolKey (including `fee`) is stored immutably at vault init: `UniswapV4FullSpreadStandardExchangeVaultPoolKeyAwareRepo.sol:14-17,29-36`; typed accessor `_fee()` at `:70-76`.
- Live fee state is also readable: `_slot0()` returns `(sqrtPriceX96, tick, protocolFee, lpFee)` (`UniswapV4FullSpreadStandardExchangeVaultCommon.sol:432-434` via `StateLibrary.getSlot0`).
- For a static pool these two are **equal for the pool's lifetime**: `PoolManager.initialize` sets `lpFee = key.fee.getInitialLPFee()` (`lib/crane/.../v4/PoolManager.sol:68-77`; `Pool.sol:101-107` writes slot0.lpFee at init), and the only mutator, `updateDynamicLPFee`, reverts unless `key.fee.isDynamicFee()` **and** caller is the pool's hook (`PoolManager.sol:288-295`).

### 1.2 Dynamic-fee detection is deterministic — but not currently enforced anywhere in V4FS
- `LPFeeLibrary.DYNAMIC_FEE_FLAG = 0x800000`; `isDynamicFee(fee) = (fee == 0x800000)`; `MAX_LP_FEE = 1_000_000` (hundredths of a bip); `isValid(fee) = fee ≤ MAX_LP_FEE` (`lib/crane/.../v4/libraries/LPFeeLibrary.sol:15-46`). Local port is byte-faithful to upstream v4-core `main` (fetched 2026-09-27, https://raw.githubusercontent.com/Uniswap/v4-core/main/src/libraries/LPFeeLibrary.sol).
- **Gap (fact):** `UniswapV4FullSpreadStandardExchangeVaultDFPkg.initAccount` (`DFPkg.sol:271-298`) stores the PoolKey with **no fee validation** (only TWAP-oracle/PoolManager match `:115-121,261-263` and WETH non-zero `:122-125`). No `isDynamicFee`/`0x800000` reference exists anywhere under `contracts/` (grep; only docs in the weighted-hook PRD).
- The repo's own quoting library already treats dynamic-fee pools as out-of-model: "with dynamic fees (FEE_DYNAMIC flag = 0x800000), quotes may differ from actual swap results because hooks can modify fees at execution time" (`lib/crane/.../v4/utils/UniswapV4Quoter.sol:17-27,99-102`). So today a dynamic-fee pool bound to a V4FS vault would be quoted (and closed-form-computed) against the wrong fee.
- PoolManager-side structural validation exists at pool *initialize*: `Hooks.isValidHookAddress` (`Hooks.sol:111-129`) — a hookless pool cannot be dynamic-fee, and return-delta flags require their action flags.

### 1.3 What "static" covers — and what it does not
| Component | Static? | Evidence | Consequence for calculations |
|---|---|---|---|
| **LP fee** (`PoolKey.fee`) | **Immutable for pool lifetime** | part of pool identity (`poolId = keccak(key)`); slot0.lpFee set once at initialize; `updateDynamicLPFee` gated (above) | Safe to read once from stored PoolKey; deterministic. ✓ |
| **Protocol fee** | **Directional, controller-mutable, not static** | packed uint24: bits 0-11 = zeroForOne, bits 12-23 = oneForZero; `MAX_PROTOCOL_FEE = 1000` pips (0.1%) (`ProtocolFeeLibrary.sol:9,18-24`); settable any time by `protocolFeeController` (`ProtocolFees.sol:34-40`; owner rotates controller `:28-31`) | **Affects user-visible amounts**, not just accrual split: `Pool.swap` charges `swapFee = lpFee` if pf==0 else `calculateSwapFee(pf, lpFee) = pf + lpFee − pf·lpFee/1e6` (`Pool.sol:291-313`, `ProtocolFeeLibrary.sol:35-47`). Must be read **live, per direction, per transaction** (constant within a tx: slot0 read at swap start). Cannot be frozen at deployment. Per-tx closed forms remain deterministic; cross-tx mutability does not break them. |
| **Hook fee override** (per-swap) | dynamic pools only | `beforeSwap` may return `OVERRIDE_FEE_FLAG` fee; parsed only `if (key.fee.isDynamicFee())` (`Hooks.sol:260-265`; applied `Pool.sol:305-313`) | Eliminated entirely by rejecting dynamic pools (R1). |
| **Hook amount deltas / other callbacks** | **possible on static-fee pools** | `BEFORE_SWAP_RETURNS_DELTA_FLAG` alters the specified amount (`Hooks.sol:268-281`); `AFTER_SWAP_RETURNS_DELTA_FLAG` takes the unspecified leg (Pons: two floored bps cuts, `PonsV2MemeHook.sol:495-504`); add/remove-liquidity return deltas (`Hooks.sol:230-246`) | Static LP fee ≠ static total cost. Quote-exact/closed-form paths must stay gated to modeled hooks: hookless, or validated Pons launch schema (`UniswapV4FullSpreadStandardExchangeVaultQuoteService._supportsProjectedHook`, `QuoteService.sol:44-48`, `_ponsHookFees:21-42`). Everything else = deployer responsibility (PRD §10/D14), measured-actual execution only. |

### 1.4 Legal context (current family law)
- PRD §10 (`docs/plans/UNISWAP_V4_STANDARD_EXCHANGE_PROPORTIONAL_ZAP_IN_PRD.md:293-308`): "Retain deterministic structural PoolKey validation"; "Hook compatibility assurance belongs to the deploying user where it cannot be determined on-chain. No discretionary hook whitelist"; "Do not present an inaccurate vanilla-pool quote as exact for unmodelled hook behavior." Dynamic-vs-static fee **is** determinable on-chain → vault-side enforcement is lawful and is not hook admission.
- CP accounting PRD Q3 (`.../v4/UNISWAP_V4_STANDARD_EXCHANGE_CONSTANT_PRODUCT_ACCOUNTING_PRD.md:299`): LP, protocol, hook and SE fees must map to explicit legs with ownership and rounding; "no new fee knob introduced without an explicit product decision." Deployment rejection adds no knob (immutable structural check).
- Vault instances are immutable/unowned (CLAUDE.md non-negotiable 5); the PoolKey is immutable in storage, so a deploy-time check can never be bypassed later.
- Scope consequence (fact): IndexedEx's own Orbital/Weighted hook pools are dynamic-fee (`contracts/hooks/uniswap/v4/weighted/UNISWAP_V4_WEIGHTED_SWAP_HOOK_PRD.md`: `fee = DYNAMIC_FEE_FLAG` factory doors, D68). FullSpread vaults could therefore never bind those pools. This does not break the documented SE-buffer topology (outer hook pools buffer *into* SE vaults; the vault's own bound pool is separate; the Pons V2 fixture uses static `PONS_V2_POOL_FEE = 0`, `TestBase_UniswapV4StandardExchange_PonsV2.sol:66`), but it is a product-visible restriction to record.

## 2. Recommended requirements (requirements-level; no code written)

- **R1 (core).** At deployment (`initAccount`, or equivalently `processArgs` before deploy): revert (new named error, e.g. `DynamicFeePoolIncompatible()`) when `poolKey.fee == LPFeeLibrary.DYNAMIC_FEE_FLAG`. Deterministic, fee-domain, per-instance, permanent via immutable storage.
- **R2 (bounds).** Also require `poolKey.fee.isValid()` (`≤ 1_000_000`). Cheap; makes the vault self-contained even for not-yet-initialized or foreign keys.
- **R3 (liveness/fee-equality, recommended).** At deployment, read `StateLibrary.getSlot0(poolManager, poolId)` and require the pool is initialized and `slot0.lpFee == poolKey.fee`. Proves the bound key is a live static pool and the configured fee is the effective one. (For static pools this equality then holds forever, §1.1.)
- **R4 (protocol fee handling).** All fee-sensitive calculations read `slot0.protocolFee` **live per direction** at route/quote time and compose it exactly as the executing port does (`calculateSwapFee`, `Pool.sol:291-313`) — never cached, never assumed zero, never frozen at deployment. Fee **accrual** accounting continues to use actual `feeGrowthInside` deltas (`_collectablePositionFees`, `Common.sol:637-648`), which already net the protocol fee; prediction models must apply the directional `pf` to the LP-fee share only.
- **R5 (domain separation).** Keep the fee gate (R1–R3) distinct from the hook-model gate (`_supportsProjectedHook`): the former is structural deployment validation; the latter governs quote-exactness/closed-form availability at runtime; neither is a discretionary whitelist (D14 preserved). Exact-in routes keep measured-actual execution on unmodelled-hook static pools; quote-exact/closed-form paths fail closed.
- **R6 (documentation).** Record the dynamic-pool exclusion (incl. IndexedEx Orbital/Weighted pools, §1.4) in the package README/compatibility notes so deployers learn it before pool selection, and state that blocked sleeve-only routes are fee-policy-independent (no pool interaction while in-session).

## 3. Caveats and limits of the static-fee assumption

1. **Total swapper fee ≠ LP fee when protocol fee > 0.** Any calculation that models only `key.fee` misprices whenever the controller has set a directional protocol fee (up to 0.1% per direction; combined `swapFee` capped < 100% else exact-out reverts `InvalidFeeForExactOut`, `Pool.sol:315-321`). R4 is mandatory, not optional.
2. **Static fee ≠ static total cost on hooked pools.** Amount-altering hooks exist on static-fee pools (§1.3 row 4). The assumption "static fee ⇒ CP closed form valid" is false without the modeled-hook gate.
3. **Local port is authoritative.** The local `ProtocolFeeLibrary.calculateSwapFee` computes `pf + lpFee − pf·lpFee/1e6` by integer division (`ProtocolFeeLibrary.sol:39-47`); the quoter and PoolManager share the same port, so model == execution by construction. Do not substitute upstream rounding comments for port arithmetic.
4. **Protocol fee can change between preview and execution** (different txs). Previews are per-state exact; integrators must still use min-out/max-in — preserved route requirements already cover this (PRD §3).
5. **No retroactive protection for existing instances:** V4FS instances already deployed without R1–R3 and bound to a dynamic pool would remain misquoted; this work does not authorize migration — the check protects new deployments only. (No evidence such an instance exists; not verified on-chain.)
6. Rejection is **pool-lifetime permanent**: a pool can never migrate static→dynamic (flag is in the key), so there is no false-positive risk of a pool "becoming" incompatible after vault deployment.
