**Intended behavior.** `docs/reviews/apex-2026-09-17-second-audit-readiness/REMEDIATION_PRD.md:255–268` requires an outside pool trade that does not refresh the vault book, followed by credit only for tokens actually held. R:215–228 requires inspection of preconditions and meaningful conservation assertions, not acceptance of a passing test name.

**Observed test.** `T/VaultMoney.t.sol:26–40` calls the real actor's pool swap and checks unchanged `IBasicVault.reserveOfToken` values and total supply. It then compares the vault's own preview to its own successful funded deposit. It does **not** measure the later payer debit/received custody delta, independently derive the post-harvest share entitlement, or assert a no-delivery credit rejection after that external trade. Preview and execution can agree while sharing the same credit/accounting error. The swap return value is discarded and there is no before/after pool-price or deployed-principal assertion proving the intended market change in the test itself.

**Path validation and counterevidence.** The fixture initializes a real pool and deploys the package through the IndexedEx manager and registry (`W/test/bases/TestBase_Vault.sol:29–50`). The actor opens its own manager session and calls `manager.swap`, not a vault route (`T/reference/VaultPoolActor.sol:48–65,81–100`). Bootstrap checks a funded target wing (`T/VaultMoney.t.sol:45–58`). These support the external-trade setup and the unchanged-book assertions; they are not missing altogether. Separately, `test_pretransferCannotConsumeBookedBackingOrReplay` has exact errors (`T/VaultMoney.t.sol:88–96`), but it does not execute the outside trade. `test_pendingDepositExcludedFromConvertedWingHarvest` checks balance/book equality (`:104–112`) but again uses preview/execute equality for issuance. Neither is a substitute for the missing independent post-trade credit assertion.

The production implementation actually uses local custody subtraction and exact pull-delta checks (`W/VaultMoney.sol:81–93`), which is counterevidence to treating this test deficiency as rediscovery of the historical stale-total defect. The opposing `IBasicVault` reserve assertion is also limited: the package registers only the target token (`W/VaultDFPkg.sol:108–109`) and money completion publishes only that target reserve (`W/VaultMoney.sol:49–53`). It does not inspect the full wings `local0/local1` book.

**Impact and corrective objective.** The supplied passing test cannot close the entire no-unearned-credit property. A separately authorized verification effort should establish an actual external market change and independently reconcile subsequent delivered input, credit, shares and custody, including the relevant negative control. This review supplies no executable procedure and makes no fund-loss claim.

**Evidence:** E:26–34 reports the four outside-trade tests passed; for this lane the evidence state is `INCOMPLETE_PROVENANCE`, supplied outcome `PASS` (narrative), not an independently reproduced pass. Attribution C05; cross-review **not performed**; coordinator disposition **pending**.

### C05-02 — Successful money completion does not perform the specified final custody synchronization

| Field | Assessment |
| --- | --- |
| Class / origin | `CODE_DEFECT` — source/specification mismatch / supplemental wings own-law review |
| Severity / confidence | **Medium** / High for the missing final synchronization; Medium for downstream economic consequences, which were not executed |
| Affected surface | Deposit, redemption, exact-output/refund completion and rebalance via `Money.end`; `S2-ADD-009` custody/donation seam |
| Inspection | `CONTRADICTS` P:C6 as written; this is not a claim that every tracked settlement delta is wrong |
| Readiness | `BLOCKS` closure of the final-custody-sync requirement absent correction or a scoped owner amendment |

**Intended behavior.** Wings' own P:155–165 distinguishes custody from deployed backing, allows source-agnostic **unbooked** input, limits current-call credit/refunds, and expressly requires final local custody synchronization after successful routes. P:15 authorizes valuation exclusion of unsellable inventory, not inaccurate physical custody. O1/O3 zero-supply residual policy does not waive C6 for live supply.

**Observed implementation.** `W/VaultMoney.sol:49–63` ends an operation by checking only `actual >= booked` for both tokens, copying the already-tracked target ledger to `MultiAssetBasicVaultRepo`, and clearing `busy`. It does not synchronize either wings local balance to the final physical balance. Actual ERC20 balances are assigned into both local fields only in `_bootstrapBacking` when supply is zero (`:106–110,129–130`). On live-supply deposits `_pull` authenticates delivery, but `_changeTarget` adds only the declared input (`:81–93,128–138`). Thus pre-existing excess can remain unbooked after successful completion. Local opposing surplus likewise has no completion-time capture in the inspected path. `Common.quoteRequest` subsequently values only the local ledger plus owned positions (`W/VaultCommon.sol:23–36`), while `QueryTarget.localReserves` exposes that ledger (`W/VaultQueryTarget.sol:19–22`).

**Important boundary/counterevidence.** Operation-local pool settlement updates both local ledgers using actual deltas and does not double-count the separately returned fees (`W/VaultExecutionDelegate.sol:28–38,50–51,56–73`). It rejects insufficient tracked funds and bad settlement. The mismatch concerns surplus at completion, not the correctness of every ledger delta. C4 expressly permits source-agnostic unbooked availability, so availability **before** an operation is not by itself a defect or an original-donor claim. The outstanding issue is that C6's final synchronization is not implemented after the credit/refund liability is resolved. `OutTarget` already refunds before `Money.end` (`W/VaultOutTarget.sol:15–20`), so the relevant completion boundary is identifiable.

**Impact and corrective objective.** The implementation does not establish the specified boundary between unbooked availability and the finalized custody book. This can leave physically held surplus outside current accounting after a successful route; no quantified dilution, theft, or loss was demonstrated here. Reconcile final custody with C6 after operation-local liabilities, without crediting extra exact-input amounts, refunding incumbent inventory, adding a sink/recovery ledger, or changing the O1/O3 first-depositor policy. If perpetual unbooked surplus is intended instead, a scoped product-law decision is needed; it is not inferred from FullSpread behavior.

**Evidence:** source inspection only; fresh execution `MISSING`, outcome `UNKNOWN`. Attribution C05; cross-review **not performed**; coordinator disposition **pending**.
