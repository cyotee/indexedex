### B-01 — Camelot share-to-token exact-output withdrawal omits the pull-path maximum check

- **Class / origin / severity / confidence:** `CODE_DEFECT`; original-program R7/D15 consumer; Medium; high confidence in the source deviation, runtime reachability not executed.
- **Affected snapshot and surface:** bound snapshot above; registry-deployed Camelot V2 SE, `exchangeOut` with SE shares as input and a pool token as output, `pretransferred=false`.
- **Intended behavior:** the user's declared maximum bounds shares burned on an exact-output route. R7.5 preserves max-input rejection, R7.6 applies the share-burn rules to Camelot, and D15 retains quoted actual-use accounting without waiving slippage limits.
- **Observed behavior:** `contracts/protocols/dexes/camelot/v2/CamelotV2StandardExchangeOutTarget.sol:699` enters the zap-out withdrawal branch; :748–764 computes `amountIn`, snapshots credit only for true-flag calls, and burns without comparing the computed input to `maxAmountIn`. The function has no shared maximum check at entry (:339–353). The pool is initialized on the common path at :443, so this is not an uninitialized-pool false positive. `CamelotV2StandardExchangeCommon.sol:214–219` immediately returns from `_refundExactOutCredit` for false-flag calls; it does not enforce the maximum later. `BasicVaultCommon.sol:151–156` burns directly from the owner. A funded holder's balance is therefore the limiting bound on that branch, not the declared maximum.
- **Production wiring:** `CamelotV2StandardExchangeOutFacet.sol:19,46–50` exposes the inherited entrypoint; `CamelotV2StandardExchangeDFPkg.sol:506–512` installs that facet. This is a production proxy route, not an isolated helper.
- **Impact:** slippage/input-authorization violation on a holder's own withdrawal; a successful downstream withdrawal can burn more shares than the caller authorized. This is not a claim of third-party share theft. No exploit procedure or numeric attack fixture is supplied.
- **Counterevidence:** the true-flag branch's bounded credit check rejects `used > credit`; the adjacent SE-to-LP withdrawal explicitly checks the maximum at :657–660. Existing Camelot `SecRemediation` tests inspect swap refunds; `In_SlippageProtection` tests cover exact-input minimums. Neither substitutes for this false-flag exact-output branch. The current test search found no branch-specific maximum-negative assertion for it.
- **Linked rows:** R7.5, R7.6, R8.5, R9.3; E6/N2/H rollback obligations. No Stage-1 repair or regression is attributed.
- **Readiness:** `BLOCKS` closure of exact-output limit preservation for this consumer.
- **Corrective objective:** enforce the maximum on the computed share charge before settlement and substantiate it with a funded production-proxy negative plus successful equal-bound control, preserving rollback.
- **Attribution / cross-review / coordinator:** B independent original; cross-review pending; coordinator disposition pending.

### B-02 — Rocket's second sleeve investment can combine a skipped old-reserve allocation with caller input

- **Class / origin / severity / confidence:** `CODE_DEFECT`; original-program; Low; high source confidence. Economic loss is not demonstrated.
- **Surface:** Rocket Pool rETH SE WETH-to-SE issuance in both exactness modes, same bound snapshot.
- **Authority:** original APEX plan D39 and R14.3/R14.19 require separate old-reserve and caller allocations; each deposit must individually meet the minimum, and an eligible old-reserve amount below that minimum stays booked. R14.20 explicitly requires preserving that skipped amount.
- **Observed:** `RocketPoolRETHStandardExchangeCommon.sol:500–515` computes `fromBooked`, calls `_stakeWethToRethSoft(fromBooked)`, then recomputes live `liquid - target` and passes the entire remainder to another soft stake. `_stakeWethToRethSoft` at :446–459 returns without investment for a below-minimum allocation. The second call receives no caller-credit bound and no information that the old allocation was skipped. Thus the remaining aggregate can become independently depositable even though the required first allocation was below minimum; the later call can invest both sources together. The function cannot distinguish them because it accepts no caller amount. Calls are production `InTarget.sol:71–80` and `OutTarget.sol:60–73`.
- **Impact:** violates the authorized reserve/caller isolation and minimum-allocation policy; changes when old holder cash is invested and may incur existing protocol deposit fees sooner. It does not create a new caller share entitlement by itself, and no insolvency or theft is alleged.
- **Counterevidence:** the common open-capacity examples and the locked 20% sleeve case behave as specified. `RocketPoolRETHStandardExchange_APEX_R14.t.sol:48–63` tests a skipped old amount while the combined remainder is also below minimum, then lowers the minimum; that fixture does not distinguish separate allocation from aggregate pooling. The :159 locked-arithmetic test and :200/:218 target-extreme controls are substantive positive evidence for their own cases.
- **Linked rows:** R14.2, R14.3, R14.4, R14.19, R14.20; K/N2. Original-program, not Stage-1 regression.
- **Readiness:** `BLOCKS` the stated separate-allocation acceptance claim; severity remains Low because the observed deviation concerns the chosen investment policy and accounting isolation, without established extraction.
- **Corrective objective:** preserve the two source budgets across a skipped first stake and show independently eligible/sub-minimum combinations on both production routes.
- **Attribution / cross-review / coordinator:** B; pending; pending.
