## 2. Corrections to my own original (explicit)

1. **Instance identity claim — wrong.** I cited the registry comment "no package-in-salt" and concluded family exclusivity was load-bearing against address collisions. Code wins: the package address **is** in the instance salt (§1 row 1). Same PoolKey through two packages yields **two different vaults**; within one package, a duplicate-key deploy reverts at CREATE2. Family exclusivity is a *product* invariant (no duplicate vaults over one pool across families), not an address-safety requirement.
2. **Occupied-salt redeploy — wrong.** The factory silently returns the existing package without re-running its constructor (§1 row 2). Therefore (a) same-name family packages are a **silent-misconfiguration hazard**, not a revert; (b) distinct concrete contract identifiers are **mandatory**; (c) post-deploy binding assertions (expected hook/immutables match the manifest) are required, per Astra's "assert bindings when reusing an occupied address."
3. **"Discriminated salt strings `<name>:<family>`" — withdrawn.** It violates the owner-confirmed D3 salt law (name-only; no caller namespaces/release labels, §1 row 3). Replaced by: distinct concrete package contract names, each earning its own compliant name-only salt.
4. **`requiredHook` placement.** With distinct concrete packages, the expected hook is a constructor immutable on each family package (per-family `PkgInit` on a shared new interface carrying `expectedHook`, or a constructor arg on a shared new abstract base) — not a widening of the deployed v1 package's interface, which stays frozen.

## 4. Final recommended architecture (minimal disruption, per user direction)

1. **Two new thin concrete packages in the FullSpread tree**, each with its own contract identifier (own name-only D3-compliant salt), e.g. `UniswapV4FullSpreadStandardExchangeVaultHooklessDFPkg` and `UniswapV4FullSpreadStandardExchangeVaultPonsV2DFPkg`, factored over a **new** shared abstract base authored in the new tree (the deployed v1 DFPkg is not subclassable and stays untouched — additive change).
2. **Reuse 15/15 facets + 2 execution delegates unchanged** (existing QuoteService already models both families; admission makes the unmodeled fallback unreachable). New salts/names only for the two package contracts; facet FactoryService calls remain idempotent and return canonical facet addresses.
3. **Admission checks in both `processArgs` and `initAccount`, before any token registration/approvals** (`DFPkg.sol:274-292` ordering): hookless → `poolKey.hooks == address(0)` + static-fee structural checks (`fee != 0x800000`, `fee ≤ 1_000_000`; 100%-fee boundary remains the separately open choice from the fee round). Pons → `poolKey.hooks == EXPECTED_PONS_HOOK` (constructor immutable), `EXPECTED_PONS_HOOK.poolManager() == POOL_MANAGER`, `poolKey.fee == 0`, launch decode valid (`_ponsHookFees` structural: flags, 13-word layout, `registered`, currency orientation, bps bounds — with `hookFeeBps ≤ 1000` matching the hook's real `MAX_HOOK_FEE_BPS`, Astra's correct tightening over the current looser `≤ 2000` at `QuoteService.sol:35-36`), codehash recorded and asserted against the deployment-manifest fingerprint.
4. **Registry/discovery:** both packages register via the manager/registry `deployPkg` path (`IVaultRegistryDeployment.sol:49`); `pkgsOfType` sets support identical interface sets (Astra/MiniMax verified); consumers must select by package address/name, not "first package of type". Sleeve type-default (20% usage-fee type via the LiquidReserve interface id, `DFPkg.sol:132-137`) intentionally shared across families.
5. **Deferred (not now):** query-facet splitting per family (first family needing a new quote model), any one-vault-per-pool registry rule, deprecation of the v1 package, dynamic-fee integrations (each would be its own future family with its own model).
6. **Unchanged law:** D17–D19 `InvalidRoute` combined route on both families; D20 25/50/10/1 bp; D21 progress policy; pretransfer guard; full booking; no old-tree edits/migration.
