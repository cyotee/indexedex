# Kimi K3 — Original: Hook-specific Uniswap V4 Standard Exchange Vault Packages

**Date/access date:** 2026-09-27 · **Researcher:** Kimi K3 (independent first pass this round; no peer artifacts read)
**Proposal under evaluation:** adopt hook-specific V4 SE vault packages — (1) a hookless package that checks `hooks == address(0)`; (2) a Pons Family package that checks the specific Pons hook; (3) future integrations: one package per compatible hook, reusing identical facet sets where compatible — thereby avoiding arbitrary-hook quote concerns.
**Verdict:** **Recommend adoption.** The pattern is architecturally native to the FullSpread design: facets/delegates are hook-agnostic and fully reusable; the DFPkg already binds PoolManager/TWAP/WETH immutably; hook identity can be pinned per-package at instance init with exact-equality, on-chain, deterministic checks. It converts hook compatibility from deployer *assurance* (old D14) into admission *by construction*, and eliminates the arbitrary-hook quote-exactness problem rather than managing it. Current PRD constraints respected: combined exact-output-plus-rebalance stays release-unsupported/`InvalidRoute` (D17–D19), protections 25/50/10/1 bp and the D21 progress policy untouched.

## 1. Architecture fit (evidence from NEW FullSpread code)

- **Facet sets are hook-agnostic.** Every facet reads the hook from the instance's stored PoolKey at runtime (`UniswapV4FullSpreadStandardExchangeVaultPoolKeyAwareRepo.sol:86-92`); no facet bytecode mentions any hook. The two execution delegates are constructor-wired per facet (`InTarget.sol:31-36`, `OutExecuteTarget.sol:28-32`) and are likewise hook-agnostic. ⇒ **All 15 facets + 2 delegates are reusable verbatim across every hook family** (same CREATE3 addresses; FactoryService deploys are idempotent by salt).
- **The DFPkg is the natural family discriminator.** `PkgInit` (on the interface, `IUniswapV4FullSpreadStandardExchangeVaultDFPkg.sol:22-45`) already immutably binds `poolManager`, `positionManager`, `twapOracle`, `weth`, and validates `twapOracle.poolManager() == poolManager` at construction and again in `processArgs` (`DFPkg.sol:115-121,261-263`). Adding one field — `IHooks requiredHook` — gives an immutable, per-package family identity checked once per instance in `initAccount` (`DFPkg.sol:271-298`), which today stores the PoolKey with **no hook/fee validation** (verified last round).
- **Quote model is already family-segmented.** `UniswapV4FullSpreadStandardExchangeVaultQuoteService.sol:44-48` (`_supportsProjectedHook`: hookless → vanilla; validated Pons launch → modeled cuts) and `:50-58` (`_adjustHookSwap`). With family packages, every deployed instance lands in a *modeled* branch by construction; the unmodeled fallback (`:55` returns vanilla amount) becomes unreachable for registered families and remains only as fail-closed defense.
- **Package deploy path supports multiple packages.** `vaultRegistry.deployPkg(initCode, initArgs, salt)` (`IVaultRegistryDeployment.sol:49`); current FactoryService deploys the single package with salt string `"UniswapV4FullSpreadStandardExchangeVaultDFPkg"` (`..._Component_FactoryService.sol:174-183`). Crane CREATE3 addresses derive **only from (deployer, salt)** and revert on re-use (`Bytecode.sol:278-307`) ⇒ family packages need **discriminated salt strings** (e.g. `"UniswapV4FullSpreadStandardExchangeVaultDFPkg:hookless"`, `"...:ponsV2"`); identical type name/bytecode is fine because initcode (creation code + constructor args incl. `requiredHook`) differs, keeping the registry's initcode-hash package mapping unique.
- **Instance-salt law makes family exclusivity load-bearing.** Registry doc: "vault diamond factory salt law (**no package-in-salt**)" (`IVaultRegistryDeployment.sol:60`) and `calcSalt(pkgArgs) = hash(PkgArgs{poolKey})` (`DFPkg.sol:253-255`) ⇒ the *same* PoolKey deployed through two packages targets the *same* instance address. With exact-equality family predicates a key can pass at most one family, so no collision is possible — but this invariant must be enforced (exact equality only, no overlapping predicates) and tested.
- **No TWAP/hook-slot conflict.** The vault's TWAP is the external multi-pool oracle (`UniswapV4TwapOracleAwareRepo`), which exists precisely because Pons/SE-hook pools cannot carry a TWAP hook (`oracles/.../UNISWAP_V4_MULTI_POOL_TWAP_ORACLE_PRD.md:21-22,72-80`). Works identically for hookless and Pons pools.

## 2. Hook identity, version, and PoolManager binding — Pons facts (source-verified)

From `lib/crane/contracts/protocols/launchpads/ponsFamily/v2/hooks/PonsV2MemeHook.sol`:
- **Pool creation is factory-doored.** `_beforeInitialize` reverts unless `sender == factory` (`:454-457`); `setFactory` is one-time (`AlreadySet`, `:211-216`). A pool bearing the Pons V2 hook can therefore only be factory-made, and `registerPool` rejects wrong-hook keys and mis-sided memecoins (`:382-384`).
- **Per-pool fee terms are frozen for life.** `LaunchInfo` snapshots `hookFeeBps`, `creatorTaxBps`, `protocolFeeShareBps`, `buybackBurnBps`, `maxInternalPriceImpactBps` at registration (`:48-67,389-403`), guarded by `AlreadyRegistered` (`:357`); "Terms frozen here govern the pool for life" (`:359-363`). Ceilings: hook fee ≤ 1000 bps, tax+fee ≤ 2000 bps (`:70-74,364-376`) — matching `QuoteService._ponsHookFees` bounds (`QuoteService.sol:35-36`).
- **Global owner setters cannot touch existing pools.** `setHookFeeBps`/`setProtocolFeeShareBps`/`setBuybackBurnBps`/`setMaxInternalPriceImpactBps` (`:239-261`) mutate only the *global* policy that **future** launches snapshot via `currentFeePolicy` (`:283-295`). Per-launch mutables are limited to `setCreatorFeeRecipient` and `setBuybackEnabled` (`:415-435`, onlyFactory) — these redirect fee *distribution*, not the swapper-visible charge. ⇒ The swap-fee model per graduated pool is **immutable**.
- **Hook is PoolManager-bound and non-upgradeable.** `BaseHook(poolManager_)` at construction (`:160-165`); no proxy. A package can cross-check `requiredHook.poolManager() == POOL_MANAGER` deterministically.
- **Hook flags are exactly** `beforeInitialize + afterSwap + afterSwapReturnDelta` (`getHookPermissions`, `:184-201`) — the exact mask `_ponsHookFees` requires (`QuoteService.sol:24-26`).
- **Version posture:** this is the v2 hook (`PonsV2MemeHook`, `launches(bytes32)` 13-field getter layout consumed by `QuoteService.sol:28-41` — field order verified against `LaunchInfo` `:48-67`: `info[0]=registered, info[1]=memecoinIsCurrency0, info[7]=creatorTaxBps, info[10]=hookFeeBps`). A future Pons v3 (new address and/or new schema) is a **new family package**, never the same one — the family check must be **exact address equality**, not "any Pons-looking hook".

## 3. Recommended design (requirements-level; no code written)

**D-fam-1 — Uniform family mechanism.** One DFPkg artifact gains `IHooks requiredHook` in `PkgInit` (interface struct; new deployments only — deployed v1 packages are bytecode-frozen and untouched) plus a public `requiredHook()` view for registry discovery. `initAccount` reverts (new named error, e.g. `HookFamilyMismatch(expected, actual)`) unless `poolKey.hooks == requiredHook` — exact equality, before any token registration/approvals commit state.
**D-fam-2 — Initial families.** (a) *Hookless:* `requiredHook = 0`; fold in the static-fee policy (reject `fee == DYNAMIC_FEE_FLAG`, validate `fee ≤ 1_000_000`; 100%-fee boundary still an open owner choice from the fee-policy round). (b) *Pons V2:* `requiredHook = <mined PonsV2MemeHook address>`; additional deterministic pins: `poolKey.fee == 0` (economic model assumes fee-0; the hook does not itself enforce fee at initialize — only factory sender — so pin it), `requiredHook.poolManager() == POOL_MANAGER`, and a one-time launch-decode sanity (`_ponsHookFees(poolKey).supported == true`) so schema drift fails at deployment, not first quote. Leave `tickSpacing` unpinned (full-range math is spacing-generic, `Common.sol:1141-1145`).
**D-fam-3 — Salts and registry.** Discriminated package salt strings (`"<name>:<family>"`) via the existing `deployPkg(initCode, initArgs, salt)` path; facets/delegates deployed once and reused (idempotent FactoryService). `PkgArgs{poolKey}` and `deployVault(PoolKey)` signatures unchanged for integrators. Preserve the mutual-exclusivity invariant (exact-equality predicates; documented as load-bearing because instance salts exclude package identity — §1).
**D-fam-4 — Future families.** One package per compatible hook: reuse all facets when the existing quote model covers the hook; when a new model is needed, version only the query-side facets (In/Out Query + MultiQuery) and reuse execution facets. Admission = deploying a new family package through the manager registry (owner/registry action) — never runtime admission, never a discretionary whitelist.
**D-fam-5 — Runtime defense-in-depth unchanged.** Keep `_supportsProjectedHook` gates and `_adjustHookSwap` verbatim: any decode failure reverts `InvalidQuoteState` (`Common.sol:103-109`) rather than misquoting. Measured-fill settlement (`balanceOf` deltas), D20 protections (25/50/10/1 bp), D21 progress policy, D17–D19 `InvalidRoute` for the combined exact-output route — all unchanged for both families.

## 4. Does splitting eliminate the arbitrary-hook quote concern? — Yes, structurally

- Today an instance *can* bind an arbitrary hook; §10 then requires honest-but-inexact quoting and deployer assurance. Under family packages, **no instance can exist against an unmodeled hook**: hookless instances are exactly vanilla-modeled (static fee + live directional protocol fee, already composed by `UniswapV4Quoter.sol:205-211`), Pons instances are exactly Pons-modeled (two floored cuts, `QuoteService.sol:50-58` == `PonsV2MemeHook.sol:495-504`). The "inaccurate vanilla-pool quote" surface disappears for registered families rather than being labeled.
- **Relationship to old D14** ("deployer assurance; no discretionary whitelist"): the proposal does not reintroduce discretion — it makes hook compatibility *determined on-chain at deployment*, which is D14's own carve-out ("where it cannot be determined on-chain") operating favorably. The human note that the proposal may supersede D14 is consistent with my reading: D14's residual scope becomes non-hook dimensions (token sanity under weird-token law, pool liquidity/price at binding, oracle wiring). Recommend rewording D14 at the next authorized PRD/documentation touch; until then this round's proposal is the owner's statement of direction.
- **Not a panacea (honest limits):** family packages pin *identity and fee model*, not behavior. A modeled hook can still revert operations (factory-door state, paused launches), and Pons sweep/operator mechanics (`:896-994`) move their own funds but do not touch vault settlement. Quote exactness still excludes cross-tx protocol-fee drift and Pons *distribution* changes (min-out/max-in + measured fills remain the backstop). Closed-form/combined routes stay `InvalidRoute` this release regardless (D17–D19).

## 5. Tests (production-path, registry-deployed)

1. Family admission matrix: hookless rejects Pons key / arbitrary-hook key / dynamic-flag key / `fee > 1e6` (and 100%-fee per pending owner choice); Pons package rejects hookless key, wrong hook address, `fee != 0`, hook PoolManager mismatch, non-decodeable launch (schema-drift fake), and accepts a real graduated Pons pool.
2. Family coexistence: both packages deployed (distinct addresses/initcode-hash registrations), **identical facet addresses wired into both** (reuse proof), distinct package salts; instance type ids identical; shared sleeve type-default resolution.
3. Exclusivity invariant: every test PoolKey passes exactly one family predicate; same key cannot instance through two packages (instance-salt law, §1).
4. Quote==execution per family: vanilla static fees (0 / ordinary / both protocol-fee directions, controller update between preview and execution); Pons cuts both directions; **LaunchInfo freeze proof** — owner `setHookFeeBps` after graduation does not change the pool's charged/quoted fee (`:251` vs `:389-403`).
5. Full D1–D21 acceptance regression on **both** families (incl. `InvalidRoute` battery, blocked sleeve ops, pretransfer guard, full booking), plus existing hook SE-matrix fixtures (`test/foundry/spec/hooks/uniswap/v4/standardExchange/`) against the Pons family.
6. FactoryService idempotency: second family deployment does not redeploy facets; package salt strings enumerated in the plan (CP-PRD §7 identity map: old package ↔ hookless family ↔ Pons family artifact/salt/registry mapping).

## 6. Minimal owner decisions

1. **Adopt the family pattern** (hookless + Pons V2 as the initial registered families); confirm hook compatibility for registered families is package-curator (owner) responsibility, superseding D14's deployer-assurance for that dimension only.
2. **Identity convention:** single DFPkg artifact + `requiredHook` in `PkgInit` + discriminated salt strings + public `requiredHook()` view (recommended) — versus distinct contract names per family (heavier, unnecessary since bytecode is identical except one immutable).
3. **Pons pins:** exact hook address, `fee == 0`, hook-PoolManager equality, launch-decode-at-init (all recommended); tickSpacing unpinned.
4. **Static-fee boundary for the hookless family:** the still-open 100%-fee choice (reject with distinct named product error — recommended — vs accept-and-fail-naturally).
5. **Future-hook admission process:** new family package via registry deployment only (no runtime path), each with its own quote-model verification evidence before registration.

## 7. Caveats and blockers

- **PkgInit interface change is additive-for-new-deployments only**; the deployed v1 package is frozen and keeps decoding the old struct — do not attempt to redeploy it at the same salt (would revert; old tree/instances untouched as required).
- **`requiredHook` must be chain-correct.** The Pons hook address is CREATE2/3-mined per deployment (`HookMiner.find`, `TestBase_UniswapV4StandardExchange_PonsV2.sol:148`); each chain's family package must bind that chain's hook and PoolManager — the package's immutable binding already enforces PoolManager consistency (`DFPkg.sol:118-120`).
- **Instance-salt exclusivity is a real invariant, not a formality** (§1): if two future families ever used non-exact predicates (e.g. flag-mask acceptance), the same PoolKey could collide at one instance address. Exact-equality-only is the mitigation; assert in tests.
- **Pons owner powers are non-trivial** (global policy for future launches, recipient/operator rotation, `OwnershipCannotBeRenounced` `:78`) but provably cannot alter an existing pool's swapper-visible fee terms (§2); no residual quote-model risk, only distribution routing.
- **Blockers:** none technical. The adoption decisions in §6 are the only gating items; everything else is engineering under existing law.
