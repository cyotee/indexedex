## Conclusion

There are three production/test mismatches, not one universal failure:

1. The shared bind path requires `pair ∈ se.vaultTokens()` even for a legitimate identity wrapper leg whose pair and SE are the wrapper share token. A rebasing wrapper lists its underlying asset, not itself, so the single, dual, orbital, weighted, Balancer, Curve, DETF, invariant, and Wings identity-leg deployments are rejected before their tested behavior begins. The same probe propagates an empty revert when the candidate has no `vaultTokens()` function.
2. Full-spread one-sided sizing derives liquidity from the swap output alone, then rejects the entire plan if rounded output is not exactly equal to the quote or if the corresponding input requirement exceeds the unswapped 51%. The planner converts that rejection into a whole-input refund. This is the shared sizing path behind the whole-input remainder and the direction-dependent no-liquidity outcomes; the 49% swap fraction is not the defect.
3. Several sibling rows still assert “rejected sibling” behavior unconditionally, although their own `processArgs` probe now accepts the sibling because its paired face is in `vaultTokens()`. Those supply and zero-call expectations are stale on the accepted path. The bare-protocol-vault control likewise expects deployment to succeed despite the new bind-time surface check.

## Source observations and inference

### A. Shared wrapper-bind and inventory failures

**Source observations.**

- `pairInVaultTokens` rejects zero addresses and code-free SEs, then directly calls `IBasicVault(se).vaultTokens()` and scans for `pair`; it has no `try/catch` and no `asset()` call (`contracts/hooks/uniswap/v4/libs/UniswapV4SeBufferHookLegLib.sol:172-181`). `addPairSe` applies that check specifically to `pair == se` and reverts `PairSeOverlap` when it is false (`contracts/hooks/uniswap/v4/libs/UniswapV4SeBufferHookLegLib.sol:196-202`).
- The existing `isWrapperShareInventory` classifier recognizes exactly the identity-inventory case: `pair == se`, with a successful `asset()` probe returning a different nonzero underlying. Its comment says it is not presently a bind gate (`contracts/hooks/uniswap/v4/libs/UniswapV4SeBufferHookLegLib.sol:181-190`).
- A production rebasing wrapper returns its configured asset from `asset()` (`contracts/protocols/staking/rebasingVault/RebasingAwareERC4626Target.sol:26-28`), while `vaultTokens()` returns a one-element array containing that asset, not the wrapper share address (`contracts/protocols/staking/rebasingVault/RebasingAwareVaultMetadataTarget.sol:29-32`).
- The failing fixtures deliberately configure identity legs. Representative examples are single CP `standardExchange = pairToken = wrapper` (`test/foundry/spec/protocols/staking/rebasingVault/RebasingAwareERC4626_Buffers.t.sol:302-306`), dual CP (`test/foundry/spec/protocols/staking/rebasingVault/RebasingAwareERC4626_Buffers_Dual.t.sol:48-53`), orbital (`test/foundry/spec/protocols/staking/rebasingVault/RebasingAwareERC4626_Buffers_Orbital.t.sol:219-223`), and the buffer invariant (`test/foundry/spec/protocols/staking/rebasingVault/RebasingAwareERC4626_BufferInvariant.t.sol:265-270`). Weighted and the two quad fixtures assign the wrapper as its own SE in their sorted arrays (`test/foundry/spec/protocols/staking/rebasingVault/RebasingAwareERC4626_Buffers_Weighted.t.sol:211-233`; `test/foundry/spec/protocols/staking/rebasingVault/RebasingAwareERC4626_Buffers_Balancer.t.sol:214-227`; `test/foundry/spec/protocols/staking/rebasingVault/RebasingAwareERC4626_Buffers_Curve.t.sol:211-223`). The DETF composition does the same for CP and weighted hooks (`test/foundry/spec/protocols/staking/rebasingVault/RebasingAwareERC4626_Buffers_Detf.t.sol:48-64,183-205`). The Wings dual fixture creates its second leg as `standardExchange1 = token1 = output`, where `output` is a rebasing wrapper (`test/foundry/spec/hooks/uniswap/v4/standardExchange/FullSpreadSameManagerAmmFixture.sol:105-122,198-202`).
- Every listed package reaches the same helper: single CP reverts `TokenNotInVaultTokens` on false (`contracts/hooks/uniswap/v4/standardExchange/constantProduct/single/UniswapV4SingleStandardExchangeBufferConstantProductHookDFPkg.sol:399-401`), dual CP does so for both legs (`contracts/hooks/uniswap/v4/standardExchange/dual/UniswapV4DualStandardExchangeBufferConstantProductHookDFPkg.sol:384-392`), and orbital, weighted, Balancer quad, and Curve quad map false to `InvalidSE` (`contracts/hooks/uniswap/v4/standardExchange/orbital/UniswapV4StandardExchangeOrbitalBufferHookDFPkg.sol:408-410`; `contracts/hooks/uniswap/v4/standardExchange/weighted/UniswapV4StandardExchangeWeightedBufferHookDFPkg.sol:450-451`; `contracts/hooks/uniswap/v4/standardExchange/stable/quad/balancer/UniswapV4StandardExchangeBalancerQuadStableBufferHookDFPkg.sol:412-413`; `contracts/hooks/uniswap/v4/standardExchange/stable/quad/curve/UniswapV4StandardExchangeCurveQuadStableBufferHookDFPkg.sol:422-423`).
- The ordinary-overlap negative tests expect `InvalidSE`, not an empty revert (`test/foundry/spec/protocols/staking/rebasingVault/RebasingAwareERC4626_Buffers_Orbital.t.sol:47-52`; `test/foundry/spec/protocols/staking/rebasingVault/RebasingAwareERC4626_Buffers_Weighted.t.sol:52-61`; `test/foundry/spec/protocols/staking/rebasingVault/RebasingAwareERC4626_Buffers_Balancer.t.sol:53-62`; `test/foundry/spec/protocols/staking/rebasingVault/RebasingAwareERC4626_Buffers_Curve.t.sol:53-62`).
- `SimpleYieldERC4626` exposes `asset()` (`contracts/test/stubs/SimpleYieldERC4626.sol:94-96`) but has no `vaultTokens()` definition anywhere in its contract (`contracts/test/stubs/SimpleYieldERC4626.sol:17-178`). The leg-library wrapper-overlap test binds that stub to itself (`test/foundry/spec/hooks/uniswap/v4/interfaces/UniswapV4SeBufferHookLegLib.t.sol:111-121`). The bare-vault control instead expects a bare `SimpleYieldERC4626` to deploy and then revert on its first buffering call (`test/foundry/spec/hooks/uniswap/v4/standardExchange/constantProduct/single/UniswapV4SingleStandardExchangeBufferConstantProductHook_SeMatrix_SimpleYieldERC4626Control.t.sol:31-53`).

**Inference.**

- For every rebasing identity leg, `pair` is the wrapper address while the sole element of `vaultTokens()` is the different underlying address. The membership scan therefore returns false, producing exactly the reported package-specific `TokenNotInVaultTokens()` or `InvalidSE()` before setup or the test body can proceed. This one helper-level mismatch covers the listed rebasing, DETF, invariant, and Wings failures.
- For a code-bearing candidate without `vaultTokens()`, the external call itself reverts before the helper can return false. That explains the leg-library wrapper-overlap revert and the ordinary-overlap cases that expected `InvalidSE` but received empty revert data.
- The bare-vault control is a different expectation problem: its candidate does not satisfy the new bind surface and is not an identity wrapper. Weakening binds to accept any matching `asset()` would restore this old control only by creating the prohibited `asset()` bind requirement.

### B. Full-spread one-sided sizing

**Source observations.**

- `_size` keeps the locked one-exact-input-swap structure and computes `swapIn_ = FullMath.mulDiv(amount_, 49, 100)` (`contracts/vaults/standard/exchange/protocols/uniswap/v4/fullSpread/UniswapV4FullSpreadStandardExchangeVaultPlanner.sol:180-203`). After quoting, it delegates to `Math.sizeOneSided`; zero liquidity or zero swap input causes it to clear the plan and set `remainder = amount_` (`contracts/vaults/standard/exchange/protocols/uniswap/v4/fullSpread/UniswapV4FullSpreadStandardExchangeVaultPlanner.sol:205-220`).
- `sizeOneSided` computes `remaining_ = amount_ - swapIn_`, obtains liquidity solely from `swapOut_`, recomputes both payments at the post-swap price, and rejects the whole candidate when `needOut_ != swapOut_` **or** `needIn_ > remaining_` (`contracts/vaults/standard/exchange/protocols/uniswap/v4/fullSpread/UniswapV4FullSpreadStandardExchangeVaultMath.sol:47-71`). Only otherwise does it return a nonzero liquidity and a remainder limited to the unswapped-input budget (`contracts/vaults/standard/exchange/protocols/uniswap/v4/fullSpread/UniswapV4FullSpreadStandardExchangeVaultMath.sol:73-77`).
- `_liquidityFittingOut` uses only `amountOut_`; its raw result is zero-rejected when zero or above `uint128` (`contracts/vaults/standard/exchange/protocols/uniswap/v4/fullSpread/UniswapV4FullSpreadStandardExchangeVaultMath.sol:81-99`). Payment calculation then uses the round-up `amountsToPay` path (`contracts/vaults/standard/exchange/protocols/uniswap/v4/fullSpread/UniswapV4FullSpreadStandardExchangeVaultMath.sol:103-121`). The same file already has a `proportional` loop that reduces liquidity until both rounded payments fit their respective budgets (`contracts/vaults/standard/exchange/protocols/uniswap/v4/fullSpread/UniswapV4FullSpreadStandardExchangeVaultMath.sol:101-114`).
- The single full-spread regression explicitly requires the final refund to be a small residue rather than the input (`test/foundry/spec/hooks/uniswap/v4/standardExchange/single/UniswapV4SingleSEBufferHook_SeMatrix_UniswapV4FullSpreadStandardExchangeVault.t.sol:76-90`). The shared refund helper likewise requires `refund_ > 0 && refund_ < amount_` (`test/foundry/spec/hooks/uniswap/v4/standardExchange/dual/UniswapV4DualSEBCPHook_SeMatrix_UniswapV4FullSpreadStandardExchangeVault.t.sol:148-174`).

**Inference.**

- Output-only liquidity can require more unswapped input than remains after the fixed swap, and floor-derived liquidity followed by ceiling-rounded payment can produce `needOut_ < swapOut_`. Either condition currently takes the whole-refund path. Capping the candidate against both budgets, rather than rejecting it, is the direct correction for the partial-consumption failure and the shared direction-sensitive sizing path in the dual and orbital rows.
- The supplied `assertLe` integers alone do not identify which of the two guards fired, and no test execution was performed. The source-proven defect is the output-only, all-or-nothing sizing logic; the exact guard-to-number mapping remains unverified.

### C. Accepted siblings with rejected-sibling assertions

**Source observations.**

- A full-spread vault initializes its basic-vault token list from the two pool faces (`contracts/vaults/standard/exchange/protocols/uniswap/v4/fullSpread/UniswapV4FullSpreadStandardExchangeVaultDFPkg.sol:187-192`). Thus a sibling bind whose pair is `pairRecord.p0()` satisfies the membership rule without any `asset()` requirement.
- Balancer sets `identityAccepted = true` when its real `processArgs` call succeeds, and strips the sibling SE only in the catch branch (`test/foundry/spec/hooks/uniswap/v4/standardExchange/stable/quad/balancer/UniswapV4StandardExchangeBalancerQuadStableBufferHook_SeMatrix_UniswapV4FullSpreadStandardExchangeVault.t.sol:128-145`). Nevertheless, `_seedBalancer` asserts unchanged sibling supply for every five-leg row, and `_balancerDirections` installs zero-call expectations and repeats that supply assertion without testing `identityAccepted` (`test/foundry/spec/hooks/uniswap/v4/standardExchange/stable/quad/balancer/UniswapV4StandardExchangeBalancerQuadStableBufferHook_SeMatrix_UniswapV4FullSpreadStandardExchangeVault.t.sol:164-187,201`).
- Curve and weighted N3 have the same accepted/catch setup followed by unconditional unchanged-supply assertions (`test/foundry/spec/hooks/uniswap/v4/standardExchange/stable/quad/curve/UniswapV4StandardExchangeCurveQuadStableBufferHook_SeMatrix_UniswapV4FullSpreadStandardExchangeVault.t.sol:96-110,127-134,139-162`; `test/foundry/spec/hooks/uniswap/v4/standardExchange/weighted/UniswapV4StandardExchangeWeightedBufferHook_SeMatrix_UniswapV4FullSpreadStandardExchangeVault_N3.t.sol:93-108,123-130,137-158`). Orbital also records acceptance but unconditionally asserts that its “rejected identity seed” did not mint the sibling (`test/foundry/spec/hooks/uniswap/v4/standardExchange/orbital/UniswapV4StandardExchangeOrbitalBufferHook_SeMatrix_UniswapV4FullSpreadStandardExchangeVault.t.sol:81-92,113-117`).

**Inference.**

- Once `processArgs` accepts the sibling, the catch branch does not remove that SE binding. An unchanged-supply/zero-conversion assertion then contradicts the accepted configuration. The reported small supply increases are consistent with exercising the accepted sibling leg, not with a need to alter the 49% fraction. Fixing a sizing bug so that these rows accidentally mint zero would preserve a stale expectation rather than correct the tests.

## Smallest fix direction

1. **Centralize the bind correction in `UniswapV4SeBufferHookLegLib`.** Make the `vaultTokens()` probe non-reverting and return false on a missing or reverting probe, so ordinary invalid candidates reach the package’s named `TokenNotInVaultTokens`, `InvalidSE`, or `PairSeOverlap` errors. Accept a bind when either reserve membership holds **or** the existing `isWrapperShareInventory(pair, se)` identity-inventory classification holds. Keep the wrapper alternative limited to `pair == se`; non-overlap binds remain `vaultTokens()`-only. Do not require `asset()` on ordinary SEs. Because all six packages and `addPairSe` already call this helper, their validation loops need no competing reimplementations.
2. **Cap one-sided liquidity by both post-swap budgets.** Keep `_size`’s `49 / 100` calculation and single quote unchanged. In `sizeOneSided`, retain the existing zero/`uint128` guards, but reduce the output-derived liquidity when its round-up input payment exceeds `remaining_` instead of refunding everything; the existing `proportional` reduction loop is the in-file pattern. Treat output payment as bounded by the quote (`needOut_ <= swapOut_`), not necessarily bit-equal to it, and explicitly account for any output-token rounding residue as residual vault inventory rather than disguising it as consumed output or extra input refund. Preserve whole-input refund only for a genuinely unusable zero-liquidity/zero-swap plan.
3. **Update the two stale test expectations, not production bind policy.** Change the bare-`SimpleYieldERC4626` control to expect bind-time rejection; do not make its `asset()` sufficient for deployment. In Balancer, Curve, weighted, and orbital sibling rows, apply unchanged-supply and `expectCall(..., 0)` assertions only on `!identityAccepted`; on the accepted path, assert the intended real conversion behavior. Keep a separately constructed invalid bind for rejected-sibling coverage.
