## 2. A1 — Force-claim reconciliation: the mechanism is derivable; withdraw the blocker

**Allegation (exact citations).** Plan v0.9 §6.6.4, final paragraph: "current raw surplus plus a zero upstream accrued balance does not alone identify which historical receipt was interest, an incentive or an unrelated donation… The operation-state/retained-series accounting must specify source-backed reconciliation without requiring public payer provenance, fabricating lost receivables or appropriating declared credit." Tracker NN-07: "Finish the on-chain mechanism reconciling historical unnotified receipts… Event monitoring/raw surplus alone is not that mechanism."

**Concrete reachable transitions.** (T1) Third party calls `YT.redeemDueInterestAndRewards(hook,…)` (permissionless, pays hook; plan §6.6.1) → SY arrives unbooked; native `userInterest[hook].accrued` is zeroed upstream. (T2) Before any booking, a supported pretransfer caller declares and consumes credit from `max(raw−booked,0)` (L2; PRD §6.3 v0.32). (T3) Nobody consumes it; the route ends with full expected-set sync (PRD §6.3; plan §7.1 step 8).

**Why existing rules already determine each transition.**
- C is **native-state-derived**, not receipt-derived: plan §6.6.2 computes C per YT from current `userInterest` reads plus the current index/fee. After a force-claim, native accrued is zero, so C recomputes downward by itself — the settled receivable *cannot* remain counted beside its cash, because C is never carried from a stale local expectation (§6.6.4: "Refresh native C immediately"; NN-11 once-only).
- H is **booked-balance-derived with exclusions**, not provenance-derived: §6.5.5 step 2 defines H as recognized eligible held SY excluding payables, exclusive principal, transient Keep-YT and allocated principal-exit SY. Excluded roles are booked only by protocol operations (§6.1 table). A surplus that no protocol operation booked into an excluded role enters the general SY book at full-set sync — no receipt classification is required, and "do not auto-classify every surplus or donation as interest" is satisfied because eligibility is a *role-absence* test, not an *interest-label* test. Interest-vs-donation distinction survives only as a reporting metric, which PRD §1 explicitly declares non-entitlement.
- T2 is settled by L2 itself: consumed units are the caller's contribution (plan §6.1), and since C is native-derived the upstream-cleared receivable cannot be double-counted against them.
- Ordering is already specified twice: capture declared credit **before** sync/recognition (§6.1; §6.6.4: "Capture valid declared public pretransfer credit from max(raw-booked,0) before sync/recognition erases it").
- Token-identity separation handles interest-vs-incentive without provenance: SY vs PENDLE are different addresses; the only same-address case (PENDLE == reserve SY) is already quarantined as a conditional binding check in §6.6.1 ("Prove that address differs from reserve SY before declaring no collision"), i.e. A6/fork work.

**What is actually missing (narrow).** The reconciliation rule above exists only distributed across §6.1/§6.5.5/§6.6.2/§6.6.4/§7.1. It has not been written once, deterministically, with its exact read set (native `userInterest`/`userReward` per retained series, booked raw, role bookings), write set, and the T1–T3 worked cases. **Minimal next deliverable:** one replacement paragraph for §6.6.4's residual note stating the deterministic rule ("C := Σ native-derived net claims; H := booked raw − excluded roles; a settled receivable cannot coexist with its cash because C is recomputed from native state; declared credit captured before recognition; consumed credit never rebooked") plus three vectors (T1, T2, T3). Plan-author work; no owner input; no event monitoring primitive required — the plan's own sentence "event monitoring/raw surplus alone is not that mechanism" is answered by the fact that **no receipt classification is needed at all**.

**Classification:** RESOLVED as a design question; IMPLEMENTATION/TEST (documentation + W2/A05/A27 vectors) as work. **Withdrawn as a blocker.**

## 3. A2 — Provider/caller rounding: determined by existing architecture, not a decision

**Allegation.** Plan §6.5.6: "Pin the provider/caller scaling and rounding chain before plan freeze: multiplying a raw SY book by this per-share rate can differ from first flooring the whole book to native sNET and then scaling."

**Analysis.** The provider is a *reusable per-SY rate provider* (PRD §4.5) consumed through the **existing** rate-provider/host mechanics: PRD §4.5's evidence row names the existing `StandardExchangeRateProviderFacet.sol:61–124` sampling reference, and the Weighted host already has its rate-scaling path with its own floors (the same architecture §4.3/§6.4 reuse). Given that the host consumes `rate × balance` through its existing scaling, the residual choice "rate-then-scale vs whole-book floor" is not free: the selected reuse of existing host mechanics picks rate-then-scale, and the provider sample is already pinned exactly (`q=1e18 → a=Ic → rate=Ic×1e9`, §6.5.6). What remains is mechanical: (i) write the exact chain (sample → rate → host scaling → sNET coordinate) with each floor location; (ii) bound the divergence from the whole-book floor `floor(book×Ic/1e18)` (at most one rounding step per scaling stage — an arithmetic bound, not an economic choice); (iii) one worked numeric example; (iv) a differential vector against the source formula. None of this changes any price by more than documented integer dust, and finite-size funding never uses the rate (§6.5.6: "Full-size executable funding always uses §6.5.3 independently").

**Minimal deliverable:** §6.5.6 rounding-chain paragraph + divergence bound + one example + two vectors. **Classification: IMPLEMENTATION/TEST.** Not an owner question; not a spec gap.

## 5. A4 — Exact-output residual at I>1e18: the selected rule already answers it

**Allegation.** Plan §6.5.3: "this round does not select gifting/warehousing excess or blanket removal of unrepresentable ERC4626 withdrawals… the latter is the narrow remaining L3 composition item." §6.5.7 row: "prove reachable domain or source-map delivery under existing rights."

**Why existing rules answer it.** (i) For `0 < I ≤ 1e18` the minimum-sufficient inverse reaches every target **exactly** (§6.5.3, proved). (ii) For `I > 1e18`, some native-unit targets are unrepresentable (e.g. `I=2×1e18, y=1` → `qMin=1` yields nominal 2). For those, **R22 already selects the behavior**: "Exact-output withdrawal delivers the requested net amount or reverts" (PRD R22; restated in plan §7.4: "Deliver all requested sNET or revert"). A revert on an unrepresentable dust target is therefore not a dropped route and not a missing residual policy — it is the selected transition. (iii) The two safeguards are also already selected: never warehouse overshoot as unbooked surplus (it would become L2 public credit; §6.5.3/§6.6.4), and never silently boost user output (plan §7.4 ERC-4626 row). No residual beneficiary needs to exist because no residual is ever delivered.

**Concrete reachability bound (inference, illustration for the horizon proof).** The index grows only through rebases; at the local reference's maximum 0.45% per epoch (`Constants.sol:19`, R_MAX_WAD), 1e9-fold growth from `I=1e9` to `I=1e18` needs on the order of `ln(1e9)/ln(1.0045) ≈ 4,600` epochs ≈ 4+ years of continuous maximum rebase — and the targets that become unrepresentable first are sub-dust (1 native unit = 1e-9 NET). The genuine supported-domain proof belongs to NN-18's operating-horizon analysis, which is already scoped.

**Minimal deliverable:** NN-18 index-growth/horizon bound (arithmetic), plus two vectors: `I=2×1e18, y=1` reverts exact-out without warehousing, and an in-horizon vector proving `I < 1e18` exactness. **Classification: RESOLVED as a rule; IMPLEMENTATION/TEST remainder.** **Withdraw the "narrow remaining L3 composition item" framing** — no rights-compatible residual route needs designing because R22's revert is the rights-compatible route.

## 8. A7 — L4 terminal rights: the one surviving ACTUAL SPEC GAP (narrow)

**Citations.** Plan §2.2 L4 row: "The PRD still retains late-principal timing and terminal residual/late-gift disposition; burning, permanently retaining the NFT or abandoning recognized rights are not interchangeable implementations." Plan §5.4 exposes `retire(tokenId)`; §7.3 "Irreversible retirement" leaves its transition unselected. Tracker H01: "Only late-proceeds timing and direct-donation classification remain"; H03: "Specify mature-and-empty retirement/late gifts separately."

**Concrete reachable transition 1 — post-completion excess lock class.** Intended note completes (`claimed == payout`), final contribution at processed epoch E sets unlock E+1 (NN-04, resolved). Native notes can still pay **excess**, and third parties can append notes to arbitrary recipients (`BondDepository.sol:104–165,183–188`, tracker §5 evidence), so the holder can receive further native proceeds after completion. H01 selects that excess "contributes/mints/stakes as same-NFT principal" — but the lock rules enumerate only purchase epoch, intermediate installments (no reset), final intended contribution (E+1), and new bonds (independent locks). A post-completion excess contribution is none of those. Two non-interchangeable derivations exist: (i) generalize E+1 — any successful contribution at processed epoch E′ unlocks at E′+1; (ii) treat post-completion excess as immediately withdrawable principal (no new lock). They differ in **availability timing of user entitlement**, and no selected sentence picks one.

**Concrete reachable transition 2 — `retire()` and late gifts.** After a position is drained (intended note complete, principal/rewards zero; §7.3 "Drained candidate" is specified), may `retire(tokenId)` execute, what does it do (burn vs dormant flag vs nothing), and what is the disposition of native receipts arriving afterward (collectible by current NFT owner via the retained holder, forfeited, or forwarded)? The plan records that these outcomes are **not interchangeable** and that "no current-balance check proves that arbitrary future gifts cannot arrive" (§7.3). A "permanent retention" derivation is internally consistent and forfeits nothing, but the plan explicitly declines to adopt it unilaterally, and the recorded "original mature-and-empty retirement intent" implies a retirement capability exists.

**Why no existing rule answers these.** Every settled timing rule (NN-04/H02) is keyed to the intended note's lifecycle and new-bond issuance; the post-completion, pre/post-retirement window has no assigned lock class or disposition rule, and the candidate dispositions differ in user entitlement/asset forfeiture — exactly the category the owner-question filter reserves for escalation ("a concrete required behavior, entitlement… cannot be derived without changing the product").

**Minimal next deliverable (not an owner questionnaire).** One page: the two transitions above, with alternatives and consequences — for T1: (i) E′+1 generalization vs (ii) immediate-withdrawable; for T2: (a) permanent retention with continued collection (conservative, nothing forfeited), (b) burn with late gifts forfeited, (c) burn with late gifts forwarded to the last owner — plus the recommendation that (T1-i) and (T2-a) jointly close the lifecycle without any forfeiture, subject to owner confirmation because the plan has recorded the alternatives as non-interchangeable. **One focused owner checkpoint.** Everything else under L4/NN-02/NN-15 (E+1, intermediate no-reset, independent new locks, zero-principal ≠ retirement, partial reinvestment, purchase-epoch distinction) is RESOLVED.

**Classification: ACTUAL SPEC GAP — narrow, two transitions, one checkpoint.** This is the audit's only survivor.
