## Conclusions

The owner's intuition is broadly right, with one named exception and one condition.

The accepted redefinition did fill the gap the paired group was created for. The review file justifies the group as "the two-token operations the standard one-token interface cannot express", and the accepted set now has a many-in, one-out bundle route and a one-in, many-out bundle route. A two-currency vault's paired deposit and paired exit are exactly the shapes those two routes describe, and the accepted refund rule already carries the "the vault may take less than you declared" behaviour that `depositPair` was invented for. Two functions in the group, `donate` and `compound`, are not routes at all: one books tokens without minting, the other is permissionless maintenance. No accepted standard function does either job, so neither can be mapped and both must stay.

The exception is raw-ETH settlement, and it is an exception about delivery form, not about the operation. The accepted functions are nonpayable and refuse `address(0)`; the paired functions on a native pool are payable on entry and pay raw ETH on exit. The full-spread family installs no SY surface, so once the paired group goes there is no raw-ETH entry or exit path left in it at all. That is a product decision for this family, not a gap in the accepted standard, and the accepted report says so itself: raw ETH stays on product functions outside the redefinition.

The condition is that the mapping is only correct if the vault implements the two accepted routes with the paired economics. The accepted report defines the interfaces and the refund rule, not the vault's internals. If `exchangeBundleInForSingleOut` is not implemented with the paired acceptance rule and the paired genesis branch, and `exchangeBundleOut` is not implemented as a proportional paired removal, then mapping the paired functions away would delete a capability rather than relocate it.

### The four resolutions the brief asked not to be left silent

**R1. `depositPair` takes maxima and may take less; bundle-in takes declared amounts and refunds the unkept part. Is that enough to keep `depositPair`?** Recommendation: no, it is not enough to keep it. The accepted refund rule already defines the outcome the paired rule produces: declared amount equals amount consumed plus amount refunded, so the caller ends up holding exactly the same amount of each input either way. The floor, the recipient and the deadline bind identically on both routes, with `minShares` becoming `minAmountOut` on the same minted number. The difference that survives is flow, not capability: bundle-in's pull path takes the declared maximum and returns the unkept part, so the caller must hold and approve the maximum, where the paired form pulled only the accepted amounts and left the rest untouched. That is a real cost and it belongs in the interface and the UI, but it is a cost the accepted standard imposes on every exact-in caller, and the owner already chose that flow deliberately. Recommendation: map it, and record the approval-and-balance sizing in the family requirements so integrators are not surprised.

**R2. `redeemPair` pays raw ETH on a native pool and the accepted bundle functions do not. Is that a reason to keep a paired redeem, or a reason to extend the standard?** Recommendation: it is not a reason to extend the standard, and not by itself a reason to keep the paired group as it stands today. The accepted report deliberately keeps raw ETH out of these functions and points it at "product functions outside this redefinition", so extending the standard would reopen an owner-locked definition and move a delivery-form decision into a common interface where every other vault would inherit it. There are two coherent positions for this family, and the choice is the owner's. Position one, which I recommend: the family operates a native pool in wrapped-ERC-20 form at the standard boundary, consistently with the locked role of `wrappedNative()` as "the wrapper used when a standard nonpayable call has to represent ETH"; a caller who wants ETH wraps before depositing and unwraps after exiting, and the paired group is fully replaced. Position two: the family must deliver raw ETH on exit, in which case exactly one narrow product function is kept that pays the native leg raw while the ERC-20-face route stays on the standard bundle-out, with identical economics and one shared engine, and it is added as an additive product function rather than as a standard extension. What I do not recommend is keeping the current paired group unchanged, because that keeps a second general-purpose ERC-20-face entry and exit path alongside the standard routes, which is the disagreement risk described in R3.

**R3. Does dropping the paired functions remove a second entry path that could disagree with `exchangeBundleInForSingleOut`?** Recommendation: yes, dropping removes it, and keeping both creates a real risk rather than a theoretical one. Four concrete disagreement surfaces exist between a kept `depositPair` and the accepted bundle-in route for the same economic intent: the acceptance rule itself, because the paired rule is `used_i = min(a_i, ceil(qQuote*R_i/S))` with a geometric-mean genesis branch and the bundle-in route must implement the same rule or a different one; the pull flow, because the paired form pulls only accepted amounts while bundle-in pulls the declared amount and refunds, so the same intent produces different allowance requirements, different refund transfers and different failure modes if a refund fails; the preview surfaces, because `previewDepositPair` returns used amounts and `previewExchangeBundleInForSingleOut` returns refunds, so one rule has two output shapes that each have to be execution-equivalent to execution and can only be cross-checked by tests; and the floor, because `minShares` and `minAmountOut` bind the same minted number and can drift apart silently. The same argument applies on the exit side to `redeemPair` against `exchangeBundleOut`. Recommendation: one route per direction, the standard routes, with the paired economics implemented inside them.

**R4. If the paired mutators are dropped, do `previewDepositPair` and `previewRedeemPair` remain necessary?** Recommendation: no. With the mutators mapped, the standard previews cover the same operations: `previewExchangeBundleInForSingleOut` for the paired deposit and `previewExchangeBundleOut` for the paired exit, with the information preserved under different names, used amounts as `amountsIn[i] - amountsRefunded[i]` and the paired payouts as `amountsOut[0]` and `amountsOut[1]`. Two conditions attach. First, the mapped routes must be execution-equivalent under the same quote discipline, including the maintenance-mode choice, the fee checkpoints, the compounding swap, the tick-crossing budgets and the integer settlement, because a preview that does not match its execution is worse than no preview. Second, the positional bundle-in preview only works if the family locks `vaultTokens()` membership and order, which the accepted report says is a conformance requirement and not an existing Basic Vault guarantee.

### Requirements the recommendations imply for the family PRD

These follow from the mapping and are not new owner decisions; they are what has to be written down for the mapping to be true.

- The vault implements `exchangeBundleInForSingleOut` with `tokenOut` = the share token using the paired acceptance rule, including the paired genesis branch. The first deposit of a fresh vault is that route, and single-token deposit routes reject on an empty supply, as the stage-one PRD already requires for the one-token zap.
- The vault implements `exchangeBundleOut` with `tokenIn` = the share token as a proportional paired removal when both currencies are named, selling nothing, so the "no sale, therefore no counterparty liquidity needed" exit survives. A single named output remains the sell-and-pay route, and it reverts when the unwanted leg cannot be sold.
- The rejection of a positive-share burn with a zero total payout, and the proportional allocation of removed principal and idle balances, apply to the mapped share-input route exactly as they apply to the paired route today.
- `vaultTokens()` must be locked for this family: order equal to the PoolKey currency order, and the wrapped ERC-20 face at the native leg's index, because the accepted bundle-in is positional and refuses `address(0)`. This is the one new conformance obligation the standard brings to this family.
- The family's paired events, `PairDeposited` and `PairRedeemed` or renamed equivalents, stay, and are emitted by the mapped routes. Dropping the function names does not drop the event surface.
- The refund flow means a caller of the bundle-in route must hold and approve the declared maximum of each input. The interface documentation and any integrator-facing material have to say so.
- `donate` and `compound` stay as they are, including `donate`'s payable native form if the family keeps it, since neither is a route and neither can be made to be one.
