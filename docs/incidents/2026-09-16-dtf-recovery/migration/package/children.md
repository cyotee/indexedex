## 2. Minimal implementation and wiring contract (proposed)

### 2.1 Funded bond: narrow shared hooks, separate Migration policy

Retain ordinary `BondPosition` layout and `_fundPrincipal`, `_retireIfPaid`, `_requireFunded` and authority checks. Extract the body of `createFundedPosition` into one internal creation helper; ordinary external entry keeps its existing modifiers and behavior. Add one internal virtual claim-calculation policy used by **both** preview and `_claim`, plus a claim-permission policy that can reject a reward-bearing request before accounting/payout. Existing concrete external functions are not virtual; merely deriving another target does not replace their behavior (B1/B2).

New Migration interface minimum:

```solidity
function createMigrationPosition(uint256 principal, address recipient)
    external returns (uint256 tokenId);
function isMigrationPosition(uint256 tokenId) external view returns (bool);
```

Only the immutable parent can create. No supplied duration, historical timestamp, source adapter, arbitrary execution target or allocation privilege. Store a Migration-only `mapping(uint256 => bool)` in a separate namespace; do not reinterpret reserved IDs or mark ordinary Stage2 purchases. Internal creation funds exact principal, mints a fresh ID, records `now` and `90 days`, and atomically marks the ID. The parent supplies the verified surrendering holder or independent allocation recipient; child caller authority is the parent, never the administrative owner. Configuration cannot call either creation path.

Use the following Migration calculation for marked IDs, ordinary math otherwise:

```text
remaining = principal - claimedPrincipal
vested = now >= startTimestamp + 90 days ? principal : 0
principalDue = vested - claimedPrincipal
require floor(stakingGons / k) >= remaining
rewardsDue = floor(stakingGons / k) - remaining
```

`previewClaim` can retain funded accrued rewards in `rewardsDue`; expose activation alongside it and label these as locked accrual, not executable payout, while closed. Gate execution, not accrual. `claimRewards` and `claimBond` are reward-requesting routes and reject in Stage1; `claimPrincipal` remains usable at the cliff even with unpaid rewards. No partial principal side effect from a rejected combined claim. Debit `(principalPaid + rewardsPaid) * k` once, update attributed gons once, and keep a reward-only NFT alive. Preserve ordinary approved-operator claims and recipient checks; the stricter surrender-owner rule is enforced in the parent, not retrofitted to ordinary child claims.

Retained parent interface minimum is an authoritative read such as `migrationActivated() external view returns (bool)`, installed on the persistent facet. All Migration children query their initialized parent; no child setter, separately mutable gate or cached activation copy. This interface is proposed, not installed today. Activation must not call a child through a half-finalized lifecycle.

### 2.3 Fee/creator allocations: concrete bounded custody design

Introduce one internal reward-distribution hook in `StakedDETFTarget` at S1's existing `Repo._distribute` call; default implementation remains unchanged. Migration override still pulls exact rewards, uses the same `_allocate`/rebase/top-up order and captures the fee/creator reserved-NFT owners **at allocation time**.

During Stage1 call the existing distribution with the staking proxy itself as the receipt destination for both role allocations. Record the issued `fee * postDistributionK` and `creator * postDistributionK` as beneficiary-keyed pending gons in Migration-only storage. This preserves `totalGons`, subsequent ordinary rebase participation and top-up inputs without delivering receipts outside protocol custody. Merge credits if recipients coincide. Previous allocations belong to their captured recipients; later reserved-role transfers affect later allocations, not prior pending rights. Role NFTs remain standing rights with no principal.

Add `deferredRoleGons(address)` and an activation-gated, synchronized, guarded `claimDeferredRoleRewards()` with fixed payment to the recorded caller-beneficiary. Pay `floor(pendingGons/k)` sDETF, debit exactly `paid*k` from pending attribution and protocol-held gons, and retain any sub-native remainder. Release is a transfer of already issued receipts, not a second funding/mint. Never redirect pending rights to the owner, current fee oracle address or current role holder on activation. Activation opens release; it must not scan all beneficiaries. This is a proposed mechanism grounded in S2; no deployed deferred-claim selector exists.

### 2.4 Required receipt/SY egress prerequisite

**Do not mistake section 2.3 for full E5 closure.** Concrete source counterexample:

1. Stage1 lasts past a migration bond's cliff.
2. Holder calls permitted `claimPrincipal`; sDETF now resides outside the bond.
3. A later funded distribution lowers `k`, increasing that wallet's balance without changing its gons (S2).
4. Ordinary `exchangeIn`/`exchangeOut` can withdraw the entire increased balance. Alternatively `transfer`/`transferFrom`, parent `_unstakePath`, or staking-SY deposit/redemption moves that growth outside the original gate (S1/Y1/P4).

This follows directly from the inspected code; it was **not executed** here. The source's actual ordinary test explicitly expects wallet growth and full-balance unstaking: `test/foundry/spec/vaults/detf/common/claimToken/RebasingClaimToken_Accounting.t.sol:53-70,73-109`.

Therefore a complete Migration implementation requires a **principal-preserving, reward-aware egress ledger** for new-instance wallet receipts and staking SY, not just NFT flags. It must retain exact funded reward ownership under custody until activation, propagate principal attribution through every permitted transfer/wrap/unwrap, preserve mature principal access, and conserve gons/dust. Ordinary receipt storage has no such split (S2), and SY stores only backing gons/dust or raw backing (`contracts/vaults/detf/common/sy/DETFSYRepo.sol:15-23`). A blanket receipt/SY pause would violate mature-principal access; treating all post-cliff receipts as unrestricted would leak subsequent rewards; suppressing funding until activation would violate accrued participation.

**Not frozen in this preflight:** the additional receipt/SY split storage and principal-only wrapper-exit ABI. The planned deep-high task 5 must establish one accounting construction and prove section 4's egress oracles before composing these as E5-complete children. This is a new-instance accounting proof, independent of the legacy E2 authentication gap. No owner-policy alternative is proposed. The source-backed bounded next increment is sections 2.1-2.3 plus real-proxy tests, with section 2.4 retained as an explicit completion dependency, not deferred out of the product.

### Cross-contract locks and ordering

1. **Parent-origin creation:** parent lock -> settle old participants -> mint exact new principal -> bond synchronization (authenticated parent-lock no-op) -> bond lock -> staking synchronization (same no-op) -> staking lock -> exact credit -> bond open/mark -> reset allowances. New principal must not enter before parent settlement. An empty aggregate must advance the reward baseline without minting an unallocatable reward or giving the first bond pre-creation epochs (P2/P3/B5).
2. **Child-origin claim/transfer/exit:** synchronize **before** local lock so parent can fund staking; parent settlement may take staking's funding lock. The staking `synchronizing` flag is a recursion guard, not a global lock (S1:241-246). Ordinary dust retirement calls back from bond to staking and must remain composable.
3. **Safe NFT receiver:** C1 calls receiver before transfer authorization/ownership mutation completes. Test callback state, reentrant claims/activation/surrender and full rollback; do not assume OpenZeppelin's post-transfer receiver ordering. The new funded mint itself is not safe mint.
4. **Donations:** bond lock -> parent `joinDonatedCapital` lock, then `notifyReserveDonated`; existing parent-forwarded donation enters bond without holding the parent lock (P4:731-745; B donation anchors). Do not put a blanket parent lock around that forwarding call and deadlock its authorized callback. Bootstrap lane owns the adapted first-join contract.
5. Locks are per proxy. A view of finalized lifecycle is not a shared reentrancy guard. Parent activation/configuration/surrender must reject cross-child callbacks under its own lock; all participating receipt/SY/role-release money paths need their own lock and fixed initialized authorities. No generic executor or arbitrary callback whitelist is introduced.
