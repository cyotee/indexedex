# Migration DETF - draft product requirements

- **Status:** Requirements ready for implementation-and-test planning; implementation is not authorized by this document.
- **Date:** 2026-11-08.
- **Updated:** 2026-11-11.
- **Revision:** migration-detf-discussion-r21-stage2-surrender.
- **Owner-approved lifecycle correction (2026-11-11):** All legacy surrender is Stage 2-only. Atomic activation enables ordinary deposits and surrender while removing every entitlement loader/amendment and discretionary issuance selector. Partly surrendered migration configuration cannot be edited. Implementation plan sections 1.3-1.4 also govern original-wallet admission.
- **Purpose:** Record the accepted migration requirements and the engineering work needed for an implementation-and-test plan.
- **Scope:** A new Migration DETF type composed from compatible existing DETF code, new migration-specific facets and a deployment package. Its administrative owner is configured per proxy through `PkgArgs` and Crane Ownable. No upgrade of an immutable legacy deployment.
- **Authorization:** This draft does not authorize contract implementation, deployment, token issuance, asset transfers, or final compensation allocations.

## 1. Outcome

Create a new Migration DETF type, reusing the existing Uniswap V4 DETF implementation wherever compatible and adding the facets and package needed for the migration behavior. Do not rewrite the DETF stack as a separate implementation. It has two distinct paths: **independent compensation allocation**, delivered as a bond without a user deposit, and **surrender-triggered migration credit**, delivered as a bond only when the user surrenders eligible legacy assets. Both paths use the same class of new bond: principal is locked for the full 90 days, and accrued bond rewards may be claimed during the lock only after activation. No new-instance reward claims are permitted during Stage 1.

The new package's `PkgArgs` supplies the initial administrative owner for each deployed proxy. Initialize that address through Crane's ERC8023 `MultiStepOwnableRepo` and expose the existing Ownable facet surface. The current proxy owner controls loading and alteration of both entitlement configurations, independent compensation issuance, activation and harvesting. The owner does not set a separate ETH or DTF contribution price. This supersedes every earlier fee-recipient-based migration administration role and keeps the functionality reusable across compatible packages.

The new instance has two stages. **Stage 1 - configuration:** ordinary new-money deposits and all legacy surrender-triggered credit are disabled; the current owner may configure entitlements, fund reserves and execute independent compensation under its separate rules. **Stage 2 - active:** one owner-authorized atomic transaction enables ordinary deposits, eligible legacy surrender and reward claims while removing all entitlement configuration/amendment and discretionary compensation issuance selectors through ERC-2535 routing removal. No intermediate state may expose open deposits or surrender with configuration authority still usable. A partly surrendered migration entitlement can never be amended. The latest configured-original-wallet and missing-entitlement rules are recorded in implementation plan section 1.3.

Deposited legacy assets are retained under migration control for potential recovery of DTF over time. Surrender determines who receives migration credit and puts the asset in custody. It does not reprice the credit. Use the original verified historical ETH and DTF contribution amounts as mint inputs against a snapshot of the new reserve pool taken after recovery-fund funding. The credit is the user DETF the existing mint preview would return if that contribution had been deposited at that snapshot. For a legacy bond NFT, load its historical purchase contributions into migration credit configuration keyed by the source NFT contract and token ID; do not assume those contributions can be recovered from the NFT alone. Loading this configuration does not award a new bond: the matching legacy NFT must first be surrendered. No linear contribution-price setter, intermediate ETH-only accounting unit, or balance-compression curve is used.

The mint input is the original contribution. Previously claimed principal does not reduce it, and accrued or future old-bond rewards do not increase it. The contribution-based mint preview replaces the earlier blanket old-DETF-to-new-DETF 1:1 preference and the November 9 linear output-rate setters. The correspondence between each legacy entitlement and its eligible original contribution amounts must remain explicit.

The owner's funding plan is to use part of the proposed 90 ETH to acquire DTF, then donate DTF and ETH to the new DETF. A donation function accepting all underlying reserve-pool legs is required. Scripts are responsible for arranging funding before dependent configuration and bond issuance; funding is expected to be complete when entitlement configurations are loaded. Do not introduce independent funding-complete or entitlement-configuration finalization gates. During Stage 1, scripts may restructure remaining batches, resume interrupted work, make corrective funding transactions, and replace incorrect on-chain entitlement configurations of either type. Later DTF and harvested legacy DETF are donated rather than placed into ordinary bonds; future harvests are not a bootstrap prerequisite.

This is an explicit product exception for recovery. It must not silently turn ordinary DETF packages into permissioned arbitrary-mint products.

**Configuration is not delivered compensation.** Stage 1 is the configuration window: setters overwrite the complete configured entitlement for a recipient address or source NFT contract/token ID. They do not apply deltas, append another entitlement, or alter compensation already delivered. Repeating the same setter with the same values is idempotent. Stage 2 is the live stage: activation removes the entitlement-configuration facet's complete callable surface from the proxy through an ERC-2535 cut, so no caller can configure or amend entitlements afterward. There is no administrative mechanism in either stage to claw back, resize, reprice or otherwise alter delivered compensation.

### 1.1 Terms used throughout this document

| Term | Meaning |
| --- | --- |
| Independent compensation allocation | The owner's consolidated compensation allocation for a recipient address, without requiring that recipient to surrender assets. Multiple eligible compensation components for that recipient may be combined into this record; no separate arbitrary allocation ID is required. It excludes legacy holdings awaiting surrender. |
| Surrender-triggered migration credit | The credit awarded only when an eligible legacy asset is successfully surrendered into recovery custody. It goes to the surrendering owner as a new bond, not to an address merely because that address held the asset when configuration was loaded. |
| Migration credit configuration | The loaded source-specific historical contribution data and rules used to calculate surrender-triggered migration credit. For a bond NFT, identify the source contract and token ID and record the original ETH/DTF purchase contributions. Configuration alone does not issue credit or a new bond. |
| Entitlement configurations | The collective term for independent compensation allocations and migration credit configurations. Both may be loaded and altered in Stage 1; both become administratively immutable in Stage 2. |
| Issued bond / consumed credit | Actual consideration already delivered through either path, distinct from merely loading configuration. Configuration setters cannot alter this consideration or reset its consumption record. Keep actual issuance, claims and custody history separately; replaying or replacing configuration is not another payout or an adjustment to a delivered bond. |

Use "compensation allocation" only for the independent path, and "migration credit" only for the surrender-triggered path. Loading contribution data for a held NFT is not an independent compensation allocation for that NFT. If the holder transfers it before surrender, the new holder must surrender it to receive migration credit; the former holder receives no independent allocation for retaining or previously holding it.

### 2.2 Confirmed principal rule and resolved interpretations

The original interpretation IDs are retained for traceability. The November 9 subtraction rule is not the conversion input after the November 10 mint-preview decision:

- **MIG-A01 - Superseded as a conversion input:** The November 9 confirmation subtracted previously claimed principal from principal credit. MIG-D18 supersedes that as the amount rule. The mint input is the original contribution. Previously claimed principal is not subtracted from it and is not replenished as a second contribution. The same contribution still must not be paid twice through another representation.
- **MIG-A02:** Resolved by MIG-D13: surrender is when credit is delivered and custody is taken, not the incident snapshot or an earlier registration date. Surrender does not reprice the original contribution.
- **MIG-A03:** Resolved for the bond class by MIG-D09/MIG-D12: credit is a new bond in the common 90-day class. Principal and reward records remain useful for harvest reconciliation. They are not extra mint inputs.

The owner has fixed the 90-day duration, claim behavior and per-bond clock: principal remains wholly locked until 90 days after that bond is created, while accrued new-bond rewards are claimable during the lock only after activation. Reward claims before activation are prohibited. The assistant's earlier linear-principal-vesting suggestion is not adopted. Final recipient allocations, total issuance and execution order remain operational inputs, not a reason to reopen the settled bond rules.

### 2.2.1 Funded-snapshot mint preview

On November 10, the owner decided to use the existing DETF minting formula. The quote book is a snapshot of the new reserve pool after it is funded from the recovery fund. The mint input is the original contribution. The compensation amount is the new DETF that would be minted to the user if that contribution had been deposited at that snapshot.

This supersedes the November 9 linear output-rate compromise, including its two owner-restricted ETH and DTF contribution-price setters, owner-directed price adjustments, and prospective rate updates after migration begins. It also supersedes the provisional 1:1 old-DETF conversion, the pre-exploit ETH-denominated valuation approach, and any remaining-principal or accrued-reward scale applied to the contribution before the quote. No curve other than the existing mint preview, arbitrary minimum award, or automatic haircut is adopted.

Historical contributions mean the actual asset quantities from the old transactions, not a new read of a historical market price and not arbitrary amounts supplied by a caller. ETH and DTF amounts stay separate. Each is quoted against the same frozen snapshot, and the user outputs are summed. Quoting them sequentially against a book that moves is not the rule. Receipt tokens and NFTs identify entitlement to contributions; their raw balances are not themselves ETH or DTF contributions. For an ETH-funded purchase routed through an exchange that delivers DTF, count the original ETH once and do not also count the intermediate DTF.

The existing mint preview, not a reimplemented linear rate, is the calculation. For the Uniswap V4 DETF path, the payment is converted to the reserve pair amount, that amount is boosted by the seigniorage fraction, and the reserve hook quotes DETF out. The user receives the depositor leg after the live mint split. The seigniorage inventory leg is not the user's compensation. The hook's input fee is inside that preview. If the live mint gate would swap existing DETF instead of minting, compensation still uses the mint preview, not that swap fallback. The implementation plan must name the snapshot fields required to reproduce this preview, including reserve balances, weights, scales, the swap fee and the seigniorage fraction, and must use the existing preview rather than a hand-rolled substitute. Integer scaling and rounding are those of that preview.

The snapshot is taken after recovery funding and before dependent compensation issuance. It is not a live quote at surrender and not an owner-adjustable rate. Existing bonds and configured credits are not repriced if the live pool later changes. The plan specifies how the snapshot is captured and how the preview is evaluated. It must not add the retired linear setters.

### 2.3 Change from the earlier ledger policy

The later owner instruction to fully credit users **when they deposit old assets** changes the earlier policy recorded in [CUSTODY_AND_HARVEST.md](CUSTODY_AND_HARVEST.md) and [LOSS_AND_RECOVERY_LEDGER.md](LOSS_AND_RECOVERY_LEDGER.md).

For this draft, the intended distinction is:

- While an eligible old holding remains with the user, exclude it from independent compensation allocations. Its migration credit configuration may be loaded without awarding credit.
- When the eligible holding is successfully surrendered into migration custody, award surrender-triggered migration credit using that configuration.
- Do not issue a second credit for the same entitlement merely because it was listed, transferred, wrapped, claimed into another representation, or later harvested.

Therefore, earlier sentences saying that a deposited asset can never receive new credit do not govern surrender-triggered migration credit. The ledger's held exclusions remain useful for separating independent compensation allocations from holdings awaiting surrender; they are not a permanent denial of migration credit after surrender.

The r20 decision is recorded in this PRD and noted in the recovery reports that would otherwise send a reader back to the linear rates or the unfilled ETH-loss formula. Frozen CSVs, evidence hashes and the November 8 ledger arithmetic are not rewritten. Their reconciliation into independent compensation allocations and migration credit configurations is future work.

## 3. Product identity and boundaries

**MIG-R01 - New DETF type, composed package.** Use the existing Uniswap V4 DETF as the base for a distinct Migration DETF type and deployment package. Reuse compatible existing facets, targets, repos, libraries and child-token packages rather than copying or replacing the whole stack. Add the new migration facets and package composition/initialization required by this PRD. Working names are `UniswapV4DetfMigrationFacet` and `UniswapV4DetfMigrationDFPkg`; exact names and supporting files remain implementation decisions.

The removable entitlement-configuration and independent compensation issuance surface must be separated from the user-facing surrender-triggered migration credit functionality required in Stage 2. A possible split is a removable `UniswapV4DetfMigrationAllocationFacet` and persistent migration functions; exact names and placement remain implementation details. Remove loaders and amendment routes for both independent compensation allocations and migration credit configurations, while retaining surrender against existing migration credit configurations, the post-funding mint-preview quote, custody/harvest operations and existing bond claims. Do not retain a linear contribution-price setter.

**MIG-R02 - Scoped exception and reuse.** Exceptional migration issuance is available only through the new package and authorized migration paths. Ordinary instances retain their existing issuance rules. Reuse existing DETF, staking and bond code by default; change or adapt it only where an accepted migration requirement is incompatible. The plan must identify such conflicts rather than promise every existing selector can be reused unchanged.

The configured Ownable authority and one-time removal of loaders are explicit exceptions to the ordinary DETF unowned/immutable-instance rule, scoped to this new type. Ownership does not authorize arbitrary upgrades or grant every privileged action to the owner. Do not expand owner-only capabilities in reused code beyond the roles specified here.

**MIG-R03 - New deployment.** The package creates a new instance; it does not upgrade the old DETF, modify a legacy NFT, or change a legacy registry disable flag. The new instance has the narrowly scoped, one-time allocation-removal transition in MIG-D21, not unrestricted owner upgrade authority.

### 3.1 Configurable proxy ownership and role boundaries

**MIG-R41 - Owner from PkgArgs.** The new package's interface-defined `PkgArgs` must include the initial owner address. Its account initialization must initialize Crane's `MultiStepOwnableRepo` in the deployed proxy's storage, not merely in a shared facet or package deployment. Include Crane's existing `MultiStepOwnableFacet` ownership/query/transfer functionality instead of a parallel migration-owner storage variable or custom ownership protocol. Reject an invalid zero initial owner rather than silently substituting `msg.sender`, the deployer, creator or `feeTo()`.

Use the current owner from that repo for every migration administration check: loading, amendment, activation, price setting and harvesting. A pending owner gains none of these permissions before the existing Crane ownership transfer completes; the former owner loses all of them once it completes. Preserve Crane's existing transfer/buffer semantics and specify their initialization in the plan. Protect proxy initialization from later caller-controlled reinitialization.

`PkgArgs.owner` here is distinct from the existing DETF `creator` field and the hook's `ownerOnlyLiquidity` policy. Different proxies deployed from one package may have different owners without changing the package or facet implementation. The registered vault/package deployment flow remains the existing IndexedEx flow.

| Action | Required authority |
| --- | --- |
| Load/alter migration credit configurations in Stage 1 | Current proxy owner in Crane Ownable storage |
| Load/alter independent compensation allocations in Stage 1 | Current proxy owner in Crane Ownable storage |
| Activate ordinary deposits and atomically remove loaders | Current proxy owner in Crane Ownable storage |
| Execute harvest batches and staged recovery | Current proxy owner in Crane Ownable storage |
| Disable/re-enable through the Vault Registry | Existing registry authority and rules |

All migration administration follows the current proxy owner. The fee recipient has no independent authority to load, activate or harvest; it can perform those actions only if it is also the current owner. Ownership transfer moves all still-available migration administration permissions, but does not alter the fee oracle or confer Vault Registry authority. After activation, ownership or oracle changes cannot restore the removed loaders.

This draft does not choose between an integrated custodian and a cooperating custody contract. It also does not require restoration of retired vault families, a change to the underlying AMM, or a redesign of unrelated DETF products.

## 4. Two-stage lifecycle and new-money gate

**Stage 1 - configuration** starts at deployment. Ordinary new-money deposits and every legacy surrender-triggered credit route are disabled. The current owner may load or replace either entitlement configuration in bounded batches. Funding and independent compensation bond creation remain available under their existing requirements. No legacy token/NFT/claim may be accepted through surrender before activation; configuration never starts a migration bond clock.

Stage 1 is an operational configuration window expected to last minutes to hours while scripts run and configuration is verified. The operator will finish it before any compensation bond's principal lock expires. This is the stated operating workflow, not an additional on-chain deadline or automatic-activation gate. New-instance reward claims are prohibited throughout Stage 1 under MIG-R43.

**Stage 2 - active** begins only through MIG-R07's atomic activation. Ordinary new-money deposits and new-instance reward claims become available under their applicable rules, and all configuration/amendment authority for both paths is permanently removed along with discretionary compensation issuance. The owner cannot alter either entitlement configuration in Stage 2. Executing surrender-triggered migration credit against a frozen configuration and the post-funding mint snapshot, and recording actual consumption or claims, are not administrative configuration amendments.

The stage boundary is enforced by atomically removing the entitlement-configuration selectors and enabling ordinary deposits and eligible surrender. Stage 1 replacement changes configuration only and cannot alter independent compensation already delivered. No migration entitlement is partly surrendered in Stage 1. Stage 2 has no entitlement setter or restoration path. Ordinary claims, accrual and permitted transfers follow their existing rules and are not administrative corrections.

**MIG-R04 - Closed at initialization.** Every new Migration DETF starts with new-money issuance disabled. Deployment or receipt of the first migration deposit must not implicitly enable it.

**MIG-R05 - Complete route coverage.** While closed, all ordinary user routes that mint new DETF or buy an ordinary bond must reject that operation, including alternative selectors, bundles, and indirect routes exposing the same behavior. A caller cannot bypass the gate by labelling new capital as a migration.

**MIG-R06 - Activation-gated migration availability.** Every legacy token, NFT or claim surrender and its surrender-triggered credit is rejected in Stage 1 before custody, consumption, minting or bond funding. Activation opens eligible surrender against frozen configured original-wallet entitlements in the same atomic transaction that enables ordinary new-money deposits and removes configuration authority. Stage 2 surrender retains its recovery exception and remains subject to normal source, ownership, registry and funding checks.

**MIG-R07 - Atomic one-way enabling and loader removal.** Moving from Stage 1 to Stage 2 requires an explicit action authorized by the current proxy owner. That action atomically enables ordinary deposits and eligible legacy surrender and removes all configuration/amendment selectors for both entitlement types and all discretionary compensation issuance selectors as specified in MIG-R27. None of these effects may succeed alone. Activation and finalization state must be observable. There is no separate new-money closing function after activation. Normal Vault Registry disablement remains applicable without reversing activation or restoring either configuration authority.

**MIG-R43 - Reward claims require activation.** Before successful activation, reject all routes that pay rewards from the new Migration DETF, including reward claims for bonds issued through either compensation path and any alternate claim, exit or settlement route that would pay the same rewards. Neither the current owner nor another caller may bypass this requirement. A rejected reward claim leaves balances and claim accounting unchanged. Use the same finalized activation state as MIG-R07, not a separately configurable reward-opening switch; no callback during activation may claim rewards through an intermediate state.

After activation, accrued rewards may be claimed during the remaining principal lock under MIG-R23 and normal ownership, accounting and registry checks. Activation does not restart accrual, discard already accrued rewards, backdate participation or change a bond's lock. This restriction concerns payouts from the new instance; it does not prohibit authorized harvesting of surrendered legacy positions into recovery custody under section 7.

| Operation | Stage 1: configuration / new-money gate closed | Stage 2: active / new-money gate open |
| --- | --- | --- |
| Authorized loading/alteration of independent compensation allocations | Permitted, including replacement of already configured records | Unavailable: configuration/amendment selectors removed |
| Independent compensation bond issuance | Permitted under the funding and allocation rules | Unavailable: discretionary compensation issuance selectors removed |
| Authorized loading/alteration of migration credit configurations | Permitted, including replacement of already configured records | Unavailable: configuration/amendment selectors removed |
| Eligible legacy token/NFT surrender and surrender-triggered migration credit | Rejected before custody, consumption or issuance | Permitted using frozen configured original-wallet entitlements |
| Reserve donations, including the required all-leg donation | Permitted by this gate | Permitted by this gate |
| Ordinary new-money mint | Rejected | Existing ordinary rules apply |
| Ordinary new-money bond purchase | Rejected | Existing ordinary rules apply |
| New-instance reward claims, including alternate payout routes | Rejected until activation | Permitted under the normal claim and registry rules; principal remains subject to its lock |
| Other claims, exits, transfers, maintenance, and legacy harvesting | Subject to existing rules and the prohibition on new-instance reward payouts | Subject to existing rules |

"Permitted by this gate" does not waive ownership, source eligibility, entitlement checks, the applicable Vault Registry disable rules, or other validity conditions. This one-time startup gate is not a new general-purpose pause mechanism. Ordinary operations remain subject to the normal registry integration. The plan must account for automatic expansion/reward issuance during bootstrap consistently with actual bond creation, funding and the no-backdating rule.

## 5. Independent compensation allocations and configuration batches

**MIG-R08 - Recipient-keyed independent compensation allocations.** Load independent compensation allocations by recipient address, consolidating that recipient's eligible compensation components rather than requiring a separate arbitrary ID for each component. Deliver the compensation as bonds without requiring asset surrender. Support a large recipient set split into independently executable batches; processing a batch must not require iterating the complete population. These bonds use the same class and 90-day duration as bonds awarded for surrender-triggered migration credit.

Independent compensation configuration, correction and discretionary issuance are Stage 1 operations. Stage 2 closes these surfaces permanently, rather than pausing them. Holdings awaiting surrender are excluded from independent compensation allocations, even if their historical contributions have been loaded into migration credit configuration.

**MIG-R34 - Resumable, replaceable Stage 1 entitlement configurations.** Allow the current proxy owner to load and alter both independent compensation allocations and migration credit configurations in bounded batches throughout Stage 1, independently of the funding batch process. The setter for each configuration accepts its complete replacement values. A previously defined recipient or source record must not be rejected merely because it already exists or was included in an earlier processed batch. Repeating identical values is idempotent; corrected values replace the prior configuration rather than append another allocation or require the script to calculate a delta.

Support both reasons for amendment: restructuring unexecuted batches after a script problem, and correcting erroneous configurations already recorded on-chain. A processed configuration batch does not mean compensation has been delivered. An independent compensation record may be overwritten during Stage 1 even after issuance, but that overwrite cannot alter consideration already delivered or make consumed credit available again. Migration credit records cannot have been partly or wholly surrendered during Stage 1 because all legacy surrender rejects until Stage 2; after activation, their configuration cannot be amended. The prohibition on changing either entitlement configuration starts at activation, not at first loading or first use.

Keep configuration replacement separate from actual donations, issuance, claims, consumption and surrendered assets. The setter overwrites the stored configuration with the supplied complete values; the script does not calculate a delta. Repeating identical values leaves the same configuration. Loading, replacing or replaying configuration does not itself issue compensation, claw back or resize an issued bond, recalculate its accrued rewards, reset its clock, or create a retroactive top-up or deduction. Delivered compensation remains governed by its bond and claim rules, not by later writes to its source configuration.

The plan must preserve separate configuration and execution records so subsequent execution uses the applicable configuration without replaying already consumed entitlement. It must not design an adjustment mechanism for delivered compensation or treat such a mechanism as an unanswered product question. Do not add a first-use configuration freeze as a substitute for the Stage 1 overwrite semantics. Bond creation timestamps and the full-duration lock remain governed by MIG-R23.

At activation, remove every loader and amendment route for both configurations, including replacement, increase, decrease, clearing and equivalent dataset/root replacement or authorization routes if such mechanisms are selected. Changes in asset ownership and consumption under frozen migration credit configurations are ordinary execution, not new administrative configuration. Remaining principal and accrued rewards do not reprice that frozen credit. The exact storage representation and resumable-script checkpoints remain implementation details.

**MIG-R09 - Idempotent configuration, no duplicate payout.** Overlapping, repeated or regrouped Stage 1 configuration batches must not duplicate credit. Consolidate eligible independent compensation components in the recipient-address record and submit the complete corrected value on replacement, rather than creating a second allocation identity for the same recipient. Record actual issuance separately from configuration; loading migration credit configuration never awards a new bond without surrender. Authorized corrections follow MIG-R34 rather than being rejected as duplicate definitions.

**MIG-R10 - Authority and reconciliation.** Only the current owner resolved from the proxy's Crane `MultiStepOwnableRepo` may load or alter independent compensation allocations in Stage 1. The initial owner comes explicitly from `PkgArgs`; neither deployment sender nor fee recipient is an implicit substitute or additional administrator. In Stage 2, this authority no longer exists even if ownership changes. Preserve observable reconciliation of the current recipient-keyed allocation, configuration corrections, actual issuance, recipient bonds and outstanding compensation. Activation is the structural cutoff in MIG-D21; no separate numerical issuance cap is selected.

The word "premint" establishes the issuance exception. The completed allocation process must provide the recipient's compensation bond without requiring legacy-asset surrender. Initial reserve funding must precede compensation-bond creation. Within that constraint, the exact sequence of recording, minting, bond funding and receipt/ownership delivery remains an implementation-planning decision. Merely recording an allocation does not prove that the recipient has a funded bond or start its lock or reward participation.

The relationship between the paths is decided: independent compensation allocations require no deposit; surrender-triggered migration credit requires surrender. They address the owner's recovery objective for pre-exploit exposure but must cover non-overlapping compensation. A user is not globally barred from one path because they used the other. Independent compensation is keyed by recipient address; bond-NFT migration credit configuration is keyed by source NFT contract and token ID. Reconciled contribution amounts and other source-specific representations remain to be specified.

### 5.1 One-time activation and permanent configuration cutoff

Failure of any part reverts the entire transition. There must be no externally usable intermediate state with ordinary deposits or surrender open and either configuration authority still callable.

ERC-2535 removal changes selector routing; it is not deletion of the shared facet deployment or erasure of the instance's configuration records. The transition itself preserves the then-current configurations, issued bonds, principal, reward rights, lock timestamps, consumed-credit records and accounting needed by continuing surrender-triggered migration credit. Remove every alias, single-item and batch entrypoint that can configure either path or create discretionary compensation credit, not merely one batch selector. Preserving state during the cut does not prohibit Stage 1 corrections before the cut.

**MIG-R28 - No restoration or bypass.** In Stage 2, no callable path on the instance may restore configuration/amendment authority for either path, reopen Stage 1, or perform equivalent additions, replacements, reductions or other alterations through surviving selectors or arbitrary delegatecall. A generic `diamondCut` authority capable of reinstalling either loader would not satisfy this requirement. The one-time removal capability must be consumed or rendered inaccessible after activation; exact selector placement is an implementation detail. Before activation, every surrender route rejects. Keep eligible custody/recovery, donations and existing bond claims usable under their applicable rules. Do not keep a contribution-price or entitlement-update path; surrender remains asset-backed rather than a no-deposit administrative mint.

The plan must enumerate selectors removed and retained, prove actual proxy routing before and after activation, and verify that no remaining package/factory/initialization path restores removed functionality. Merely setting an allocation-disabled Boolean while leaving restorable issuance is not the owner's chosen structural cutoff. ## 6. Legacy surrender and surrender-triggered migration credit

**MIG-R11 - Defined sources.** Support both legacy generations and all asset categories in MIG-D11: old DETF, bond NFTs, sDETF, SY, legacy staking claims, underlying vault tokens and LP tokens. Distinguish each generation, source contract and asset type. Resolve and verify the actual supported addresses and routes; do not silently defer an accepted category or accept an arbitrary address because it has a matching token interface.

**MIG-R12 - Custody before credit.** A successful migration must establish control over the actual legacy token amount or exact NFT and assign the new bond to the surrendering owner under MIG-R37. Approval alone is not a deposit. Credit and custody must complete atomically: a failed deposit or failed credit must not leave the user charged without its corresponding entitlement.

**MIG-R13 - Surrender-triggered migration credit.** At successful surrender, use the loaded migration credit configuration's original ETH/DTF contribution and issue the user DETF from the post-funding mint preview as a bond in the common 90-day class. Do not remeasure that amount from remaining principal or accrued unclaimed rewards. Do not count the same contribution twice under MIG-R14. Loading configuration alone must not create that bond. Legacy surrender and its migration credit are available only in Stage 2 after atomic activation; successful surrender need not wait for the old assets to finish harvesting. Raw receipt quantities do not become new shares through a blanket 1:1 rule.

**MIG-R14 - Credit once.** Track consumed token quantities, source NFT contract/token IDs, recipient-keyed independent compensation allocations, and actual credit sufficiently to prevent duplicate payment. Wrapping, transferring, partial claims, or depositing assets obtained from a prior claim must not create a second credit for entitlement already compensated. A migration credit configuration is not itself paid credit or an independent compensation allocation for the held asset.

**MIG-R42 - Loaded contribution history for bond NFTs.** During Stage 1, the owner loads the original historical ETH and DTF amounts used to purchase each supported legacy bond NFT into migration credit configuration keyed by its source NFT contract and token ID. Token ID alone is not globally unique across source collections or legacy generations. Verify purchase evidence rather than infer the original contribution from the NFT's existence, current holder, current market value or current redemption value. That loaded history is the mint input. Do not replace it with surrender-time principal or reward balances.

The configuration may be corrected during Stage 1 under MIG-R34 and is frozen in Stage 2. It does not require surrender at loading time and does not award a new bond to the then-current holder. On actual Stage 2 surrender, require a matching configured NFT entitlement, require the caller to be its configured original acquiring or contributing wallet, verify that wallet's control of the NFT, and atomically award the frozen configured credit to that wallet. An NFT transfer does not transfer entitlement to another holder; the configured original wallet must regain control before surrender. Missing configuration or a different surrendering wallet reverts without custody or credit effects. Existing surrender and consumption checks prevent the same NFT from being credited twice.

**MIG-R35 - Final surrender, atomic failure.** A successfully completed migration is final. Do not expose a cancellation, refund or return route for its surrendered assets. Failure of custody, entitlement consumption or bond credit reverts the entire migration, leaving no unmatched asset debit, consumed credit or issued bond.

**MIG-R36 - Partial fungible migration, whole NFTs.** Users may surrender a portion of an eligible fungible balance. Consume only its proportionally attributable entitlement and preserve the unconsumed remainder for later transfer or migration. Each NFT is surrendered as a whole position; accepting an NFT does not require surrendering every NFT owned by that user.

**MIG-R37 - Surrendering owner receives credit.** The owner surrendering the legacy asset is the recipient of the new migration bond. Bind custody, consumed entitlement and bond ownership to that same asset owner; do not expose a separate beneficiary parameter or relayer feature in this version. An ERC-20 allowance or NFT operator approval alone must not let another party redirect the migration credit. This asset owner is distinct from the configurable administrative owner. This restriction is specific to user surrender: it does not remove the administrative owner's pre-activation ability to load compensation bonds for their specified recipients.

### 6.1 Fixed-principal old bonds

The mint input is the original ETH and DTF purchase contribution loaded for that source NFT contract and token ID. It is not:

`principalRemaining = originalPrincipal - principalAlreadyClaimed`

`oldBondEntitlement = principalRemaining + accruedUnclaimedRewardsAtDeposit`

That November 9 identity remains historical traceability only. It is not applied to the contribution before MIG-D18.

**MIG-R15 - No extra old-reward mint input.** Do not add projected yield, future interest, future expansion distributions, accrued unclaimed rewards, or rewards the old bond might earn after surrender to the mint input. Harvest accounting may still distinguish old principal from old rewards. That distinction does not change the new-bond amount. The new bond uses the agreed full 90-day principal lock starting at its own creation, rather than a duration or start inferred from the old lock. Rewards subsequently earned by the new bond are not part of the migration-credit calculation.

**MIG-R16 - Do not pay the same contribution twice.** A principal or reward claim before migration does not reduce the original-contribution mint input and must not create a second credit for that contribution. A claim or settlement performed as part of migration must be reconciled with custody, not used to reprice the credit. The NFT alone is not assumed to expose its historical contribution amounts. Do not substitute the bond's current underlying redemption value.

Example, not an independent compensation allocation: an old bond purchased with 1 ETH and 100 DTF, with original principal 100, prior principal claims of 20, and accrued unclaimed rewards of 5, is quoted as a 1 ETH mint preview plus a 100 DTF mint preview against the same post-funding snapshot. The 20 claimed principal and the 5 accrued rewards do not change those inputs. The user amount is the sum of those two user-mint outputs, not 85 old units and not 85 new shares.

### 6.2 Fungible legacy tokens and other bond models

Legacy DETF tokens and all categories in MIG-D11 are migration inputs. Establish the attributable original ETH and DTF contribution quantities before applying the post-funding mint preview. A liquid token balance has no separate old-bond principal/reward split merely because it came from a bond claim.

**MIG-R33 - Contribution history follows assets proportionally.** A transfer carries the asset's associated unconsumed contribution history to its new holder. A valid surrender by that holder can receive the corresponding migration credit even if another account made the historical contribution. Do not bind eligibility exclusively to the original payer or leave an additional claim for that payer after the same entitlement has transferred.

For mixed holdings of a fungible asset, a partial transfer or migration carries the same proportional fraction of each historical contribution component associated with that balance. If the selected amount is fraction `f` of the balance, it carries fraction `f` of its attributable ETH component and fraction `f` of its attributable DTF component; the remainder stays with the remaining holding. Do not select FIFO/LIFO purchase lots or let users choose the most favorable component. Merging holdings combines their associated components. NFTs retain their individual position histories.

The plan must define source-normalized balance units, wrapper conversions and integer rounding while preserving total entitlement and previously consumed credit. Splitting or repeating migrations must not manufacture additional contribution quantities through rounding.

The earlier CP bond NFTs are LP-share positions, not the later funded fixed-principal model. They are included, but need their own explicit contribution/ownership mapping. Do not rename an LP-share field to principal and then scale the contribution. For an ETH-funded purchase routed through an SE that delivers DTF, do not count both the original ETH and the intermediate DTF as separate contributions. Underlying vault tokens and LP interests need verified ownership fractions and historical asset-input attribution. The mint preview does not invent those quantities.

Staking receipts, SY wrappers, legacy TokenStaking claims, underlying vault tokens and LP tokens are expressly included, not merely possible future extensions. A nontransferable claim needs a supported way to surrender its rights or claim its assets into custody. The plan must demonstrate that route rather than assume a staking weight is an ERC-20 or require the user to retain an independently exercisable credited claim.

## 7. Custody and harvesting

**MIG-R17 - Preserve deposited positions.** Hold or process accepted legacy assets under the selected migration custody design so supported principal/reward claims can be harvested over time. Maintain source, depositor, beneficiary, token quantity or NFT ID, credit issued, and subsequent recovery linkage.

**MIG-R18 - Separate credit from realized proceeds.** Credit granted at migration is not evidence of DTF already recovered. Record actual harvested assets, intermediate conversions, and resulting DTF separately. Never count an old bond's sDETF claim and its later DTF conversion as two recoveries.

**MIG-R19 - Donate harvests to the new DETF.** Harvest rewards and unlocked, unclaimed principal from surrendered positions. Donate harvested DTF and harvested legacy DETF to the new Migration DETF through their supported recovery/donation routes; do not lock harvested DETF into an ordinary bond. DTF and legacy DETF are distinct assets, not interchangeable names or an assumed new-DETF self-leg. Verify each donation/accounting route rather than assume the current donation ABI accepts either legacy DETF generation unchanged.

Later earnings from an old bond do not enlarge the depositor's already assigned migration credit or create a second personal harvest entitlement. This donation rule concerns recovered assets, not the 90-day bond issued as migration consideration. Only the current proxy owner may trigger harvesting, including each batch. Exact conversion and donation steps remain to be specified without changing the destination or creating ordinary bonds.

**MIG-R32 - Bounded harvest batches.** Allow the current owner to process a selected, bounded subset of surrendered positions per transaction and continue with other subsets in later transactions. The selection must unambiguously identify each legacy source and position, including NFT collection and token ID where relevant. No harvest call may require scanning the full deposited-NFT population or custody inventory merely to reach its selected positions. The exact selection ABI, batch limit and per-route gas budget are implementation-planning details.

Harvest progress must remain reconcilable per position across batches, including actual proceeds and remaining claims. Repeating or overlapping batches must not double-count or redonate proceeds already accounted for; a partially harvested position must remain available for genuinely new claims as they become claimable. Do not mark a whole NFT permanently exhausted merely because it was included in an earlier batch. All claimed assets remain subject to the existing custody and donation rules, not a caller-selected payout destination.

This owner-only batch capability remains available after allocation-facet removal through the retained harvesting surface, subject to normal registry rules. It does not confer new allocation authority.

**MIG-R39 - Whole-batch harvest rollback.** A failure in any selected harvest item reverts the entire selected batch, including its claims, transfers and progress accounting. Do not silently skip failed items or retain partial success within that transaction. Earlier successful batches remain committed. The current owner may retry with a smaller selection that excludes the failing item, without scanning or restarting the full inventory.

**MIG-R40 - Staged recovery with fixed destination.** Claiming, required conversions and donation may occur in separate transactions. Between stages, proceeds remain under the selected recovery-custody design with their source and undonated amounts reconcilable. The staged route must not expose an alternative beneficiary or discretionary withdrawal destination. Donate the recovered assets into the new Migration DETF through the supported routes; do not purchase an ordinary bond with harvested DETF.

If a later conversion or donation transaction fails, earlier successful claim transactions remain in recovery custody and the failed stage can be retried without reclaiming or double-counting those proceeds. Failure atomicity applies to each selected batch transaction, not retrospectively to previously committed stages. The current owner remains the only authority to initiate the staged harvesting operations.

Do not assume migration requires re-enabling a legacy vault. The research demonstrates a later DTF-leg redemption while the WETH-leg SE remained disabled, but does not establish that every legacy route or disabled contract permits withdrawal. Validate each selected harvesting route on its actual deployed generation.

The new-money switch governs issuance from ordinary deposits, not whether old assets may be deposited or harvested.

### 7.1 Donation-funded startup and reserve support

**MIG-R20 - Initial funding through donations.** The owner intends to use some of the proposed 90 ETH to acquire DTF and donate DTF and ETH into the new DETF through `donate()`. Support that funding path while ordinary new-money mint and bond purchases are disabled. Do not classify a reserve donation as an ordinary new-money purchase merely because fresh capital enters the system.

**MIG-R21 - All-leg donation.** Add a donation function that accepts contributions for all legs of the underlying reserve pool. This is additional required functionality, not a claim that the current single-token `donate` already implements it. Define receipt, reserve accounting, leftover handling, native ETH/WETH treatment and any new-DETF self-leg contribution before implementation. A donation must not be counted as a second user compensation allocation.

**MIG-R22 - Backing reconciliation.** Keep actual external reserve donations, minted new DETF supply, and new bond/staking backing separately reconcilable. The owner's intention is that donated capital makes the compensated bonds effectively funded. A proposed 90 ETH budget, a donation of self-issued DETF, or a recorded allocation alone does not establish that all required reserve and bond-escrow balances exist.

**MIG-R31 - Scripted funding and configuration batches.** The operator's scripts arrange funding before the entitlement-configuration and independent compensation issuance work that depends on it. Funding is expected complete when entitlement configurations are loaded, but the contract must not introduce a separate funding-complete flag, independent configuration-finalization flag, or mandatory funding-target certification step. Use basic sanity checks to catch script mistakes; the plan must identify those checks without turning them into new lifecycle gates.

Funding and the two entitlement configurations may run in separate bounded batches. During Stage 1, the operator can resume interrupted work, regroup remaining batches, replace incorrect configurations from previously processed batches and make corrective funding transactions without resetting the deployment. Scripts submit full replacement configuration values, not calculated deltas, and do not replay confirmed donations or issuance. Checkpoints must distinguish independent compensation allocations, migration credit configurations, corrections, actual custody/consumption and bond issuance. A merely recorded configuration does not create a bond or start a clock; bond-NFT migration credit still requires surrender of the configured NFT. Activation remains the one permanent configuration cutoff; ordinary donation and harvest routes remain available in Stage 2.

Initial reserve funding is distinct from later donations of harvested legacy assets. This requirement neither waits for those future harvests nor specifies that all 90 ETH remains on the ETH side. Once funding is complete, each compensation bond starts its own 90-day clock at creation, not at the funding transaction or a shared launch date. Reward accounting must not backdate the new bond's participation into the unfunded period.

**MIG-R23 - Common bond class and claim behavior.** Independent compensation allocations and surrender-triggered migration credit both deliver the same bond class, with principal locked for 90 days. Set `lockStart` to the block timestamp when that bond is actually created, and `unlockTime = lockStart + 90 days`. A compensation bond starts when the allocation batch creates the recipient's bond; a migration bond starts when successful surrender and credit create the new bond. Merely recording either entitlement configuration does not start a bond clock. No shared launch timestamp or old-bond timestamp is substituted.

Before `unlockTime`, no claim or exit route may release any of that bond's principal. At or after `unlockTime`, the remaining principal is unlocked and claimable under the normal ownership and accounting checks. There is no linear principal release during the lock. Bonds created in the same block may share a timestamp; bonds created in later batches or migrations start their own full 90-day periods.

Accrued rewards earned by the new bond may be claimed before principal unlocks only after activation. Before activation, reward claims are prohibited for both independent compensation bonds and surrender-triggered migration bonds under MIG-R43. Reward participation still begins at actual bond creation; claim gating does not defer accrual until activation. After activation, a reward claim must not release principal, reduce the principal obligation, or reset or shorten the lock. One-time activation, registry disablement or re-enabling, and subsequent donations must not start, reset, shorten or extend an existing bond's clock. There is no contribution-rate change to apply to that clock.

**MIG-R38 - Ordinary bond transfer rules, unchanged lock.** Apply the ordinary bond's transfer rules to both compensation and surrender-triggered migration bonds. A permitted transfer carries the remaining principal obligation and bond rights without changing `lockStart` or `unlockTime`. Selling or transferring the bond does not permit either party to withdraw its principal before the original 90-day lock expires. The plan must verify the ordinary transfer surface rather than add a separate migration-only transfer mechanism.

### 7.2 Post-funding mint preview

**MIG-R24 - Existing mint preview, frozen book.** Do not add an ETH contribution-price setter or a DTF contribution-price setter. Credit is the user output of the existing Uniswap V4 DETF mint preview evaluated against one snapshot of the new reserve pool after recovery-fund funding. Do not substitute a per-surrender live quote, the old 1:1 token rule, a concave balance curve, or the mint path's below-threshold swap fallback.

The economic calculation, for each original contribution asset, is that preview. Quote the ETH component and the DTF component against the same snapshot and sum the user outputs:

`newBondCredit = userMintPreview(snapshot, originalEth) + userMintPreview(snapshot, originalDtf)`

`userMintPreview` means the depositor leg of the existing mint path, after the seigniorage split, with the hook's input fee inside the quote. It does not mean `contribution * newDetfPerAsset`. The implementation plan must reproduce the existing preview's integer scaling and rounding. ETH/WETH and DTF historical amounts use 18-decimal asset units in the current evidence; newer DETF uses nine decimals and older DETF/LP representations differ. The preview's own decimal handling is the rule. Avoiding an intermediate valuation asset does not remove that handling.

The code the plan must follow, rather than re-derive, is `UniswapV4DetfTarget._entryPreviewMint` and `_mintPath`, `UniswapV4DetfCommon._quoteMintGross` and `_splitMintedDetf`, and `DETFMintSplitLib._splitLiveGross`. For the weighted reserve used by this product, the hook quote continues through `previewExchangeIn` into the weighted exact-in preview, `WeightedMath.computeOutGivenExactIn`. Another hook family is not a silent substitute.

**MIG-R25 - Verified quantities, not gross wallet turnover.** Both independent compensation allocations and surrender-triggered migration credit use verified historical contributions attributable to their separate eligible exposure. Do not reduce those quantities for prior principal claims or increase them for accrued rewards. Account for external recoveries, partial surrenders, ownership transfers and previously issued credits without counting a routed asset conversion twice. A caller cannot choose an arbitrary historical amount. For bond NFTs, the owner loads the verified purchase contributions by source NFT contract and token ID under MIG-R42. The plan must specify the loading ABI and evidence reconciliation; it must not assume the NFT itself reveals those amounts. Other supported source mappings remain source-specific implementation work.

**MIG-R26 - One snapshot, no later rate change.** The quote book is the post-funding snapshot. The owner does not change an ETH or DTF contribution price after migration begins. A later surrender uses that same snapshot, not the live pool at execution and not an earlier off-chain quote. The snapshot does not recalculate existing bond principal, reset an existing lock, or alter already assigned credit.

Record the snapshot identity and the user-mint output used for each credit. The implementation plan must define how the snapshot is captured after funding and how both contribution assets are quoted against it without an inconsistent or order-dependent read. Whether a user supplies a minimum credit to protect a pending surrender remains an interface decision. Authority to update linear rates is not part of this requirement.

The mint preview replaces discretionary normalization of old token balances. It does not remove the need to resolve source units, entitlement ownership, or duplicate-credit checks. Surrender-time measurement determines who receives the configured credit and that custody succeeded. It does not select a new valuation from current legacy-pool reserves.

### 8.2 Work for the implementation-plan author

The following are engineering tasks, not additional reasons to reopen the settled product decisions:

- Exact facet boundaries, storage, selectors and events.
- Verification of source addresses and supported legacy custody/claim routes.
- Batch gas sizing, recipient-keyed independent compensation consolidation, full-value replacement setters and duplicate-payout protection.
- Loading and verifying historical ETH/DTF purchase contributions by source NFT contract and token ID; configuration must not award surrender-triggered migration credit before surrender. Evaluate those original quantities with the existing mint preview against the post-funding snapshot. Do not scale them by remaining principal or accrued rewards, and do not add linear contribution-price setters.
- Atomic custody, measurement and credit sequencing.
- Native ETH/WETH handling and all-leg donation accounting.
- Tests proving the full 90-day principal lock, rejection of every new-instance reward payout route before activation, post-activation claims of accrued rewards without resetting accrual or locks, the new-money gate and migration availability.
- Proportional historical-contribution accounting across mixed holdings, partial transfers and migrations, with conserved quantities and explicit rounding.
- Ordinary bond transfer verification, surrendering-owner recipient enforcement, atomic harvest rollback and staged recovery accounting.
- Resumable funding and configuration scripts that can restructure remaining batches and replace erroneous records from processed batches during Stage 1, with basic sanity checks and no independent lifecycle gates.
- Idempotent Stage 1 full-value configuration overwrite, with actual issued credit, claims, consumption, bond/backing accounting and custody history preserved separately. Configuration replacement cannot alter delivered compensation or replay consumed entitlement; no first-definition or first-use configuration freeze and no retroactive bond-adjustment mechanism. Remove the entitlement-configuration facet's complete callable surface at the Stage 2 transition.
- Reuse-compatible package composition, interface-defined owner-bearing `PkgArgs`, proxy-local Crane ownership initialization, transfer of all migration administration permissions, and preservation of the separate fee-accounting and registry integrations.

Final recipient amounts and the exact ETH/DTF funding split need not be hardcoded before planning, provided the PRD defines how allocations are authorized, bounded and loaded. No amount, conversion, or funding fact becomes approved merely because the plan accepts it as an input.

## 9. Draft acceptance criteria

These describe future observable behavior, not tests already executed or permission to implement.
