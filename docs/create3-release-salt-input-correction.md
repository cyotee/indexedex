# CREATE3 release salt input correction

- **Status:** planned
- **Created:** 2026-09-16
- **Updated:** 2026-09-16
- **Confirmed naming standard:** Standardize all component-name salts to `abi.encode(name)._hash()` via `BetterEfficientHashLib` (`using BetterEfficientHashLib for bytes`). Use `_hash()` for runtime CREATE3 salt hashing. Solidity `keccak256` is allowed in `constant` initializers (D14): `keccak256(abi.encode(name))` has the same value and preserves the name-only encoding. Existing compliant constants remain unchanged.
- **Confirmed scope:** Contract deployments through the CREATE3 Factory only. Proxy deployment is unchanged; `PkgArgs` and `calcSalt` are outside this effort.
- **Confirmed Crane boundary:** Correct every Crane CREATE3 package salt that still includes `PkgInit` or constructor data, including Crane-only tests and scripts. Already-name-only Crane salts are inventory-only. Unrelated Crane protocol internals, CREATE2, and proxy `deploy()` stay out of scope.
- **Confirmed runbook handling:** Update the salt-formula rows in the funded-staking public deployment runbooks to D3. Keep recorded hashes, addresses, and rehearsal results as historical, with a note that those records used the old formula.
- **Confirmed Crane test gate:** Add a hermetic IndexedEx test for the three corrected Crane superchain package producers; Script 24 and the Crane superchain fork test are compile-only for this effort.
- **Confirmed test instance keys:** Tests and TestBases that call the CREATE3 factory or registry directly may keep explicit identity fields (pool address, scenario label) in a salt as long as no creation-code or constructor-blob hash is included. Production FactoryServices, Init* services, and IndexedEx deployment scripts stay name-only. IndexedEx research fixtures under `scripts/foundry/research/` are D3 scripts, not D11.
- **Source request:** I am fine keeping the usage of a releaseSalt function, but we need to strip the usage of creationCode and constructor argument usage. If there are other cases where it's being used in a FactorySerivce or any other CREATE3 based deployment we need to change that everywhere. But that should probably be a different effort so we don't cofuse the implementors.

## Summary

Remove creation bytecode and constructor arguments from salts used to deploy contracts through the CREATE3 Factory. This covers facets, execution delegates, package contracts, libraries, and other non-proxy contracts deployed through that factory, including calls routed through FactoryServices and registry `deployPkg`. It also covers Crane FactoryServices, tests, and scripts that still fold `PkgInit` or constructor data into a CREATE3 package salt. Standardize component salts to the ABI-encoded name hash, including FullSpread: runtime expressions use `abi.encode(name)._hash()` (`BetterEfficientHashLib`), while constant initializers may use `keccak256(abi.encode(name))` under D14. Keep artifact loading, constructor execution, CREATE3 factories, and registry routing. Retain `ArtifactCreationCode.releaseSalt` as a namespace-only helper. Correct callers, independent formulas, upstream namespace construction, deployment scripts, automatic library deployment, and Crane package-salt deviations; changing only the shared helper does not complete this work. Proxy deployment algorithms, arguments, and salt derivation are outside scope.

This is a separate effort from [Uniswap FullSpread liquidity leak fixes](../contracts/vaults/standard/exchange/protocols/uniswap/uniswap-se-v2-liquidity-leak-fixes.md). Complete that work and record its preservation/validation evidence before implementing this correction. This effort then owns CREATE3 Factory component-salt policy and its deployment compatibility evidence, including the renamed FullSpread services. It does not implement vault accounting fixes or initiate any broadcast.

Paths below are repository-relative. The owner has confirmed the component-name encoding, that runtime in-scope salt hashing uses `BetterEfficientHashLib._hash` while `constant` initializers may use Solidity `keccak256`, the exclusion of proxy deployment, source-level validation with documented existing compile blockers for already-broken archived scripts, Crane CREATE3 package-salt correction including Crane-only tests and scripts, D3 formula updates in the funded-staking runbooks with historical hashes retained, a hermetic IndexedEx test gate for the corrected Crane superchain producers, explicit instance keys for direct test callers, and D3 (not D11) for IndexedEx research fixtures under `scripts/foundry/research/`. The 2026-09-16 follow-up on SuperSim chain-label aliases, Script 24 facet hashing, hook TestDeployLib callers, and D11 TestBase name-only encodings applies those same decisions; it does not add a new owner choice. Review is complete; no open questions remain.

## Constraints

- User direction overrides earlier instructions to retain bytecode/constructor-derived CREATE3 salts. Apply the correction in its own change set after the FullSpread work; FullSpread implementors do not own this repository-wide change.
- Existing CREATE3 authorization, Crane factory deployment, manager/registry package routing, production-first tests, artifact refresh, warm-cache rules, and Forge patience remain mandatory.
- Constructor arguments still initialize contracts. Their removal from address identity must not be implemented by dropping constructor encoding or replacing it with empty bytes.
- Scope is contract deployment through the CREATE3 Factory, excluding proxy deployment. FactoryService names alone do not establish scope; follow each deployment call. A service that deploys both package contracts and proxies changes only its in-scope component-salt expressions.
- Shared and independently written salt helpers must agree with their callers' explicit namespace choices. No compatibility overload may continue to hash forbidden inputs. D8 exempts existing Crane name/label-only encodings from normalization; it does not exempt any in-scope creation-bytecode contribution prohibited by D1. Classify a Crane salt containing creation bytecode as a correction even when it contains no constructor data.
- Salt policy is set by caller kind. IndexedEx production FactoryServices, Init* services, deployment scripts (including `scripts/foundry/research/`), and script libraries use D3 name-only salts written as runtime `abi.encode(name)._hash()` (`BetterEfficientHashLib`) or a value-equal D14 constant; existing Crane name/label-only encodings retain the D8 inventory-only exception. Tests and TestBases that call the CREATE3 factory or registry directly may use explicit instance keys under D11. No caller of any kind may hash creation code or the encoded constructor blob into a CREATE3 Factory salt. Runtime in-scope salt expressions this effort writes must hash through `BetterEfficientHashLib._hash`. Solidity `keccak256` is allowed in constant initializers under D14; this does not relax the required encoding or allowed salt inputs. Assembly `keccak256` inside `BetterEfficientHashLib` itself is out of scope.
- This effort edits Crane FactoryService, test, and script salt expressions that still include `PkgInit` or constructor data, and updates the IndexedEx `lib/crane` submodule pin to that Crane revision. Crane's documented canonical component salt is already `abi.encode(type(X).name)._hash()`, which is D3; superchain package helpers that still encode `pkgInitArgs` are deviations to correct. Crane scripts and tests whose salts contain only name/label inputs and no creation bytecode, `PkgInit`, or constructor data stay inventory-only under D8, including packed or version-labeled strings. Do not rewrite unrelated vendored protocol internals merely because they use CREATE2 or hash code for verification.
