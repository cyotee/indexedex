## Review findings

**No material defect.**

### LOW-1 — "Both amount functions sort their two supplied endpoints" does not describe the amount1 helper's mechanics

- **Location:** PRD `docs/research/pairtoken-unified-prd-20261027-01a17e03/handoff/PRD.md` line 138 (PT-MATH-02); source `lib/v4-core/src/libraries/SqrtPriceMath.sol` line 239 (`uint256 numerator = absDiff(sqrtPriceAX96, sqrtPriceBX96);`) and line 214 (`absDiff`).
- **Invariant or requirement:** PT-MATH-02's amount-delta definitions and the sentence "Both amount functions sort their two supplied endpoints. The amount0 function rejects a zero lower endpoint with `InvalidPrice()` … Amount1 uses the absolute endpoint difference and does not apply that price-zero check."
- **Impact:** None observable. The source's amount1 delta takes the absolute endpoint difference instead of reordering its arguments, and `|a - b|` equals the sorted difference, so every integer result, rounding direction, and the absence of a price-zero check are identical. An implementer following either wording produces the same numbers. The residual risk is purely that a reader infers a comparison-and-swap step in the amount1 path that the source does not perform; the same sentence's next clause already states the absolute-difference rule.
- **Fix direction:** In PRD line 138 only, drop "Both amount functions sort their two supplied endpoints." and keep the existing absolute-difference clause, or restate it as "the amount0 function sorts its endpoints; the amount1 function uses the absolute endpoint difference." Change the PRD only; do not change the source.
- **Evidence class:** Static source reading (`SqrtPriceMath.sol` lines 214-230, 232-250) plus arithmetic equivalence. Not runtime-verified.

### LOW-2 — "Equal bounds produce a division failure" does not name which failure encoding the source produces

- **Location:** PRD line 142 (PT-MATH-03) and PRD line 549 (PT-AC-55); source `src/vendor/uniswap/LiquidityAmounts.sol` lines 22 and 32 (`FullMath.mulDiv(amount0, intermediate, sqrtPriceBX96 - sqrtPriceAX96)` with a zero denominator) and `lib/v4-core/src/libraries/FullMath.sol` line 30 (`require(denominator > prod1);`), which reverts with no data rather than a `Panic(0x12)`.
- **Invariant or requirement:** PT-MATH-03's `L0`/`L1` definitions and "Equal bounds produce a division failure"; PT-ERROR-03's requirement to preserve "checked-arithmetic overflow/underflow, division-by-zero … helper plain reverts" without normalizing them.
- **Impact:** None observable for the integer results the PRD specifies, and the failure class is already covered: PT-MATH-01 defines `MD`/`MU` as rejecting `c = 0` with an unadorned revert, and PT-MATH-03 defines `L0`/`L1` in terms of `MD`, so the matching rule is already stated. The only residual ambiguity is that "division failure" could be read as a Solidity division panic (0x12), which is what the *initialization* path does produce via `TickMath.minUsableTick`/`maxUsableTick` (`TickMath.sol:39-49`, int24 division), whereas the amount-to-liquidity path produces the plain `FullMath` revert. An implementer who normalizes both into one panic would change the revert bytes on a rare path.
- **Fix direction:** In PRD lines 142 and 549 only, distinguish the two: state that the amount-to-liquidity path fails through the `MD`/`MU` helper's unadorned revert (PT-MATH-01) while zero tick spacing in initialization fails through the signed division. Change the PRD only; do not change the source.
- **Evidence class:** Static source reading (`LiquidityAmounts.sol` lines 22, 32; `FullMath.sol` line 30; `TickMath.sol` lines 39-49) plus the PRD's own PT-MATH-01/PT-ERROR-03 cross-references. Not runtime-verified.
