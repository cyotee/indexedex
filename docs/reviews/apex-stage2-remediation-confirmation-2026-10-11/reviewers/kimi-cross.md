### 1b. Ordinary V3 FullSpread SY redemption rejects EOA callers — Astra-01 confirmed; my original corrected

- **Correction to my original:** I listed `UniswapV3FullSpreadStandardExchangeVaultOutQueryTarget.sol` under "files examined where no defect was found" and wrote that ordinary redemption still burns the original caller. That is true only for contract callers. Astra-01 identified the break; I re-verified it independently:
  - `UniswapV3FullSpreadStandardExchangeVaultOutQueryTarget.sol:39-54` — the `_standardRoute` override converts ordinary (`internal_ == false`) share redemption into `ERC20Repo._transfer(msg.sender, address(this), amount_)` followed by a delegatecall to `exchangeIn(..., pretransferred=true, ...)`.
  - The share-input `exchangeIn` route reaches `UniswapV3FullSpreadStandardExchangeVaultOutExecutionDelegate.sol:30-36`, where `pretransferred=true` triggers `LocalCreditLib.requirePretransferCaller(msg.sender)` (:31). The delegatecall chain preserves the original caller, so a code-less holder's ordinary redemption reverts `EOAPretransferNotAllowed`.
  - The family's own regression masks this: `UniswapV3FullSpreadVaultHeldRedeem.t.sol:96-104` (`test_RC01_ordinaryRedeem_burnsCallerShares`) calls as the test contract, which has bytecode, so the EOA failure is never exercised. (My original read this test and did not notice the caller-coverage gap; Astra's observation is correct.)
  - Family inconsistency (fact): Wings ordinary redemption selects `holder = msg.sender` with no bytecode gate (`UniswapV4UpperLowerWingsStandardExchangeVaultMoney.sol:154-156`), and legacy V4's `_standardRoute` override (`UniswapV4StandardExchangeOutMultiQueryTarget.sol:27-35`) routes ordinary redemption to `_redeemVaultHeld` without a bytecode check. Only V3 FullSpread's staged-push design subjects ordinary redemption to the contract-only gate.
- **Adopted finding (credit: Astra-01; independently re-verified):** **Medium, CODE_DEFECT** — ordinary (non-internal-balance) SY redemption on V3 FullSpread is contract-only in effect. FIX_PRD RC-01 intended behavior retains ordinary redemption by the original caller ("An ordinary redemption still burns the original caller's own shares"); converting a pull into a staged push misclassifies the caller's own staged shares as external pretransfer credit. **Impact class:** wallet redemption availability / interface conformance; the staged transfer rolls back on the revert, so no unauthorized burn or loss is established. **Confidence:** high in the call path; the introduction date (this repair round vs. the earlier leak-fix design) cannot be proved without a diff. **Fix direction (prose):** settle ordinary redemption with the original caller as explicit holder without routing it through the pretransfer credit path (or record a scoped owner ruling that SY redemption is contract-only on this family); add an ordinary funded-EOA assertion beside the contract-caller case. Do not weaken the D9 gate at the external true-flag entries.
- This is either a defect introduced by the repair or a pre-existing interaction the repair's test suite fails to detect; either way it contradicts the repair's stated acceptance intent. My K3 "no defect" listing for this file is withdrawn.
