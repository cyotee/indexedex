## Point 2 — the `depositFromInternalBalance` mapping: agree with Astra; dissent from MiniMax's rule 3

Astra (`:120-124`) and my original close the mapping identically: `true` forwards to the vault's existing exact-in pretransfer path for that token (bounded credit, exact consumption, no refund, `TransferDeltaInsufficient` on a short push), and the code-less caller gate `LocalCreditLib.requirePretransferCaller(msg.sender)` runs **explicitly at the SY entry** before credit-sensitive work; `false` is the current measured pull. The family's recorded law is that code-less callers cannot use pretransfer/internal-balance privileges, and `redeem`'s internal-balance branch already gates exactly that way (`NativeStandardYieldTarget.sol:36-39`).

MiniMax's §5 rule 3 (`:302`) says the caller check "is **not** applied to the deposit path because the deposit's tokenIn is a pool currency, not vault-held shares." Dissent. The redeem path's gate is not share-specific law; it is the D9 bytecode rule for pretransfer privileges, and the deposit's true flag is the same privilege on the token leg. Astra's supporting evidence stands unrefuted: the current token credit helper does not itself contain the starter gate, so forwarding alone would let a code-less starter use the new true-flag deposit — exactly the privilege class the family gates. MiniMax's rule 1 also contains a garbled error reference ("revert `SyncMint != 0`"), which I read as a mangled `TransferDeltaInsufficient`; the correct short-credit error is the existing one. **Sentence the PRD must use:** "When `depositFromInternalBalance` is true, the deposit calls `LocalCreditLib.requirePretransferCaller(msg.sender)` before any credit measurement, then consumes the existing exact-in pretransfer path; when false, the current measured pull runs unchanged."
