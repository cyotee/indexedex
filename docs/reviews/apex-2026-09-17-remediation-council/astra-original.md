## Findings

### Astra-01 — Standalone Balancer SE exposes in-flight credit across unguarded external calls

- **Severity:** High
- **File and line:** `contracts/protocols/dexes/balancer/v3/pools/BalancerV3SinglePoolStandardExchange.sol:69–103,131–192,228–275` (particularly `83–89`, `154–174`, and `263–275`).
- **Intended behavior:** D16 includes this standalone adapter; D15 forbids spending booked inventory as caller credit. The adversarial skills require callback safety and no duplicate consumption of an operation's input. D12 accepts resting-credit risk, not callback reuse of an active funded operation.
- **Broken invariant:** Once input is credited to an operation, another entry must not consume it before that operation settles. External token operations must not expose the stale reserve book as reusable credit.
- **Impact class:** Reentrancy; value accounting; token integration.
- **Observed fact:** The contract inherits only `IStandardExchange` (`:22`). Neither money entry has a lock. Input is obtained before external approvals and router calls, and reserve synchronization occurs only after external payout. `_receiveExactIn` validates the transfer delta, but does not reserve that input. `_approvePermit2ToRouter` performs external token approval calls and grants maximum allowances. Its nonzero `amount_` argument does not bound those allowances. Credit calculation remains `balance - _tokenReserve` until settlement.
- **Inference:** A callback-capable configured token can reenter at a point after funding verification but before the outer operation has consumed or booked its input. Nested execution can interfere with the outer credit and allowance lifecycle. Where booked inventory remains, the outer router spend is not independently constrained to an isolated operation balance. This creates a credible booked-inventory-loss class rather than merely the accepted across-transaction donation risk. The downstream router's own lock does not protect token calls occurring before entry to that router.
- **Limit:** No executable reproduction was run, and exploitability for a particular deployed pool/token set is unverified. High severity describes the potential accounting impact; it is not a claim that ordinary fixed-behavior tokens currently exploit it.
- **Fix direction:** Add a shared operation-wide nonreentrancy guard to both money entries, encompassing funding, approval, router execution, refund, payout, and reserve synchronization. Constrain allowances to the required operation budget where compatible. Add production-adapter hostile-token controls covering approval and transfer callbacks, cross-entry attempts, booked-reserve preservation, and exact input/output deltas.
- **Confidence:** Medium overall; high confidence in the missing guard and stale-book window.
- **Evidence label:** Observed fact for control flow; inference for value-loss consequence.

### Astra-02 — ERC-4626 local-first payout sends rounded redemption surplus to the recipient

- **Severity:** Medium
- **File and line:** `contracts/vaults/standard/erc4626/ERC4626StandardExchangeCommon.sol:80–92`; callers `ERC4626StandardExchangeOutTarget.sol:108–115` and `ERC4626StandardExchangeInTarget.sol:144–151` in the same directory. Composing site: `contracts/hooks/uniswap/v4/standardExchange/orbital/UniswapV4StandardExchangeOrbitalBufferHookCommon.sol:550–565`.
- **Intended behavior:** The SE exact-output route delivers the requested underlying amount. R6/D25 require orbital exact-output unwrapping not to create buffered-face surplus in `beforeSwap`; unneeded conversion residual remains protocol backing rather than an unstated payout. Exact-input output reporting must agree with actual delivery.
- **Broken invariant:** Actual recipient payout must equal the accounted output. A rounded-up receipt requirement is not itself an exact-asset payout instruction.
- **Impact class:** Value accounting; token integration; spec nonconformance.
- **Observed fact:** `_payUnderlyingLocalFirst` calls `vault.redeem(vault.previewWithdraw(shortfall), recipient, address(this))`. It checks only `got >= shortfall`, and then transfers the local portion. It does not cap `got`, retain the difference, or return the actual larger amount to the caller. The exact-input caller returns its earlier `amountOut`; the exact-output caller reports only input consumed. Orbital likewise checks only that the SE delivered at least the requested output.
- **Inference:** For a valid non-unit receipt exchange rate, rounding up the receipt requirement followed by redemption can produce more assets than the requested shortfall. The recipient receives that entire redemption. Exact-input return values then under-report actual delivery, and exact-output delivery is no longer exact. When the recipient is an orbital hook during a swap, that excess can remain as newly created unbooked face despite R6/D25. This does not require a fee-on-transfer or rebasing underlying. This finding does not assert an unbounded theft from rounding alone.
- **Test evidence inspected:** `test/foundry/spec/vaults/standard/erc4626/ERC4626StandardExchange_APEX_R14.t.sol:120–138` checks local-first behavior, returned input, and approximate receipt consumption. Its exact-output section does not assert the recipient's underlying balance delta, so that particular assertion set does not prove exact delivery at a non-integral conversion boundary. I did not establish that every other test lacks such coverage.
- **Fix direction:** Use the protocol vault's exact-asset `withdraw` for the shortfall, or redeem into the SE, pay only the specified amount, and book any remainder. Verify that share charging and preview logic remain consistent with the chosen method. Add non-unit-rate, mixed-local/receipt controls that assert recipient deltas, returned amounts, final reserve books, and orbital callback face conservation.
- **Confidence:** High for the rounding mismatch; medium for its breadth across configured integrations.
- **Evidence label:** Observed fact for payout/control flow; inference for non-integral-rate outcomes.
- **Primary API evidence:** EIP-4626 distinguishes `withdraw` (sends exactly the requested assets) from `redeem` (burns exactly the requested shares), and specifies opposing rounding directions. It does not guarantee that `redeem(previewWithdraw(x))` delivers exactly `x`.

### Astra-03 — Current ERC-4626 source comments still prescribe the removed refund and fee-dust behavior

- **Severity:** Low
- **File and line:** `contracts/vaults/standard/erc4626/ERC4626StandardExchangeCommon.sol:201–211,277–281`; `contracts/vaults/standard/erc4626/ERC4626StandardExchangeInTarget.sol:126`; `contracts/vaults/standard/erc4626/ERC4626StandardExchangeOutTarget.sol:17–20`.
- **Intended behavior:** D6 retains residual backing rather than paying dust to `feeTo`; D15 prohibits exact-input refunds and permits only bounded pretransfer exact-output refunds. R13 requires conflicting integration/accounting documentation to be corrected.
- **Broken requirement:** Documentation beside security-critical money paths must describe current credit and payout semantics, not the superseded implementation.
- **Impact class:** Accounting clarity; spec nonconformance.
- **Observed fact:** `_securePull` NatSpec says pull overshoot is refunded immediately; the InTarget repeats that claim. `_burnSeShares` NatSpec says leftover free shares are refunded to the owner, although the helper now burns only the requested amount. OutTarget NatSpec still directs unrefundable dust to `feeTo`, while the current implementation retains it.
- **Inference:** These contradictory comments make the auditor handoff and subsequent maintenance error-prone, and can encourage reintroduction of the very behavior D6/D15 removed. No independent value loss is attributed to comments alone.
- **Fix direction:** Rewrite these comments against current execution and D6/D15, distinguishing the burn helper from its bounded exact-output caller. Review public family documentation for the same stale statements.
- **Confidence:** High.
- **Evidence label:** Observed fact; maintenance consequence is inference.
