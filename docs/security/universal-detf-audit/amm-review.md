## Additional findings

### AMM-01: Public V4 callback does not enter the hook's shared lock

The active `SeTarget.sol:575` `beforeSwap` checks PoolManager and liveness but omits the `nonReentrant` modifier defined at line 86. The selector is installed by `facets/UniswapV4SingleStandardExchangeBufferConstantProductHookSeFacet.sol:58`. This is the active split facet; `Target.sol:503` contains a similar older implementation.

Its exact-in/exact-out execution makes token and SE calls before final reserve synchronization (`SeTarget.sol:643`, `:678`). PoolManager's `take` transfers ERC20 tokens (`lib/crane/contracts/protocols/dexes/uniswap/v4/PoolManager.sol:240`); direct hook SE exchange methods use the shared lock (`SeTarget.sol:788`, `:830`). Therefore the V4 callback does not establish the same exclusion boundary as the direct methods. PoolManager being unlocked is required for swaps and is not a substitute for this hook lock.

Suggested correction: apply the existing shared `nonReentrant` guard to active `beforeSwap`; check both outer-V4-to-direct-hook and outer-direct-hook-to-V4 callback isolation. This is a confirmed missing guard, with no runtime proof of financial impact performed in this bounded review.

### AMM-02: Growth-fee calculation includes incoming liquidity capital

`DepositTarget.sol:665` pulls both tokens before `_deposit`; `_deposit` calls `_mintProtocolFeeIfNeeded` at line 751 and only afterward reconstructs pre-pull reserves at line 755. `_mintProtocolFeeIfNeeded` computes growth using `_wadProduct()` at line 1156. That function reads current reserve balances (`DepositTarget.sol:272`), including the newly pulled raw amount. Thus a fee-on subsequent deposit can produce protocol growth fees from incoming raw capital even when no prior swap or yield grew the reserve. The SE-share deposit variant similarly calls fee mint after receipt of incoming raw and SE balances (`DepositTarget.sol:890`), before `_seDepositPrePullBook` reconstructs the old book.

Suggested correction: settle the growth fee against pre-intake inventory before transfers, or explicitly pass a correctly reconstructed pre-pull reserve product to fee mint. Audit single-sided and generic join entry points for the same ordering when applying the correction. Add a fee-on, no-yield, no-swap balanced second-deposit assertion that protocol LP remains unchanged, covering raw/pair and raw/SE-share intakes. Compare preview and actual minted LP as well. This finding is source-confirmed but not runtime-validated here.

### Runtime evidence and subsequent accounting corrections

The parent's first combined run recorded **112 passes and 19 failures** across 131 tests; see [remediation-regressions.log](evidence/remediation-regressions.log). All four CP `SwapReentrancy` tests passed. `FeeCapital` passed eight tests and failed two: the real-growth raw/pair deposit reverted with `InsufficientLpOut()`, and the SE-share growth deposit minted one more LP atomic unit than its preview. These results do not validate the later corrections below, and do not establish production readiness.

- **Currency-order reserve reconstruction:** `DepositCommon.sol:821`, `_proportionalAddAfterZap`, previously subtracted a pair-denominated addition from the raw balance in two branches. The parent corrected it to subtract `add0` whenever raw is currency0 and `add1` whenever raw is currency1. Added four tests in `test/foundry/spec/hooks/uniswap/v4/standardExchange/constantProduct/single/UniswapV4SingleStandardExchangeBufferConstantProductHook_ZapReserveOrder.t.sol`, covering both inputs and both currency orders with raw/pair decimals 18/6 and initial reserves 300/900. They independently reconstruct post-swap reserves and proportional intake, assert exact LP issuance, and distinguish pre-mint intake from later dust buffering. This correction and these tests postdate the first combined run; runtime validation is pending.
- **SE-share preview rounding:** `DepositCommon.sol:943`, `_previewLaterMintSeShares`, now derives the pair delta as `previewClaim(currentSeBalance + usedSe) - currentClaim`, after rounding `usedSe`. This matches execution's aggregate-claim delta instead of using the unrounded claim budget. Existing exact-equality tests remain unchanged. The correction postdates the first combined run; its runtime result is pending.
- **Unresolved single-deposit preview:** `DepositPreviewTarget.sol:112`, `previewDepositSingle`, clamps and mints against pre-swap reserves and discards `saleAmt`, while execution uses post-swap reserves. This is an independent structural mismatch; the reserve-order correction does not fix it. The separately observed CP claim-purchase preview discrepancy is not evidence of preview parity and has not been conclusively attributed to either defect.
- **Unresolved generic transition quote:** `ClaimLib.sol:34`, `_claimIn`, projects aggregate claim with proportional arithmetic. The current APIs in `lib/crane/contracts/interfaces/IStandardExchangeIn.sol` and `IStandardExchangeOut.sol` quote one exchange in current state. They cannot provide the aggregate claim after a hypothetical rounded unwrap/buffer followed by another intake. Even the ERC4626 wrapper applies nested vault-share and underlying conversion rounding (`contracts/vaults/standard/erc4626/ERC4626StandardExchangeCommon.sol`); collapsing those steps is not generally exact. The raw/pair growth failure remains under trace investigation. An exact generic zap preview requires an SE-specific transition quote capability supporting sequential operations and returning aggregate holder claims after each operation, including downstream rounding and dilution. A post-swap reserve adjustment alone or a fixed-rate approximation is insufficient to claim equality.

Production filenames abbreviated in these bullets use the package directory and prefix defined at the top of this report. No equality assertion was relaxed, no approximate preview correction was applied, and the unresolved quote capability is a remaining implementation requirement.
